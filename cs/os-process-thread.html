Program, process and threadProgram, process और thread

Beginnerशुरुआती

Think of a restaurant. The recipe book is a program (just instructions on disk). A running kitchen using that recipe is a process: it has its own space and ingredients (memory). The cooks inside the kitchen are threads: they work at the same time and share the same ingredients.

एक restaurant सोचिए। Recipe book एक program है (disk पर सिर्फ़ निर्देश)। उस recipe से चलती kitchen एक process है: उसकी अपनी जगह और सामान (memory) है। Kitchen के अंदर के cooks threads हैं: वो एक साथ काम करते हैं और वही सामान बाँटते हैं।

Context switching, concurrency and parallelismContext switching, concurrency और parallelism

  • Context switch: the CPU pauses one task, saves its state, and loads another. Done thousands of times a second, it makes many programs look like they run together. Each switch has a small cost.Context switch: CPU एक task रोकता है, उसकी हालत save करता है, और दूसरा load करता है। एक second में हज़ारों बार होने से कई programs साथ चलते लगते हैं। हर switch की थोड़ी cost होती है।
  • Concurrency: dealing with many tasks by switching between them. One cook handling three orders, a bit of each.Concurrency: बीच-बीच में switch करके कई tasks संभालना। एक cook तीन orders, थोड़ा-थोड़ा हर एक।
  • Parallelism: really doing tasks at the same instant on multiple CPU cores. Three cooks, one order each.Parallelism: कई CPU cores पर सच में एक ही पल tasks करना। तीन cooks, हर एक का एक order।

Node.js note: your JavaScript runs on one main thread with an event loop. It's great at concurrency (waiting for many network calls), but heavy CPU work blocks everything. For that, use worker threads or separate processes.

Node.js note: आपकी JavaScript एक main thread पर event loop के साथ चलती है। यह concurrency में बढ़िया है (कई network calls का इंतज़ार), पर भारी CPU काम सब कुछ रोक देता है। उसके लिए worker threads या अलग processes इस्तेमाल कीजिए।

Race condition: when sharing goes wrongRace condition: जब बाँटना ग़लत हो जाए

Two tasks read the same value, both change it, and one overwrites the other. Classic example: two withdrawals from the same bank account at the same time.

दो tasks एक ही value पढ़ते हैं, दोनों उसे बदलते हैं, और एक दूसरे को overwrite कर देता है। Classic उदाहरण: एक ही bank account से एक साथ दो withdrawals।

// You can run this in Node.js. Balance 1000, withdraw 300 and 500 at the same time.
let balance = 1000;
const wait = (ms) => new Promise((r) => setTimeout(r, ms));

async function withdraw(amount) {
  const current = balance;      // 1. read
  await wait(10);               // 2. something slow, like a database call
  balance = current - amount;   // 3. write
}

await Promise.all([withdraw(300), withdraw(500)]);
console.log(balance); // expected 200, but prints 500: one withdrawal was lost!

Both withdrawals read 1000 before either wrote. The second write wiped out the first. This happens in databases, threads and async code alike.

दोनों withdrawals ने किसी के लिखने से पहले 1000 पढ़ा। दूसरे write ने पहले को मिटा दिया। यह databases, threads और async code, सब में होता है।

The fix: a lock (only one at a time)हल: एक lock (एक बार में एक)

balance = 1000;
let lock = Promise.resolve();

function safeWithdraw(amount) {
  // wait for the previous withdrawal to finish, then run this one
  lock = lock.then(async () => {
    const current = balance;
    await wait(10);
    balance = current - amount;
  });
  return lock;
}

await Promise.all([safeWithdraw(300), safeWithdraw(500)]);
console.log(balance); // 200 ✅

We ran both snippets: the first prints 500, the fixed one prints 200. In threads, the same idea is a mutex. In databases, it's a transaction with row locking, or an atomic update like UPDATE accounts SET balance = balance - 300 WHERE id = 1.

हमने दोनों snippets चलाए: पहला 500 print करता है, ठीक किया हुआ 200। Threads में यही idea mutex है। Databases में row locking वाला transaction, या UPDATE accounts SET balance = balance - 300 WHERE id = 1 जैसा atomic update।

⚠️ Common mistakesआम ग़लतियाँ
  • Saying threads have separate memory. Threads share their process's memory; processes are separate.यह कहना कि threads की memory अलग होती है। Threads अपने process की memory बाँटते हैं; processes अलग होते हैं।
  • Mixing up concurrency (switching) and parallelism (truly simultaneous).Concurrency (switch करना) और parallelism (सच में एक साथ) में गड़बड़।
  • Thinking JavaScript is free of race conditions because it's single-threaded. Async code can still interleave.यह सोचना कि JavaScript single-threaded है इसलिए race conditions नहीं होतीं। Async code फिर भी बीच में घुल-मिल सकता है।
📌 Remember these 3 thingsये 3 बातें याद रखिए
  1. Process = running program with its own memory. Thread = worker inside it, sharing memory.Process = अपनी memory वाला चलता program। Thread = उसके अंदर का worker, memory बाँटता है।
  2. Concurrency = switching between tasks; parallelism = truly at the same time.Concurrency = tasks के बीच switch; parallelism = सच में एक साथ।
  3. Shared data + no lock = race condition. Fix with locks, transactions or atomic updates.Shared data + कोई lock नहीं = race condition। Locks, transactions या atomic updates से ठीक कीजिए।

Practiceप्रैक्टिस

Exercise 1: A ticket booking site sometimes sells the same seat to two people. Explain why, and give two fixes.Exercise 1: एक ticket booking site कभी-कभी एक ही seat दो लोगों को बेच देती है। क्यों, समझाइए, और दो हल दीजिए।

Show a sample answerएक sample जवाब देखें
  • Why: a race condition. Both requests checked "is seat 12 free?" before either saved the booking.क्यों: race condition। दोनों requests ने booking save होने से पहले "seat 12 ख़ाली है?" check किया।
  • Fix 1: an atomic update: UPDATE seats SET status = 'BOOKED', user_id = 7 WHERE id = 12 AND status = 'FREE', and treat "0 rows updated" as "already taken".हल 1: atomic update: UPDATE seats SET status = 'BOOKED', user_id = 7 WHERE id = 12 AND status = 'FREE', और "0 rows updated" को "पहले ही बिक गई" मानिए।
  • Fix 2: lock the row inside a transaction (SELECT … FOR UPDATE), or a unique constraint so the database itself refuses a second booking.हल 2: transaction के अंदर row lock कीजिए (SELECT … FOR UPDATE), या unique constraint ताकि database ख़ुद दूसरी booking मना कर दे।
