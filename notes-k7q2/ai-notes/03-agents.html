Level 3: Tool Calling, AI Agents & MCP ⭐

The problem this level solves

An LLM on its own can only talk. It can't check a database, book an appointment, send a WhatsApp message or read today's date. Tool calling gives it hands. Agents let it use those hands step by step to finish a goal.

One-line summary

Tool calling = the LLM asks your code to run a function → an agent = an LLM in a loop that keeps choosing tools until the goal is done → MCP = a standard plug for connecting tools to any AI app.

1. Tool calling (function calling)

You describe your functions to the LLM. When it needs one, it replies with "call this function with these arguments" (structured JSON). Your code runs it, then sends the result back, and the LLM writes the final answer.

Tools you give the LLM:
  getAvailableSlots(date)
  bookSiteVisit(name, phone, propertyId, slot)

User: "Kal Sector 150 wala 3BHK dekhna hai"
LLM → { tool: "getAvailableSlots", args: { date: "2026-10-19" } }   ← LLM only ASKS
Your code → runs DB query → ["11:00", "16:00"]                      ← YOUR code executes
LLM → "Kal 11 baje ya 4 baje, kaunsa time theek rahega?"

Key point: the model never executes anything itself. It only requests; your backend decides and executes. That's where you put validation and permissions.

🎤 "Tool calling lets the model return a structured request to invoke a function I've defined. My application executes it and returns the result to the model. The model decides what to call; my code controls whether and how it runs."

2. AI agent

An LLM running in a loop: think → act (call a tool) → observe the result → repeat until the goal is done.

Goal: "Is lead ko qualify karke site visit book karo"

Loop 1: Think: budget pata nahi       → Act: ask user budget        → Observe: "1.5 Cr"
Loop 2: Think: matching property?     → Act: searchProperties(...)  → Observe: 2 options
Loop 3: Think: slot chahiye           → Act: getAvailableSlots()    → Observe: 11:00, 16:00
Loop 4: Think: user ne 4 baje bola    → Act: bookSiteVisit(...)     → Observe: booked ✅
Loop 5: Think: broker ko batana hai   → Act: notifyBroker(...)      → Done

Real example: Claude Code (the tool you're using right now) is an agent. It reads files, runs commands, checks the output and decides the next step on its own.

🎤 "An agent is an LLM that plans and executes multi-step tasks by calling tools in a loop, using each result to decide the next action until the goal is met."

3. Chatbot vs workflow vs agent

Chatbot Workflow Agent
What it does Answers questions Fixed steps written by you (step 1 → 2 → 3) Decides the steps itself
Flexible? Low Medium High
Predictable? High High Lower
Example FAQ bot "New lead → send template → add to CRM" "Qualify this lead and book a visit, however it takes"

Senior insight: don't use an agent when a workflow is enough. Workflows are cheaper, faster and easier to debug. Use agents only where the path genuinely varies.

4. Memory

  • Short-term: the current conversation (lives in the context window).
  • Long-term: saved facts across conversations (stored in your DB, fetched back with RAG). For example: "This lead wanted 3BHK under 1.5 Cr last week."

5. Multi-agent

Several specialised agents working together, each with its own tools and prompt. Example: Qualifier agent (asks questions) → Property-matching agent (searches listings) → Scheduler agent (books visits). Useful for complex systems, but adds cost and complexity. Start with one agent.

6. MCP (Model Context Protocol)

An open standard (introduced by Anthropic in 2024) for connecting AI apps to tools and data.

  • Before MCP: every AI app needed custom integration code for every tool.
  • With MCP: build an MCP server once (e.g. "Kodivo CRM"), and any MCP-compatible AI app (Claude, IDEs, agents) can use it.
  • Analogy: USB-C for AI. One plug, many devices.

🎤 "MCP is an open protocol that standardises how AI applications connect to external tools and data sources, so a tool built once as an MCP server can be used by any MCP-compatible client."

7. Guardrails & human-in-the-loop (production must-haves)

Agents can make mistakes, so in production:

  • Validate tool arguments (is the phone number valid? does the slot exist?)
  • Permissions: the agent can read listings but can't delete them
  • Human approval for risky actions (refunds, payments, sending bulk messages)
  • Max steps / timeouts so the loop can't run forever (and burn money)
  • Logging of every tool call for debugging and audits
  • Evals: test the agent on sample conversations before every release

🎤 "In production I'd add argument validation, least-privilege tools, human approval for irreversible actions, step limits, full tool-call logging and evals."
