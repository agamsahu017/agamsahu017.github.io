Level 5: System Design (HLD + LLD) for Interviews

With 8 years of experience, this round decides if you are seen as senior. You don't need fancy words. You need to explain clearly, think about scale, and talk about trade-offs (what you gain and what you lose with each choice).

In one line

HLD (high-level design) = draw the big picture: which services, database, cache and queue, and how they talk → LLD (low-level design) = design the classes and code inside one part (clean code, SOLID, patterns) → in both, always say why you chose something and what breaks when the system grows.

Example: building a house. HLD = the floor plan (how many rooms, where the kitchen and water tank go). LLD = the wiring and furniture inside one room.

Part A: How to answer an HLD question (use this every time)

Don't jump straight to the diagram. Follow these 7 steps, out loud:

Step What you say Time
1. Requirements "What must it do? How fast, how many users, how reliable?" 3–5 min
2. Estimates Users per day → requests per second → storage 3 min
3. APIs The 3–5 main endpoints 3 min
4. Data model Main tables, and which database 5 min
5. Diagram Client → Load balancer → Services → Cache / Database / Queue 10 min
6. Deep dive Pick the 1–2 hardest parts and explain them in detail 15 min
7. Trade-offs "If this part fails, what happens? What would I change at 10 times the users?" 5 min

🎤 "Before I design, let me confirm what the system must do and how big it is, because the design is very different for 1,000 users and 10 million users." (Interviewers like this first line.)

Example: a tailor takes measurements before cutting cloth. Designing without requirements = stitching without measurements.

Quick estimate maths (remember these)

  • 1 day ≈ 1 lakh seconds (86,400, round it to 100,000)
  • 10 lakh (1 million) requests a day ≈ 12 requests a second. Peak = 2–3 times the average.
  • 1 crore (10 million) requests a day ≈ 120 requests a second
  • 1 image ≈ 200 KB to 1 MB. 1 text row ≈ 1 KB.
  • Reads are usually 10 to 100 times more than writes, so a cache helps a lot.

Part B: Building blocks

Every HLD is made of these parts. Know what each one does and when to use it.

1. Load balancer

Spreads incoming traffic over many servers so no single server is overloaded.

  • Example: the token counter in a hospital that sends each patient to whichever doctor is free.
  • Keep servers stateless (don't keep user sessions on the server; keep them in Redis or a JWT), so any server can handle any request.

2. Scaling

  • Vertical = a bigger machine (more RAM and CPU). Easy, but it has a limit, and if it fails everything fails.
  • Horizontal = more machines behind a load balancer. This is how real systems grow.

Example: a busy dhaba. Vertical = buying a bigger stove for the same cook. Horizontal = hiring more cooks with more stoves.

3. Database: SQL vs NoSQL

Use SQL (Postgres, MySQL) when Use NoSQL (DynamoDB, Mongo) when
Data is linked (users, orders, payments) Very large scale, simple lookups by key
You need transactions (money!) The structure changes often
You need complex queries and reports You need very fast writes

Example: SQL = a bank ledger where every column is fixed and the totals must match. NoSQL = labelled boxes in a cupboard where each box can hold anything.

🎤 "Payments and orders go in SQL because I need safe transactions. Large, simple data like sessions or download logs can go in NoSQL." (You did this on ampleimages: MySQL + DynamoDB.)

4. Indexing

Like the index at the back of a book. Makes reads fast, makes writes a little slower. Add indexes on the columns you filter, join or sort on.

5. Replication (copies)

  • The primary database takes writes. Read replicas (copies) take reads.
  • Good for apps with many reads. Copies get new data after a small delay (replication lag).

Example: a school notice. The principal writes the original (primary); photocopies go to every class notice board (replicas). Students read the copies, and a new notice reaches the boards a few minutes later (lag).

6. Sharding (splitting)

When one database is too big, split the data over many databases. For example users A–M in database 1 and N–Z in database 2, or by user_id % 4.

  • Choose a shard key that spreads data evenly. A bad key puts all the load on one database (a "hot shard").
  • Joins across shards are hard, so avoid them.

Example: a bank with too many customers for one branch opens more branches by area. If every new customer is sent to the Gomti Nagar branch, that one branch gets crowded (hot shard).

7. Cache (Redis)

Keep often-read data in memory, so reads are very fast.

  • Cache-aside (most common): the app checks the cache → if it's not there, read the database → save it in the cache with a TTL (expiry time).
  • Problem: when data changes, the cache can show old data. Delete or update the cache key on every change.
  • Cache stampede: many requests miss the cache at the same time and all hit the database. Fix it with a lock or different expiry times.

Example: a shopkeeper keeps the 20 most-sold items on the front counter (cache) instead of going to the godown (database) every time. When the price changes, he must change the price tag on the counter too.

🎤 "I'd use cache-aside with Redis and a TTL, and delete the key on update so users don't see old data."

8. CDN

Keeps copies of static files (images, JS, CSS, videos) on servers near the user. A Delhi user gets images from a server in Delhi, not from the US.

  • You used this on ampleimages for 15,000 images ✅

Example: Amul milk comes from your city's local depot, not from Anand (Gujarat) every time.

9. Message queue (Kafka, SQS, RabbitMQ)

Do slow work in the background. The API replies fast; a worker does the job later.

  • Example: a restaurant order slip. The waiter takes the order and leaves; the kitchen cooks at its own speed.
  • Use it for emails, notifications, image resizing, reports and AI work.
  • Retry failed jobs. After a few failures, move the job to a dead letter queue (DLQ) so you can check it.

10. Object storage (S3)

For files. The database stores only the file path or URL, never the file itself.

  • Pre-signed URL: the browser uploads straight to S3, so your server does not carry the heavy file.

Example: a library register stores the rack number, not the book. A pre-signed URL is a one-time pass from the guard that lets you drop goods straight into the godown.

11. WebSockets

A connection that stays open, so the server can push data (chat, live notifications, live scores). With normal HTTP, the browser has to ask every time.

Example: HTTP = calling again and again to ask "have you reached?". WebSocket = keeping the call on, so they tell you the moment they reach.

Part C: Important ideas (follow-up questions)

CAP theorem (simple)

When the network between servers breaks, you must choose one:

  • Consistency: everyone sees the latest data (or gets an error). Use for bank balance, seat booking.
  • Availability: always reply, even if the data is a little old. Use for like counts, news feed.

Example: the bank's link is down. An ATM can refuse to give money (consistency: no risk of wrong balance) or show your last known balance (availability: always answers, maybe old).

🎤 "For payments I choose consistency. For a feed or a like counter, slightly old data is fine, so I choose availability."

Eventual consistency

The data becomes the same everywhere after a short time. Example: you post on Instagram and your friend sees it 2 seconds later. That is fine.

Idempotency ⭐ (very important for payments)

Sending the same request twice gives the same result as sending it once.

  • Problem: the user clicks "Pay" twice, or the network retries, and money is taken twice ❌
  • Fix: the client sends an idempotency key (a unique ID). The server saves it. If the same key comes again, it returns the saved result instead of charging again.
  • Also: payment gateway callbacks (webhooks) can arrive twice. Check if the order is already paid before updating it.

Example: pressing the lift button 5 times still calls the lift once. Paying twice for the same order must still charge once.

Rate limiting methods

  • Fixed window: 100 requests per minute. Simple, but a burst at the edge of two windows can let in about 200.
  • Sliding window: smoother and more exact.
  • Token bucket ⭐: a bucket fills with tokens at a fixed speed; each request uses one token. Allows small bursts. The most common answer.
  • Keep the counters in Redis so all servers share them.

Example: a token bucket is like a ration shop that gets 10 tokens every hour. Each customer needs one token. If tokens run out, the next person waits.

Transactions across services: Saga

One order touches many services (order, payment, stock). If payment fails, run undo steps (give back the stock, cancel the order) instead of one big transaction.

Example: booking a trip: train, hotel and cab. If the hotel booking fails, you cancel the train ticket you already booked (an undo step).

Reliability tools

  • Retry with growing wait: wait 1s, then 2s, then 4s… (don't keep hitting a failing service)
  • Circuit breaker: if a service keeps failing, stop calling it for a while and return a backup answer. Example: the MCB at home trips when there is a fault, so the whole house does not burn.
  • Monitoring: logs, metrics and alerts (CloudWatch, Grafana).

Optimistic vs pessimistic locking (booking problems)

  • Pessimistic: lock the row while booking (SELECT ... FOR UPDATE). Safe but slower.
  • Optimistic: read the row with a version number; update only WHERE version = old_version. If 0 rows change, someone else booked first, so show an error.

Example: pessimistic = locking the changing-room door while you try clothes. Optimistic = two people fill the last form; whoever submits first wins, the second is told "already taken".

Part D: Top HLD questions with short answers

These are outlines: what to draw, plus the 1–2 key points the interviewer wants to hear.

1. URL shortener (like bit.ly)

  • API: POST /shorten {longUrl} → abc123; GET /abc123 → redirect (301/302)
  • Short code: an auto-increment ID turned into base62 (a–z, A–Z, 0–9). 7 characters give about 3.5 lakh crore combinations.
  • Many more reads than writes → Redis cache for popular links.
  • Key point: how you make unique codes without clashes (a counter, or a range of IDs given to each server).

Example: a courier tracking number: a short code instead of the long address, and it leads to all the details.

2. Rate limiter

  • Sits before the services (middleware or API gateway). Token bucket in Redis, with the key = user ID or IP.
  • Return HTTP 429 with a Retry-After header.
  • Key point: a shared counter in Redis, so it works across many servers.

3. Notification system (email, SMS, push)

  • API → queue → a separate worker for each channel → provider (SES, SMS gateway, FCM).
  • Table of user choices (did they turn off SMS?), templates, retry + DLQ, priority (OTP = high, marketing = low).
  • Key point: send in the background with queues; never send inside the API call.

Example: a post office. Letters go to sorting (queue), then separate postmen for speed post, normal post and courier (workers). Urgent letters (OTP) go first.

4. Chat app (like WhatsApp)

  • WebSocket servers keep connections open. Redis remembers "user X is connected to server 3".
  • Message flow: sender → chat server → save in database → push to receiver if online; if not, save it and send a push notification.
  • Ticks: sent ✓, delivered ✓✓, read 🔵 are status updates.
  • Key point: message order (a sequence number per chat) and delivery to offline users.

5. News feed (like Instagram or LinkedIn)

  • Fan-out on write: when you post, add it to every follower's feed cache. Fast to read. Bad for celebrities with 1 crore followers.
  • Fan-out on read: build the feed when the user opens the app. Slow to read.
  • Mix ⭐: normal users = on write; celebrities = on read, then merge.

Example: on write = the newspaper boy drops a paper at every house. A celebrity has too many houses to deliver to, so people pick it up from the stall themselves (on read).

6. Ticket booking (like BookMyShow)

  • Hardest part: two people booking the same seat.
  • When a user picks a seat → hold it for 5–10 minutes (a Redis key with expiry, or a LOCKED status with an expiry time).
  • Payment works → BOOKED. Payment fails or times out → the hold ends → the seat is free again.
  • Key point: strong consistency + locking + idempotent payment.

7. Online store checkout + payment

  • Order status: CREATED → PAYMENT_PENDING → PAID → SHIPPED (or FAILED / CANCELLED).
  • Send the user to the payment gateway → webhook comes back → check its signature → mark it paid (idempotent!).
  • A cron job checks pending orders with the gateway, in case a webhook was lost.
  • Key point: idempotency, checking webhooks, and never trusting a "success" message from the frontend.

8. Image / file upload service

  • Browser asks the API for a pre-signed URL → uploads straight to S3 → S3 event → queue → worker makes thumbnails or watermarks → files served through a CDN.
  • The database keeps details (path, size, owner, tags).
  • Key point: don't send big files through your server; use a CDN for reads.

9. Search autocomplete

  • A trie (prefix tree) that keeps the top 5–10 suggestions at each node.
  • Work out popular searches in advance, cache results for common starting letters, and wait about 300 ms after typing before calling the API (debounce).

Example: a dictionary opens straight to the pages for "s", so you don't flip through the whole book.

10. Job scheduler / cron at scale

  • A jobs table (run_at, status); workers check it or use a delayed queue.
  • A distributed lock (Redis) so two servers don't run the same job. Retries + jobs that are safe to run twice.

Part E: AI system design (your edge for AI full stack jobs 🔥)

11. RAG chatbot at scale

Saving (in the background):  documents → cut into pieces → embeddings → vector database (pgvector / Pinecone)
Answering (live):            question → embedding → find top pieces → (re-rank) → prompt + pieces → LLM → stream the answer
  • Cache answers to repeated questions.
  • Stop made-up answers: "answer only from the context, otherwise say you don't know"; show the sources.
  • Separate data per customer: filter by tenant_id in every search, so company A never sees company B's documents.
  • Use a queue for saving (making embeddings for big PDFs is slow).
  • Test it: a set of questions and answers; measure if the right pieces were found and if the answers are good.

Example: a CA firm with 100 clients keeps each client's file in a separate cupboard, and an employee gets the key to that client's cupboard only (tenant filter).

12. LLM gateway (one service in front of all AI calls)

  • One place for: API keys, model routing (cheap model for easy tasks, big model for hard ones), backup if a provider is down, rate limits per user, token and cost tracking, logs and caching.
  • Key point: cost control + reliability.

Example: an office reception desk. Every outside call goes through it, gets written in the register, and is sent to the right department.

13. AI agent system

  • Loop: the LLM decides → calls a tool (API or database) → gets the result → decides again → final answer.
  • Add: a step limit, timeouts, human approval for risky actions (payments, deletes), memory (chat + long-term in the database). Long tasks run in a queue/worker, and the user sees progress by polling or WebSocket.

14. WhatsApp AI support bot

  • WhatsApp webhook → queue → worker: load the user's history (Redis or database) → RAG → LLM → reply through the WhatsApp API.
  • Hand over to a human when the bot is unsure or the user says "talk to a person".

🎤 "The main problems in LLM systems are speed, cost and made-up answers, so I'd add streaming, caching, model routing, RAG and regular tests."

Part F: LLD (Low-Level Design)

What they check

  1. Can you find the right classes from a problem?
  2. Clean code: SOLID, design patterns, no giant if-else.
  3. Edge cases and two users doing the same thing at the same time.
  4. (Machine coding round) working code in 60–90 minutes.

LLD answer steps

  1. Ask what is in scope.
  2. List the things (nouns become classes): ParkingLot, Floor, Spot, Vehicle, Ticket.
  3. How they are linked (has-a / is-a).
  4. Main methods (verbs): park(), unpark(), calculateFee().
  5. Use patterns where they fit naturally.
  6. Write code for the main flow first, then the extras.

SOLID in simple words

Letter Meaning Simple example
S Single responsibility One class = one job InvoiceService does not also send emails. (A tailor stitches; he doesn't also deliver.)
O Open/closed Add new features without changing old code A new payment method = a new class, not a new if. (Plug a new device into the extension board; don't rewire the house.)
L Liskov substitution A child class must work wherever the parent works Bike extends Vehicle must not break park()
I Interface segregation Small, focused interfaces Don't force a Printer to have fax()
D Dependency inversion Depend on interfaces, not on exact classes A service gets a PaymentGateway injected (NestJS DI!). (A phone charges from any brand's USB-C cable.)

Design patterns (most asked)

Pattern In one line Example
Strategy ⭐ Swap the method at runtime Fee: hourly vs daily; Notification: email / SMS / push. (Choosing car / bike / walk in Google Maps.)
Factory One place creates the right object VehicleFactory.create('car')
Observer Tell subscribers when something changes Seat freed → tell waiting users; event emitters. (YouTube's bell icon.)
Singleton Only one object of the class Database pool, config, logger
Decorator Add behaviour without changing the class Add logging or caching around a service; NestJS decorators. (Putting a cover on your phone.)
Adapter Make a different interface fit Put BillDesk and Razorpay behind one PaymentGateway. (A travel plug adapter.)
State Behaviour changes with the state Order: Created → Paid → Shipped; approval workflows
Builder Build a complex object step by step Query builders, report builders. (Ordering a Subway sandwich step by step.)

NestJS angle (your strength, use it!)

  • DI (dependency injection) is dependency inversion in action: services get what they need through the constructor.
  • Guards = permission checks, Interceptors = like Decorators (logging, shaping the response), Pipes = input checks, Modules = keep features separate.

🎤 "In NestJS, my service depends on an interface token like PAYMENT_GATEWAY. Switching from BillDesk to Razorpay is just a new provider, with no change in the service. That is Strategy plus dependency inversion."

Top LLD problems (practise these)

  1. Parking lot ⭐: Strategy for the fee, Factory for vehicles and spots, handle two cars taking the same spot.
  2. LRU cache ⭐: HashMap + doubly linked list → get/put in O(1). (In JS, a Map keeps insert order: delete and set again on each use.)
  3. BookMyShow: Show, Screen, Seat, Booking; seat hold with expiry.
  4. Splitwise: User, Group, Expense, split types (equal / exact / percent), simplify debts.
  5. Rate limiter class: token bucket with allowRequest(userId).
  6. Elevator: State pattern, request order.
  7. Notification service: Strategy per channel + Observer.
  8. In-memory key-value store with expiry.
  9. Vending machine (State), Snake & Ladder, Logger (Chain of Responsibility).

Mini code: LRU cache (JS, often asked live)

Example: your phone's "recent apps": when space runs out, the app you used longest ago is removed first.

class LRUCache {
  constructor(capacity) { this.capacity = capacity; this.map = new Map(); }
  get(key) {
    if (!this.map.has(key)) return -1;
    const val = this.map.get(key);
    this.map.delete(key); this.map.set(key, val); // move to "most recent"
    return val;
  }
  put(key, val) {
    if (this.map.has(key)) this.map.delete(key);
    this.map.set(key, val);
    if (this.map.size > this.capacity) this.map.delete(this.map.keys().next().value); // oldest
  }
}

Level 5: Interviews के लिए System Design (HLD + LLD)

8 साल के experience पर यही round तय करता है कि आपको senior माना जाए या नहीं। भारी शब्दों की ज़रूरत नहीं। ज़रूरत है साफ़ समझाने, scale के बारे में सोचने, और trade-offs बताने की (हर फ़ैसले से क्या मिलता है और क्या खोते हो)।

एक line में

HLD (high-level design) = बड़ी तस्वीर बनाओ: कौन सी services, database, cache और queue, और वे आपस में कैसे बात करते हैं → LLD (low-level design) = एक हिस्से के अंदर classes और code design करो (clean code, SOLID, patterns) → दोनों में हमेशा बताओ कि कोई चीज़ क्यों चुनी और system बढ़ने पर क्या टूटेगा।

उदाहरण: घर बनाना। HLD = नक्शा (कितने कमरे, kitchen कहाँ, पानी की tank कहाँ)। LLD = एक कमरे के अंदर की wiring और furniture।

  • Reads आमतौर पर writes से 10 से 100 गुना ज़्यादा होते हैं, इसलिए cache बहुत मदद करता है।

Part B: Building blocks

हर HLD इन्हीं हिस्सों से बनता है। जानो कि हर एक क्या करता है और कब इस्तेमाल होता है।

1. Load balancer

आने वाला traffic कई servers में बाँटता है ताकि किसी एक server पर ज़्यादा बोझ न पड़े।

  • उदाहरण: अस्पताल का token counter जो हर मरीज़ को उस डॉक्टर के पास भेजता है जो खाली है।
  • Servers को stateless रखो (user sessions server पर नहीं, Redis या JWT में), ताकि कोई भी server कोई भी request संभाल सके।

2. Scaling

  • Vertical = बड़ी machine (ज़्यादा RAM और CPU)। आसान, पर एक सीमा है, और वह fail हुई तो सब कुछ fail।
  • Horizontal = load balancer के पीछे ज़्यादा machines। असली systems ऐसे ही बढ़ते हैं।

उदाहरण: भीड़ वाला ढाबा। Vertical = उसी cook के लिए बड़ा चूल्हा। Horizontal = ज़्यादा cooks और ज़्यादा चूल्हे।

3. Database: SQL vs NoSQL

SQL (Postgres, MySQL) तब इस्तेमाल करो जबNoSQL (DynamoDB, Mongo) तब इस्तेमाल करो जब
Data आपस में जुड़ा हो (users, orders, payments)बहुत बड़ा scale, key से सीधी lookup
Transactions चाहिए (पैसा!)Structure बार-बार बदलता हो
Complex queries और reports चाहिएबहुत तेज़ writes चाहिए

उदाहरण: SQL = बैंक का ledger, हर column तय और हिसाब पक्का। NoSQL = अलमारी के डिब्बे, हर डिब्बे पर label, अंदर कुछ भी रख सकते हो।

🎤 "Payments and orders go in SQL because I need safe transactions. Large, simple data like sessions or download logs can go in NoSQL." (आपने ampleimages पर यही किया था: MySQL + DynamoDB।)

4. Indexing

किताब के पीछे वाले index जैसा। Reads तेज़ करता है, writes थोड़े धीमे। जिन columns पर filter, join या sort करते हो, उन पर index लगाओ।

5. Replication (copies)

  • Primary database writes लेता है। Read replicas (copies) reads लेती हैं।
  • ज़्यादा reads वाले apps के लिए अच्छा। Copies को नया data थोड़ी देर से मिलता है (replication lag)।

उदाहरण: school का notice। Principal original लिखते हैं (primary); photocopies हर class के notice board पर लगती हैं (replicas)। बच्चे copies पढ़ते हैं, और नया notice boards तक कुछ मिनट बाद पहुँचता है (lag)।

6. Sharding (बाँटना)

जब एक database बहुत बड़ा हो जाए, data को कई databases में बाँट दो। जैसे A–M वाले users database 1 में और N–Z वाले database 2 में, या user_id % 4 से।

  • ऐसी shard key चुनो जो data बराबर बाँटे। खराब key सारा बोझ एक database पर डाल देती है ("hot shard")।
  • Shards के पार joins मुश्किल हैं, इनसे बचो।

उदाहरण: एक branch में ज़्यादा customers हो गए तो bank इलाकों के हिसाब से नई branches खोलता है। अगर हर नए customer को Gomti Nagar branch ही भेजो, तो वही branch भर जाएगी (hot shard)।

7. Cache (Redis)

बार-बार पढ़ा जाने वाला data memory में रखो, ताकि reads बहुत तेज़ हों।

  • Cache-aside (सबसे common): app पहले cache देखता है → न मिले तो database से पढ़ो → TTL (expiry time) के साथ cache में रख दो।
  • समस्या: data बदलने पर cache पुराना data दिखा सकता है। हर बदलाव पर cache key delete या update करो।
  • Cache stampede: बहुत सारी requests एक साथ cache miss करती हैं और सब database पर टूट पड़ती हैं। Lock या अलग-अलग expiry times से ठीक करो।

उदाहरण: दुकानदार सबसे ज़्यादा बिकने वाली 20 चीज़ें सामने counter पर रखता है (cache), हर बार godown (database) नहीं जाता। दाम बदले तो counter वाला price tag भी बदलना पड़ता है।

🎤 "I'd use cache-aside with Redis and a TTL, and delete the key on update so users don't see old data."

8. CDN

Static files (images, JS, CSS, videos) की copies user के पास वाले servers पर रखता है। Delhi का user images Delhi के server से लेता है, US से नहीं।

  • आपने ampleimages पर 15,000 images के लिए यह इस्तेमाल किया था ✅

उदाहरण: Amul का दूध हर शहर के local depot से आता है, हर बार Anand (Gujarat) से नहीं।

9. Message queue (Kafka, SQS, RabbitMQ)

धीमे काम background में करो। API जल्दी जवाब देती है; worker काम बाद में करता है।

  • उदाहरण: restaurant की order पर्ची। Waiter order लेकर चला जाता है; kitchen अपनी speed से खाना बनाती है।
  • Emails, notifications, image resize, reports और AI के काम के लिए इस्तेमाल करो।
  • Fail हुए jobs को retry करो। कुछ बार fail होने के बाद job को dead letter queue (DLQ) में डाल दो ताकि बाद में देख सको।

10. Object storage (S3)

Files के लिए। Database में सिर्फ़ file का path या URL रखो, file खुद कभी नहीं।

  • Pre-signed URL: browser सीधे S3 पर upload करता है, ताकि आपके server को भारी file न ढोनी पड़े।

उदाहरण: library के register में किताब का rack number लिखा होता है, किताब नहीं। Pre-signed URL = guard का दिया एक बार का pass, जिससे आप सीधे godown में सामान रख आओ।

11. WebSockets

एक connection जो खुला रहता है, ताकि server खुद data push कर सके (chat, live notifications, live scores)। Normal HTTP में browser को हर बार पूछना पड़ता है।

उदाहरण: HTTP = बार-बार फ़ोन करके पूछना "पहुँचे क्या?"। WebSocket = call चालू रखना, जैसे ही पहुँचे वह खुद बता दे।

Part C: ज़रूरी ideas (follow-up सवाल)

CAP theorem (आसान भाषा में)

जब servers के बीच network टूट जाए, तो एक चुनना पड़ता है:

  • Consistency: सबको सबसे नया data दिखे (या error मिले)। Bank balance, seat booking के लिए।
  • Availability: हमेशा जवाब दो, भले data थोड़ा पुराना हो। Like counts, news feed के लिए।

उदाहरण: bank का link down है। ATM या तो पैसे देने से मना कर दे (consistency: गलत balance का खतरा नहीं) या आपका आखिरी पता balance दिखा दे (availability: जवाब हमेशा, शायद पुराना)।

🎤 "For payments I choose consistency. For a feed or a like counter, slightly old data is fine, so I choose availability."

Eventual consistency

Data हर जगह थोड़ी देर बाद एक जैसा हो जाता है। उदाहरण: आप Instagram पर post करते हो और आपके दोस्त को 2 second बाद दिखती है। यह ठीक है।

Idempotency ⭐ (payments के लिए बहुत ज़रूरी)

एक ही request दो बार भेजने पर नतीजा वही हो जो एक बार भेजने पर होता।

  • समस्या: user "Pay" दो बार दबा देता है, या network retry करता है, और पैसा दो बार कट जाता है ❌
  • इलाज: client एक idempotency key (unique ID) भेजता है। Server उसे save करता है। वही key दोबारा आए, तो दोबारा charge करने की जगह save किया हुआ result लौटा देता है।
  • साथ ही: payment gateway के callbacks (webhooks) दो बार आ सकते हैं। Update से पहले check करो कि order पहले से paid तो नहीं।

उदाहरण: lift का button 5 बार दबाओ, lift एक ही बार आती है। एक order के लिए दो बार pay दबाया, तो भी पैसा एक ही बार कटना चाहिए।

Rate limiting के तरीके

  • Fixed window: हर minute 100 requests। आसान, पर दो windows की सीमा पर burst से लगभग 200 घुस सकती हैं।
  • Sliding window: ज़्यादा smooth और सटीक।
  • Token bucket ⭐: एक बाल्टी तय speed से tokens से भरती है; हर request एक token लेती है। छोटे bursts की इजाज़त देता है। सबसे common जवाब।
  • Counters Redis में रखो ताकि सारे servers उन्हें share करें।

उदाहरण: token bucket = राशन की दुकान जिसे हर घंटे 10 tokens मिलते हैं। हर customer को एक token चाहिए। Tokens खत्म तो अगला इंतज़ार करे।

Services के पार transactions: Saga

एक order कई services को छूता है (order, payment, stock)। Payment fail हो तो एक बड़े transaction की जगह undo steps चलाओ (stock वापस करो, order cancel करो)।

उदाहरण: trip book करना: train, hotel और cab। Hotel booking fail हुई तो पहले से book train ticket cancel कर दो (undo step)।

Reliability के tools

  • बढ़ते इंतज़ार के साथ retry: 1s रुको, फिर 2s, फिर 4s… (fail हो रही service को लगातार मत ठोको)
  • Circuit breaker: कोई service बार-बार fail हो, तो थोड़ी देर उसे call करना बंद करो और backup जवाब दो। उदाहरण: घर का MCB, fault होते ही trip हो जाता है ताकि पूरा घर न जले।
  • Monitoring: logs, metrics और alerts (CloudWatch, Grafana)।

Optimistic vs pessimistic locking (booking की समस्याएँ)

  • Pessimistic: booking के दौरान row lock करो (SELECT ... FOR UPDATE)। सुरक्षित पर धीमा।
  • Optimistic: row को version number के साथ पढ़ो; update सिर्फ़ WHERE version = old_version पर। 0 rows बदलीं, मतलब किसी और ने पहले book कर लिया, error दिखाओ।

उदाहरण: pessimistic = trial room में कपड़े पहनते समय दरवाज़ा lock करना। Optimistic = आखिरी seat के लिए दो लोग form भरते हैं; जो पहले submit करे वह जीते, दूसरे को "पहले ही ले ली गई" बताया जाए।

Part D: Top HLD सवाल, छोटे जवाबों के साथ

ये outlines हैं: क्या बनाना है, और वे 1–2 मुख्य बातें जो interviewer सुनना चाहता है।

1. URL shortener (bit.ly जैसा)

  • API: POST /shorten {longUrl} → abc123; GET /abc123 → redirect (301/302)
  • Short code: auto-increment ID को base62 (a–z, A–Z, 0–9) में बदलो। 7 characters से लगभग 3.5 लाख करोड़ combinations।
  • Writes से बहुत ज़्यादा reads → popular links के लिए Redis cache।
  • मुख्य बात: बिना टकराव के unique codes कैसे बनाते हो (एक counter, या हर server को IDs की एक range)।

उदाहरण: courier का tracking number: लंबे पते की जगह छोटा code, जिससे पूरी जानकारी निकल आती है।

2. Rate limiter

  • Services से पहले बैठता है (middleware या API gateway)। Redis में token bucket, key = user ID या IP।
  • HTTP 429 लौटाओ, Retry-After header के साथ।
  • मुख्य बात: Redis में साझा counter, ताकि कई servers पर काम करे।

3. Notification system (email, SMS, push)

  • API → queue → हर channel का अलग worker → provider (SES, SMS gateway, FCM)।
  • User की पसंद की table (SMS बंद किया है?), templates, retry + DLQ, priority (OTP = high, marketing = low)।
  • मुख्य बात: queues से background में भेजो; API call के अंदर कभी मत भेजो।

उदाहरण: post office: चिट्ठियाँ छँटाई (queue) में जाती हैं, फिर speed post, साधारण डाक, courier के अलग डाकिए (workers)। ज़रूरी चिट्ठी (OTP) पहले।

4. Chat app (WhatsApp जैसा)

  • WebSocket servers connections खुले रखते हैं। Redis याद रखता है "user X server 3 से जुड़ा है"।
  • Message का रास्ता: भेजने वाला → chat server → database में save → receiver online हो तो push; नहीं तो save करके push notification।
  • Ticks: sent ✓, delivered ✓✓, read 🔵 status updates हैं।
  • मुख्य बात: messages का क्रम (हर chat का sequence number) और offline users तक पहुँचाना।

5. News feed (Instagram या LinkedIn जैसा)

  • Fan-out on write: आप post करो तो हर follower के feed cache में डाल दो। पढ़ने में तेज़। 1 करोड़ followers वाले celebrities के लिए खराब।
  • Fan-out on read: user app खोले तब feed बनाओ। पढ़ने में धीमा।
  • Mix ⭐: आम users = on write; celebrities = on read, फिर दोनों मिलाओ।

उदाहरण: on write = अख़बार वाला हर घर में अख़बार डाल आए। Celebrity = इतने घर कि बाँटना मुश्किल, तो लोग खुद stall से उठाएँ (on read)।

6. Ticket booking (BookMyShow जैसा)

  • सबसे मुश्किल हिस्सा: दो लोग एक ही seat book करें।
  • User seat चुने → उसे 5–10 मिनट के लिए hold करो (expiry वाली Redis key, या expiry time के साथ LOCKED status)।
  • Payment सफल → BOOKED। Payment fail या time out → hold खत्म → seat फिर से खाली।
  • मुख्य बात: strong consistency + locking + idempotent payment।

7. Online store checkout + payment

  • Order status: CREATED → PAYMENT_PENDING → PAID → SHIPPED (या FAILED / CANCELLED)।
  • User को payment gateway पर भेजो → webhook वापस आता है → उसका signature check करो → paid mark करो (idempotent!)।
  • एक cron job pending orders को gateway से check करता है, अगर कोई webhook खो गया हो।
  • मुख्य बात: idempotency, webhooks की जाँच, और frontend से आए "success" पर कभी भरोसा मत करो।

8. Image / file upload service

  • Browser API से pre-signed URL माँगता है → सीधे S3 पर upload → S3 event → queue → worker thumbnails या watermarks बनाता है → files CDN से दिखती हैं।
  • Database details रखता है (path, size, owner, tags)।
  • मुख्य बात: बड़ी files अपने server से मत गुज़ारो; reads के लिए CDN।

9. Search autocomplete

  • एक trie (prefix tree) जो हर node पर top 5–10 suggestions रखता है।
  • Popular searches पहले से निकाल कर रखो, आम शुरुआती अक्षरों के results cache करो, और type करने के बाद API call से पहले लगभग 300 ms रुको (debounce)।

उदाहरण: dictionary में "स" से शुरू वाले पन्ने सीधे खुल जाते हैं, पूरी किताब नहीं पलटनी पड़ती।

10. बड़े scale पर job scheduler / cron

  • एक jobs table (run_at, status); workers इसे check करते हैं या delayed queue इस्तेमाल करते हैं।
  • एक distributed lock (Redis) ताकि दो servers एक ही job न चलाएँ। Retries + ऐसे jobs जो दो बार चलें तो भी नुकसान न हो।

Part E: AI system design (AI full stack jobs में आपकी बढ़त 🔥)

11. बड़े scale पर RAG chatbot

Save करना (background में):  documents → हिस्सों में काटो → embeddings → vector database (pgvector / Pinecone)
जवाब देना (live):            सवाल → embedding → top हिस्से ढूँढो → (re-rank) → prompt + हिस्से → LLM → जवाब stream करो
  • दोहराए गए सवालों के जवाब cache करो।
  • मनगढ़ंत जवाब रोको: "सिर्फ़ context से जवाब दो, नहीं तो कहो पता नहीं"; sources दिखाओ।
  • हर customer का data अलग: हर search में tenant_id से filter, ताकि company A कभी company B के documents न देखे।
  • Save करने के लिए queue (बड़े PDFs के embeddings बनाना धीमा है)।
  • Test करो: सवाल-जवाब का एक set; नापो कि सही हिस्से मिले या नहीं और जवाब अच्छे हैं या नहीं।

उदाहरण: एक CA firm जिसके 100 clients हैं: हर client की file अलग अलमारी में, और employee को सिर्फ़ उसी client की अलमारी की चाबी मिलती है (tenant filter)।

12. LLM gateway (सारी AI calls के आगे एक service)

  • एक जगह पर: API keys, model routing (आसान काम के लिए सस्ता model, मुश्किल के लिए बड़ा), provider down हो तो backup, हर user की rate limits, tokens और cost की tracking, logs और caching।
  • मुख्य बात: खर्च पर control + भरोसेमंदी।

उदाहरण: office का reception: हर बाहरी call यहीं से होकर जाती है, यहीं register में लिखा जाता है, और ज़रूरत के हिसाब से सही विभाग में भेजा जाता है।

13. AI agent system

  • Loop: LLM तय करता है → कोई tool call करता है (API या database) → result लेता है → फिर तय करता है → final जवाब।
  • जोड़ो: step limit, timeouts, risky कामों (payments, deletes) के लिए इंसान की approval, memory (chat + database में long-term)। लंबे काम queue/worker में चलें, और user को polling या WebSocket से progress दिखे।

14. WhatsApp AI support bot

  • WhatsApp webhook → queue → worker: user की history लाओ (Redis या database) → RAG → LLM → WhatsApp API से जवाब।
  • Bot को पक्का न पता हो या user कहे "इंसान से बात करनी है", तो इंसान को सौंप दो।

🎤 "The main problems in LLM systems are speed, cost and made-up answers, so I'd add streaming, caching, model routing, RAG and regular tests."

NestJS वाला नज़रिया (आपकी ताक़त, इस्तेमाल करो!)

  • DI (dependency injection) असल में dependency inversion है: services को जो चाहिए वह constructor से मिलता है।
  • Guards = permission checks, Interceptors = Decorators जैसे (logging, response को shape देना), Pipes = input checks, Modules = features अलग रखना।

🎤 "In NestJS, my service depends on an interface token like PAYMENT_GATEWAY. Switching from BillDesk to Razorpay is just a new provider, with no change in the service. That is Strategy plus dependency inversion."

Top LLD problems (इनकी practice करो)

  1. Parking lot ⭐: fee के लिए Strategy, vehicles और spots के लिए Factory, दो गाड़ियों का एक ही spot लेना संभालो।
  2. LRU cache ⭐: HashMap + doubly linked list → get/put O(1) में। (JS में Map insert का क्रम रखता है: हर इस्तेमाल पर delete करके फिर set करो।)
  3. BookMyShow: Show, Screen, Seat, Booking; expiry वाला seat hold।
  4. Splitwise: User, Group, Expense, split के तरीके (बराबर / exact / percent), कर्ज़ simplify करना।
  5. Rate limiter class: allowRequest(userId) वाला token bucket।
  6. Elevator: State pattern, requests का क्रम।
  7. Notification service: हर channel के लिए Strategy + Observer।
  8. Expiry वाला in-memory key-value store।
  9. Vending machine (State), Snake & Ladder, Logger (Chain of Responsibility)।

छोटा code: LRU cache (JS, अक्सर live पूछा जाता है)

उदाहरण: आपके phone के "recent apps": सबसे पुराना इस्तेमाल हुआ app जगह भरने पर सबसे पहले हटता है।

class LRUCache {
  constructor(capacity) { this.capacity = capacity; this.map = new Map(); }
  get(key) {
    if (!this.map.has(key)) return -1;
    const val = this.map.get(key);
    this.map.delete(key); this.map.set(key, val); // "सबसे नया" बना दो
    return val;
  }
  put(key, val) {
    if (this.map.has(key)) this.map.delete(key);
    this.map.set(key, val);
    if (this.map.size > this.capacity) this.map.delete(this.map.keys().next().value); // सबसे पुराना
  }
}

Part G: आपकी अपनी कहानियाँ (ये 3 तैयार करो, ज़रूर पूछेंगे)

Interviewers किताबी जवाबों से ज़्यादा असली काम पर भरोसा करते हैं। वही 7 steps इस्तेमाल करो।

कहानी 1: ampleimages.com (India TV)

  • Next.js frontend + Node/Express APIs + MySQL (users, orders, payments) + DynamoDB (बड़ा data) + Redis (cache, sessions) + लगभग 15,000 images के लिए CDN।
  • BillDesk से payment: order बना → redirect → callback → check → download unlock। Idempotency और server पर callback की जाँच ज़रूर बताओ।
  • OpenSearch से search, API rate limiting, JWT login + role-based admin access, database indexes।
  • Emails, order receipts और image watermarking के लिए AWS Lambda (धीमे काम main API से बाहर)।
  • Admin panel: S3 upload के साथ images जोड़ना/बदलना, categories, order history, error codes के साथ payment history।
  • इसके लिए तैयार रहो: "How do you stop someone downloading without paying?" → CDN पर watermark वाले previews; original file private storage में रहती है और payment के बाद ही कम समय में expire होने वाले signed URL से मिलती है।

कहानी 2: Multi-level approval system (general रखो)

  • Roles → कई approval steps (submit → review → approve / send back / reject), status state machine, audit logs (किसने क्या कब बदला), role-based access, read replica से reports, तेज़ dashboards के लिए cron से बनी summary tables।
  • ⚠️ Client का नाम या अंदर की details मत बताओ। ज़्यादा से ज़्यादा "a large training platform" बोलो।

कहानी 3: RAG chatbot (आपका अपना project)

  • Local embeddings + Neon पर pgvector + streaming के साथ Claude API। Chunking, top हिस्से ढूँढना, और "सिर्फ़ context से जवाब" क्यों, यह समझाओ।
