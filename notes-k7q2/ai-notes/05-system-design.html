Level 5: System Design (HLD + LLD) for Interviews

For 8 years of experience, this round decides "senior hai ya nahi". You don't need fancy words. You need to explain clearly, think about scale, and talk about trade-offs.

One-line summary

HLD = draw the big picture (which services, DB, cache, queue and how they talk) → LLD = design the classes and code inside one part (clean, SOLID, patterns) → in both, always say why you chose something and what breaks at scale.

Part A: The HLD answer framework (use this every time)

Never jump straight to the diagram. Follow these 7 steps, out loud:

Step What you say Time
1. Requirements "What must it do? (functional) How fast / how many users / how reliable? (non-functional)" 3–5 min
2. Estimates Users per day → requests per second → storage 3 min
3. APIs 3–5 main endpoints 3 min
4. Data model Main tables and which DB 5 min
5. Diagram Client → Load Balancer → Services → Cache / DB / Queue 10 min
6. Deep dive Pick the 1–2 hardest parts and go deep 15 min
7. Trade-offs "If this fails, what happens? What would I change at 10x scale?" 5 min

🎤 "Before designing, let me confirm the requirements and the scale, because the design changes a lot between 1,000 users and 10 million." (Interviewers love this first line.)

Quick estimate math (memorise)

  • 1 day ≈ 1 lakh seconds (86,400, round up to 100,000)
  • 10 lakh (1M) requests/day ≈ ~12 requests/sec. Peak = 2–3x average.
  • 1 crore (10M) requests/day ≈ ~120 requests/sec
  • 1 image ≈ 200 KB–1 MB. 1 text row ≈ 1 KB.
  • Reads are usually 10–100x more than writes → cache helps a lot.

Part B: Building blocks (the "Lego pieces")

Every HLD is made of these pieces. Know what each does + when to use it.

1. Load Balancer

Sends incoming traffic to many servers so no single server is overloaded.

  • Analogy: the token counter in a hospital that sends patients to whichever doctor is free.
  • Keep servers stateless (no user session stored on the server, keep it in Redis/JWT) so any server can handle any request.

2. Scaling

  • Vertical = bigger machine (more RAM/CPU). Easy, but has a limit and is a single point of failure.
  • Horizontal = more machines behind a load balancer. This is how real systems scale.

3. Database: SQL vs NoSQL

Use SQL (Postgres/MySQL) when Use NoSQL (DynamoDB/Mongo) when
Data has relations (users, orders, payments) Huge scale, simple lookups by key
You need transactions (money!) Flexible / changing structure
Complex queries, reports Very high write speed

🎤 "Payments and orders go in SQL because I need ACID transactions. High-volume, key-based data like sessions or download logs can go in NoSQL." (You actually did this in ampleimages: MySQL + DynamoDB.)

4. Indexing

Like the index at the back of a book. Makes reads fast, makes writes slightly slower. Index the columns you filter / join / sort on.

5. Replication (copies)

  • Primary handles writes, read replicas handle reads.
  • Good for read-heavy apps. Small delay before replicas get new data (replication lag).

6. Sharding (splitting)

When one DB is too big, split data across many DBs, e.g. users A–M on DB1, N–Z on DB2, or by user_id % 4.

  • Pick a shard key that spreads data evenly. Bad key = one shard gets all the load ("hot shard").
  • Cross-shard joins are hard → avoid them.

7. Cache (Redis)

Keep frequently read data in memory → super fast.

  • Cache-aside (most common): app checks cache → miss → read DB → put in cache with TTL.
  • Problem: cache invalidation. When data changes, delete/update the cache key.
  • Cache stampede: many requests miss at once and hit DB → use a lock or stagger TTLs.

🎤 "I'd use cache-aside with Redis and a TTL, and delete the key on update so users don't see stale data."

8. CDN

Copies static files (images, JS, CSS, videos) to servers near the user. A Delhi user gets images from a Delhi server, not from the US.

  • You used this in ampleimages for 15k images ✅

9. Message Queue (Kafka / SQS / RabbitMQ)

Do slow work in the background. The API replies fast; a worker processes later.

  • Analogy: restaurant order slip: the waiter takes the order and goes, the kitchen cooks at its own speed.
  • Use for: emails, notifications, image resizing, reports, AI processing.
  • Retry failed jobs; after N failures move to a Dead Letter Queue (DLQ) to inspect.

10. Object Storage (S3)

For files. DB stores only the file path/URL, never the file itself.

  • Pre-signed URL: the browser uploads directly to S3, so your server doesn't carry the heavy file.

11. WebSockets

A connection that stays open so the server can push data (chat, live notifications, live scores). Normal HTTP = the client must ask every time.

Part C: Important concepts (follow-up questions)

CAP theorem (simple)

When the network between servers breaks (Partition), you must choose:

  • Consistency: everyone sees the latest data (or gets an error), e.g. bank balance, seat booking.
  • Availability: always respond, even if the data is slightly old, e.g. likes count, news feed.

🎤 "For payments I choose consistency. For a feed or like counter, availability with eventual consistency is fine."

Eventual consistency

Data will become the same everywhere after a short time. Example: you post on Instagram, your friend sees it 2 seconds later. Fine.

Idempotency ⭐ (very important for payments)

Doing the same request twice gives the same result as doing it once.

  • Problem: the user clicks "Pay" twice, or the network retries → money is deducted twice ❌
  • Fix: the client sends an idempotency key (unique id). The server saves it; if the same key comes again, it returns the old result instead of charging again.
  • Also: payment gateway callbacks (BillDesk webhook) can arrive twice → check whether the order is already marked paid before updating.

Rate limiting algorithms

  • Fixed window: 100 requests per minute. Simple, but a burst at the window edge can let in ~200 requests.
  • Sliding window: smoother, more accurate.
  • Token bucket ⭐: a bucket refills tokens at a fixed speed; each request uses one token. Allows small bursts. Most common answer.
  • Store counters in Redis so all servers share them.

Distributed transactions: Saga

An order touches many services (order, payment, inventory). If payment fails, run compensating actions ("undo": release the stock, cancel the order) instead of one big transaction.

Reliability tools

  • Retry with exponential backoff: wait 1s, 2s, 4s… (don't hammer a failing service)
  • Circuit breaker: if a service keeps failing, stop calling it for a while and return a fallback.
  • Monitoring: logs, metrics, alerts (CloudWatch / Grafana).

Optimistic vs pessimistic locking (booking problems)

  • Pessimistic: lock the row while booking (SELECT ... FOR UPDATE). Safe, slower.
  • Optimistic: read with a version; update only WHERE version = old_version. If 0 rows updated → someone else booked first → show an error.

Part D: Top HLD questions with short answers

These are skeletons: what to draw + the 1–2 key points the interviewer is waiting for.

1. URL Shortener (bit.ly)

  • API: POST /shorten {longUrl} → abc123; GET /abc123 → redirect (301/302)
  • Short code: auto-increment id → base62 (a–z, A–Z, 0–9). 7 chars ≈ 3.5 lakh crore combinations.
  • Reads >> writes → Redis cache for popular links.
  • Key point: how you generate unique codes without collision (counter / pre-generated key range per server).

2. Rate Limiter

  • Middleware/API gateway before the services. Token bucket in Redis, key = userId or IP.
  • Return HTTP 429 with a Retry-After header.
  • Key point: shared counter in Redis so it works across many servers.

3. Notification System (Email / SMS / Push)

  • API → queue → separate workers per channel → provider (SES, SMS gateway, FCM).
  • User preferences table (opted out of SMS?), templates, retry + DLQ, priority queue (OTP = high priority, marketing = low).
  • Key point: async with queues; never send directly inside the API call.

4. Chat app (WhatsApp)

  • WebSocket servers keep connections open; Redis tracks "user X is connected to server 3".
  • Message flow: sender → chat server → save in DB → push to receiver if online, else store + push notification.
  • Delivery ticks: sent ✓, delivered ✓✓, read 🔵 = status updates.
  • Key point: message ordering (sequence number per chat) and offline delivery.

5. News Feed (Instagram / LinkedIn)

  • Fan-out on write: when you post, push it into every follower's feed cache. Reads are fast. Bad for celebrities with 1 crore followers.
  • Fan-out on read: build the feed when the user opens the app. Slow reads.
  • Hybrid ⭐: normal users = on write; celebrities = on read and merge.

6. Ticket Booking (BookMyShow)

  • Hardest part: two people booking the same seat.
  • When a user selects a seat → temporary lock for 5–10 min (Redis key with TTL, or DB status LOCKED with expiry).
  • Payment success → BOOKED. Payment fails / timeout → lock expires → seat free again.
  • Key point: strong consistency + locking + idempotent payment.

7. E-commerce checkout + payment

  • Order states: CREATED → PAYMENT_PENDING → PAID → SHIPPED (or FAILED / CANCELLED).
  • Payment gateway redirect → webhook callback → verify signature → mark paid (idempotent!).
  • Reconciliation cron: check pending orders against the gateway status in case the webhook was lost.
  • Key point: idempotency, webhook verification, never trust the frontend's "success".

8. Image / File upload service

  • Browser asks API for a pre-signed URL → uploads directly to S3 → S3 event → queue → worker makes thumbnails/watermark → served via CDN.
  • DB stores metadata (path, size, owner, tags).
  • Key point: don't stream big files through your server; use CDN for reads.

9. Search Autocomplete

  • Trie (prefix tree) with top 5–10 suggestions stored at each node.
  • Precompute popular queries offline; cache results for common prefixes; debounce on the frontend (wait ~300 ms after typing).

10. Job scheduler / cron at scale

  • Jobs table (run_at, status), workers poll or use a delayed queue.
  • Distributed lock (Redis) so 2 servers don't run the same job. Retries + idempotent jobs.

Part E: AI system design (your edge for AI Full Stack roles 🔥)

11. RAG chatbot at scale

Ingestion (offline):  docs → chunk → embed → vector DB (pgvector / Pinecone)
Query (online):       question → embed → top-K search → (rerank) → prompt + chunks → LLM → stream answer
  • Cache answers for repeated questions (exact or semantic cache).
  • Hallucination control: "answer only from the context, else say you don't know"; show sources.
  • Per-tenant data: filter by tenant_id in vector search so client A never sees client B's docs.
  • Ingestion via queue (embedding big PDFs is slow).
  • Evaluate: a test set of Q&A, measure retrieval hit rate and answer quality.

12. LLM Gateway (one service in front of all AI calls)

  • One place for: API keys, model routing (cheap model for easy tasks, big model for hard), fallback if a provider is down, rate limits per user, token/cost tracking, logging, caching.
  • Key point: cost control + reliability.

13. AI Agent system

  • Loop: LLM decides → calls a tool (API/DB) → gets the result → decides again → final answer.
  • Add: max steps limit, timeouts, human approval for risky actions (payments, deletes), memory (conversation + long-term in DB), long tasks run in a queue/worker with status polling or WebSocket updates.

14. WhatsApp AI support bot

  • WhatsApp webhook → queue → worker: load user history (Redis/DB) → RAG → LLM → reply via WhatsApp API.
  • Handover to a human when confidence is low or the user says "talk to a person".

🎤 "Main challenges in LLM systems are latency, cost and hallucinations, so I'd add streaming, caching, model routing and grounding with RAG plus evaluation."

Part F: LLD (Low Level Design)

What they check

  1. Can you find the right classes / entities from a problem?
  2. Clean code: SOLID, design patterns, no giant if-else.
  3. Handles edge cases + concurrency.
  4. (Machine coding round) working code in 60–90 min.

LLD answer steps

  1. Clarify requirements (what's in scope).
  2. List entities (nouns → classes): ParkingLot, Floor, Spot, Vehicle, Ticket.
  3. Relationships (has-a / is-a).
  4. Key methods (verbs): park(), unpark(), calculateFee().
  5. Apply patterns where they fit naturally.
  6. Write the code for the core flow first, then extras.

SOLID in simple words

Letter Meaning Simple example
S Single Responsibility One class = one job InvoiceService doesn't also send emails
O Open/Closed Add new features without editing old code New payment method = new class, not a new if
L Liskov Substitution A child class must work wherever the parent works Bike extends Vehicle shouldn't break park()
I Interface Segregation Small, focused interfaces Don't force Printer to implement fax()
D Dependency Inversion Depend on interfaces, not concrete classes Service gets PaymentGateway injected (NestJS DI!)

Design patterns (most asked)

Pattern One line Example
Strategy ⭐ Swap algorithms at runtime Fee: hourly vs daily; Notification: Email/SMS/Push
Factory One place creates the right object VehicleFactory.create('car')
Observer Notify subscribers when something changes Seat freed → notify waiting users; event emitters
Singleton Only one instance DB connection pool, config, logger
Decorator Add behaviour without changing the class Add logging/caching around a service; NestJS decorators
Adapter Make an incompatible interface fit Wrap BillDesk & Razorpay behind one PaymentGateway
State Behaviour changes by state Order: Created → Paid → Shipped; approval workflows
Builder Build complex objects step by step Query builders, report builders

NestJS angle (your strength, use it!)

  • DI = Dependency Inversion in action: services get dependencies through the constructor.
  • Guards = authorization, Interceptors = Decorator-like (logging, response mapping), Pipes = validation, Modules = separation of concerns.

🎤 "In NestJS, I depend on an interface token like PAYMENT_GATEWAY, so switching from BillDesk to Razorpay is just a new provider, with no change in the service. That's Strategy plus Dependency Inversion."

Top LLD problems (practice these)

  1. Parking Lot ⭐: Strategy for fee, Factory for vehicle/spot, handle concurrent parking.
  2. LRU Cache ⭐: HashMap + doubly linked list → get/put in O(1). (In JS, a Map keeps insertion order: delete + re-set on access.)
  3. BookMyShow: Show, Screen, Seat, Booking; seat lock with expiry.
  4. Splitwise: User, Group, Expense, split strategies (equal / exact / percent), simplify debts.
  5. Rate Limiter class: token bucket with allowRequest(userId).
  6. Elevator: State pattern, request scheduling.
  7. Notification service: Strategy per channel + Observer.
  8. In-memory key-value store with TTL.
  9. Vending machine (State), Snake & Ladder, Logger (Chain of Responsibility).

Mini code: LRU cache (JS, often asked live)

class LRUCache {
  constructor(capacity) { this.capacity = capacity; this.map = new Map(); }
  get(key) {
    if (!this.map.has(key)) return -1;
    const val = this.map.get(key);
    this.map.delete(key); this.map.set(key, val); // move to "most recent"
    return val;
  }
  put(key, val) {
    if (this.map.has(key)) this.map.delete(key);
    this.map.set(key, val);
    if (this.map.size > this.capacity) this.map.delete(this.map.keys().next().value); // oldest
  }
}
