Level 5: System Design (HLD + LLD) for Interviews

With 8 years of experience, this round decides if you are seen as senior. You don't need fancy words. You need to explain clearly, think about scale, and talk about trade-offs (what you gain and what you lose with each choice).

In one line

HLD (high-level design) = draw the big picture: which services, database, cache and queue, and how they talk → LLD (low-level design) = design the classes and code inside one part (clean code, SOLID, patterns) → in both, always say why you chose something and what breaks when the system grows.

Part A: How to answer an HLD question (use this every time)

Don't jump straight to the diagram. Follow these 7 steps, out loud:

Step What you say Time
1. Requirements "What must it do? How fast, how many users, how reliable?" 3–5 min
2. Estimates Users per day → requests per second → storage 3 min
3. APIs The 3–5 main endpoints 3 min
4. Data model Main tables, and which database 5 min
5. Diagram Client → Load balancer → Services → Cache / Database / Queue 10 min
6. Deep dive Pick the 1–2 hardest parts and explain them in detail 15 min
7. Trade-offs "If this part fails, what happens? What would I change at 10 times the users?" 5 min

🎤 "Before I design, let me confirm what the system must do and how big it is, because the design is very different for 1,000 users and 10 million users." (Interviewers like this first line.)

Quick estimate maths (remember these)

  • 1 day ≈ 1 lakh seconds (86,400, round it to 100,000)
  • 10 lakh (1 million) requests a day ≈ 12 requests a second. Peak = 2–3 times the average.
  • 1 crore (10 million) requests a day ≈ 120 requests a second
  • 1 image ≈ 200 KB to 1 MB. 1 text row ≈ 1 KB.
  • Reads are usually 10 to 100 times more than writes, so a cache helps a lot.

Part B: Building blocks

Every HLD is made of these parts. Know what each one does and when to use it.

1. Load balancer

Spreads incoming traffic over many servers so no single server is overloaded.

  • Example: the token counter in a hospital that sends each patient to whichever doctor is free.
  • Keep servers stateless (don't keep user sessions on the server; keep them in Redis or a JWT), so any server can handle any request.

2. Scaling

  • Vertical = a bigger machine (more RAM and CPU). Easy, but it has a limit, and if it fails everything fails.
  • Horizontal = more machines behind a load balancer. This is how real systems grow.

3. Database: SQL vs NoSQL

Use SQL (Postgres, MySQL) when Use NoSQL (DynamoDB, Mongo) when
Data is linked (users, orders, payments) Very large scale, simple lookups by key
You need transactions (money!) The structure changes often
You need complex queries and reports You need very fast writes

🎤 "Payments and orders go in SQL because I need safe transactions. Large, simple data like sessions or download logs can go in NoSQL." (You did this on ampleimages: MySQL + DynamoDB.)

4. Indexing

Like the index at the back of a book. Makes reads fast, makes writes a little slower. Add indexes on the columns you filter, join or sort on.

5. Replication (copies)

  • The primary database takes writes. Read replicas (copies) take reads.
  • Good for apps with many reads. Copies get new data after a small delay (replication lag).

6. Sharding (splitting)

When one database is too big, split the data over many databases. For example users A–M in database 1 and N–Z in database 2, or by user_id % 4.

  • Choose a shard key that spreads data evenly. A bad key puts all the load on one database (a "hot shard").
  • Joins across shards are hard, so avoid them.

7. Cache (Redis)

Keep often-read data in memory, so reads are very fast.

  • Cache-aside (most common): the app checks the cache → if it's not there, read the database → save it in the cache with a TTL (expiry time).
  • Problem: when data changes, the cache can show old data. Delete or update the cache key on every change.
  • Cache stampede: many requests miss the cache at the same time and all hit the database. Fix it with a lock or different expiry times.

🎤 "I'd use cache-aside with Redis and a TTL, and delete the key on update so users don't see old data."

8. CDN

Keeps copies of static files (images, JS, CSS, videos) on servers near the user. A Delhi user gets images from a server in Delhi, not from the US.

  • You used this on ampleimages for 15,000 images ✅

9. Message queue (Kafka, SQS, RabbitMQ)

Do slow work in the background. The API replies fast; a worker does the job later.

  • Example: a restaurant order slip. The waiter takes the order and leaves; the kitchen cooks at its own speed.
  • Use it for emails, notifications, image resizing, reports and AI work.
  • Retry failed jobs. After a few failures, move the job to a dead letter queue (DLQ) so you can check it.

10. Object storage (S3)

For files. The database stores only the file path or URL, never the file itself.

  • Pre-signed URL: the browser uploads straight to S3, so your server does not carry the heavy file.

11. WebSockets

A connection that stays open, so the server can push data (chat, live notifications, live scores). With normal HTTP, the browser has to ask every time.

Part C: Important ideas (follow-up questions)

CAP theorem (simple)

When the network between servers breaks, you must choose one:

  • Consistency: everyone sees the latest data (or gets an error). Use for bank balance, seat booking.
  • Availability: always reply, even if the data is a little old. Use for like counts, news feed.

🎤 "For payments I choose consistency. For a feed or a like counter, slightly old data is fine, so I choose availability."

Eventual consistency

The data becomes the same everywhere after a short time. Example: you post on Instagram and your friend sees it 2 seconds later. That is fine.

Idempotency ⭐ (very important for payments)

Sending the same request twice gives the same result as sending it once.

  • Problem: the user clicks "Pay" twice, or the network retries, and money is taken twice ❌
  • Fix: the client sends an idempotency key (a unique ID). The server saves it. If the same key comes again, it returns the saved result instead of charging again.
  • Also: payment gateway callbacks (webhooks) can arrive twice. Check if the order is already paid before updating it.

Rate limiting methods

  • Fixed window: 100 requests per minute. Simple, but a burst at the edge of two windows can let in about 200.
  • Sliding window: smoother and more exact.
  • Token bucket ⭐: a bucket fills with tokens at a fixed speed; each request uses one token. Allows small bursts. The most common answer.
  • Keep the counters in Redis so all servers share them.

Transactions across services: Saga

One order touches many services (order, payment, stock). If payment fails, run undo steps (give back the stock, cancel the order) instead of one big transaction.

Reliability tools

  • Retry with growing wait: wait 1s, then 2s, then 4s… (don't keep hitting a failing service)
  • Circuit breaker: if a service keeps failing, stop calling it for a while and return a backup answer.
  • Monitoring: logs, metrics and alerts (CloudWatch, Grafana).

Optimistic vs pessimistic locking (booking problems)

  • Pessimistic: lock the row while booking (SELECT ... FOR UPDATE). Safe but slower.
  • Optimistic: read the row with a version number; update only WHERE version = old_version. If 0 rows change, someone else booked first, so show an error.

Part D: Top HLD questions with short answers

These are outlines: what to draw, plus the 1–2 key points the interviewer wants to hear.

1. URL shortener (like bit.ly)

  • API: POST /shorten {longUrl} → abc123; GET /abc123 → redirect (301/302)
  • Short code: an auto-increment ID turned into base62 (a–z, A–Z, 0–9). 7 characters give about 3.5 lakh crore combinations.
  • Many more reads than writes → Redis cache for popular links.
  • Key point: how you make unique codes without clashes (a counter, or a range of IDs given to each server).

2. Rate limiter

  • Sits before the services (middleware or API gateway). Token bucket in Redis, with the key = user ID or IP.
  • Return HTTP 429 with a Retry-After header.
  • Key point: a shared counter in Redis, so it works across many servers.

3. Notification system (email, SMS, push)

  • API → queue → a separate worker for each channel → provider (SES, SMS gateway, FCM).
  • Table of user choices (did they turn off SMS?), templates, retry + DLQ, priority (OTP = high, marketing = low).
  • Key point: send in the background with queues; never send inside the API call.

4. Chat app (like WhatsApp)

  • WebSocket servers keep connections open. Redis remembers "user X is connected to server 3".
  • Message flow: sender → chat server → save in database → push to receiver if online; if not, save it and send a push notification.
  • Ticks: sent ✓, delivered ✓✓, read 🔵 are status updates.
  • Key point: message order (a sequence number per chat) and delivery to offline users.

5. News feed (like Instagram or LinkedIn)

  • Fan-out on write: when you post, add it to every follower's feed cache. Fast to read. Bad for celebrities with 1 crore followers.
  • Fan-out on read: build the feed when the user opens the app. Slow to read.
  • Mix ⭐: normal users = on write; celebrities = on read, then merge.

6. Ticket booking (like BookMyShow)

  • Hardest part: two people booking the same seat.
  • When a user picks a seat → hold it for 5–10 minutes (a Redis key with expiry, or a LOCKED status with an expiry time).
  • Payment works → BOOKED. Payment fails or times out → the hold ends → the seat is free again.
  • Key point: strong consistency + locking + idempotent payment.

7. Online store checkout + payment

  • Order status: CREATED → PAYMENT_PENDING → PAID → SHIPPED (or FAILED / CANCELLED).
  • Send the user to the payment gateway → webhook comes back → check its signature → mark it paid (idempotent!).
  • A cron job checks pending orders with the gateway, in case a webhook was lost.
  • Key point: idempotency, checking webhooks, and never trusting a "success" message from the frontend.

8. Image / file upload service

  • Browser asks the API for a pre-signed URL → uploads straight to S3 → S3 event → queue → worker makes thumbnails or watermarks → files served through a CDN.
  • The database keeps details (path, size, owner, tags).
  • Key point: don't send big files through your server; use a CDN for reads.

9. Search autocomplete

  • A trie (prefix tree) that keeps the top 5–10 suggestions at each node.
  • Work out popular searches in advance, cache results for common starting letters, and wait about 300 ms after typing before calling the API (debounce).

10. Job scheduler / cron at scale

  • A jobs table (run_at, status); workers check it or use a delayed queue.
  • A distributed lock (Redis) so two servers don't run the same job. Retries + jobs that are safe to run twice.

Part E: AI system design (your edge for AI full stack jobs 🔥)

11. RAG chatbot at scale

Saving (in the background):  documents → cut into pieces → embeddings → vector database (pgvector / Pinecone)
Answering (live):            question → embedding → find top pieces → (re-rank) → prompt + pieces → LLM → stream the answer
  • Cache answers to repeated questions.
  • Stop made-up answers: "answer only from the context, otherwise say you don't know"; show the sources.
  • Separate data per customer: filter by tenant_id in every search, so company A never sees company B's documents.
  • Use a queue for saving (making embeddings for big PDFs is slow).
  • Test it: a set of questions and answers; measure if the right pieces were found and if the answers are good.

12. LLM gateway (one service in front of all AI calls)

  • One place for: API keys, model routing (cheap model for easy tasks, big model for hard ones), backup if a provider is down, rate limits per user, token and cost tracking, logs and caching.
  • Key point: cost control + reliability.

13. AI agent system

  • Loop: the LLM decides → calls a tool (API or database) → gets the result → decides again → final answer.
  • Add: a step limit, timeouts, human approval for risky actions (payments, deletes), memory (chat + long-term in the database). Long tasks run in a queue/worker, and the user sees progress by polling or WebSocket.

14. WhatsApp AI support bot

  • WhatsApp webhook → queue → worker: load the user's history (Redis or database) → RAG → LLM → reply through the WhatsApp API.
  • Hand over to a human when the bot is unsure or the user says "talk to a person".

🎤 "The main problems in LLM systems are speed, cost and made-up answers, so I'd add streaming, caching, model routing, RAG and regular tests."

Part F: LLD (Low-Level Design)

What they check

  1. Can you find the right classes from a problem?
  2. Clean code: SOLID, design patterns, no giant if-else.
  3. Edge cases and two users doing the same thing at the same time.
  4. (Machine coding round) working code in 60–90 minutes.

LLD answer steps

  1. Ask what is in scope.
  2. List the things (nouns become classes): ParkingLot, Floor, Spot, Vehicle, Ticket.
  3. How they are linked (has-a / is-a).
  4. Main methods (verbs): park(), unpark(), calculateFee().
  5. Use patterns where they fit naturally.
  6. Write code for the main flow first, then the extras.

SOLID in simple words

Letter Meaning Simple example
S Single responsibility One class = one job InvoiceService does not also send emails
O Open/closed Add new features without changing old code A new payment method = a new class, not a new if
L Liskov substitution A child class must work wherever the parent works Bike extends Vehicle must not break park()
I Interface segregation Small, focused interfaces Don't force a Printer to have fax()
D Dependency inversion Depend on interfaces, not on exact classes A service gets a PaymentGateway injected (NestJS DI!)

Design patterns (most asked)

Pattern In one line Example
Strategy ⭐ Swap the method at runtime Fee: hourly vs daily; Notification: email / SMS / push
Factory One place creates the right object VehicleFactory.create('car')
Observer Tell subscribers when something changes Seat freed → tell waiting users; event emitters
Singleton Only one object of the class Database pool, config, logger
Decorator Add behaviour without changing the class Add logging or caching around a service; NestJS decorators
Adapter Make a different interface fit Put BillDesk and Razorpay behind one PaymentGateway
State Behaviour changes with the state Order: Created → Paid → Shipped; approval workflows
Builder Build a complex object step by step Query builders, report builders

NestJS angle (your strength, use it!)

  • DI (dependency injection) is dependency inversion in action: services get what they need through the constructor.
  • Guards = permission checks, Interceptors = like Decorators (logging, shaping the response), Pipes = input checks, Modules = keep features separate.

🎤 "In NestJS, my service depends on an interface token like PAYMENT_GATEWAY. Switching from BillDesk to Razorpay is just a new provider, with no change in the service. That is Strategy plus dependency inversion."

Top LLD problems (practise these)

  1. Parking lot ⭐: Strategy for the fee, Factory for vehicles and spots, handle two cars taking the same spot.
  2. LRU cache ⭐: HashMap + doubly linked list → get/put in O(1). (In JS, a Map keeps insert order: delete and set again on each use.)
  3. BookMyShow: Show, Screen, Seat, Booking; seat hold with expiry.
  4. Splitwise: User, Group, Expense, split types (equal / exact / percent), simplify debts.
  5. Rate limiter class: token bucket with allowRequest(userId).
  6. Elevator: State pattern, request order.
  7. Notification service: Strategy per channel + Observer.
  8. In-memory key-value store with expiry.
  9. Vending machine (State), Snake & Ladder, Logger (Chain of Responsibility).

Mini code: LRU cache (JS, often asked live)

class LRUCache {
  constructor(capacity) { this.capacity = capacity; this.map = new Map(); }
  get(key) {
    if (!this.map.has(key)) return -1;
    const val = this.map.get(key);
    this.map.delete(key); this.map.set(key, val); // move to "most recent"
    return val;
  }
  put(key, val) {
    if (this.map.has(key)) this.map.delete(key);
    this.map.set(key, val);
    if (this.map.size > this.capacity) this.map.delete(this.map.keys().next().value); // oldest
  }
}
