Level 2: Embeddings, Vector Database and RAG ⭐

The problem

An LLM does not know your data: your clinic's fees, your company's PDFs, your database. If you ask, it will guess (hallucinate). RAG fixes this. It first finds the right information, then gives it to the AI along with the question.

In one line

Turn text into numbers (embeddings) → save them in a vector database → when a question comes, find the closest pieces (semantic search) → give those pieces + the question to the LLM → it answers from your data. This whole flow is RAG.

1. Embedding

Turning text into a list of numbers that holds its meaning.

"What are the clinic fees?"        → [0.12, -0.53, 0.88, ...]
"How much is the consultation?"    → [0.11, -0.50, 0.85, ...]  ← very close numbers
"How is the weather today?"        → [-0.70, 0.31, -0.10, ...] ← very different numbers
  • Same meaning = numbers close together, even when the words are different (even in another language).
  • You make embeddings by calling an embedding model API.

Example: like a map location for meaning. "Fees" and "charges" live in the same area. "Weather" lives in another city.

🎤 "An embedding is a list of numbers that stands for the meaning of a text. Texts with similar meaning get numbers that are close together."

2. Vector database

A database made to store embeddings and quickly find the closest ones.

  • Examples: pgvector (an add-on for PostgreSQL, which you already know), Pinecone, Qdrant, Weaviate, Chroma.
  • Normal SQL: WHERE name = 'fees' (exact match).
  • Vector database: "find the 5 rows whose meaning is closest to this question".

Example: a normal database is a phone book (search by exact name). A vector database is a good shopkeeper: you say "something for a headache" and he hands you the right medicine even though you never said its name.

🎤 "A vector database stores embeddings and can quickly find the ones closest to a question."

3. Keyword search vs semantic search

Keyword search Semantic search
Matches the exact words Matches the meaning
"fees" ≠ "charges" "fees" ≈ "charges" ≈ "how much will it cost"
SQL LIKE, Elasticsearch Embeddings + vector database

Closeness is usually measured with cosine similarity: 1 = same meaning, 0 = not related.

Note: our Kodivo demo bot uses keyword matching. The real version will use semantic search, so it will understand any way of asking.

4. Chunking

Cutting big documents into small pieces before making embeddings.

  • Why: one embedding for a 50-page PDF is too vague, and the whole PDF will not fit well in the prompt.
  • Usual size: a few hundred tokens per piece, with a small overlap so sentences are not cut in half.
  • Better cutting (by heading, section or FAQ) gives better answers.

Example: you don't give someone a whole book. You give them the right page.

5. RAG (Retrieval-Augmented Generation) ⭐⭐

Find the right information → add it to the prompt → write the answer.

Two parts

A) Saving the data (once, or when the data changes)

Clinic PDF / FAQs / database rows
   → cut into pieces
   → make an embedding for each piece
   → save (piece text + embedding) in the vector database

B) Answering (for every question)

User: "Is the clinic open on Sunday?"
   → make an embedding of the question
   → vector database: find the 3 closest pieces
        → "Sunday: 10 AM – 1 PM"
   → prompt to the LLM:
        System: Answer ONLY from the context. If it is not there, say you will confirm.
        Context: <the 3 pieces>
        Question: Is the clinic open on Sunday?
   → LLM: "Yes, the clinic is open on Sunday from 10 AM to 1 PM. 🙂"

Why RAG (and not a huge prompt or fine-tuning)?

  • ✅ Answers come from your real data, so far fewer hallucinations
  • ✅ Update the data any time: just save it again, no retraining
  • ✅ Cheaper: you send only the useful pieces, not everything
  • ✅ You can show the source ("from: fee-list.pdf")

Example: an open-book exam. The student first finds the right page (retrieval), then writes the answer from it (generation), and can point to the page number (source).

🎤 "RAG finds the right pieces of my documents using embeddings, adds them to the prompt, and the LLM answers only from them. This cuts hallucination and keeps answers up to date without retraining."

6. RAG vs fine-tuning (very common question)

RAG Fine-tuning
What it does Gives the model facts at question time Changes how the model behaves or writes by training it
Data changes often? ✅ Just save it again ❌ Train again every time
Cost Low Higher
Best for FAQs, documents, company data Fixed tone, fixed format, special tasks

Easy rule: facts → RAG; style → fine-tuning. Most business apps need RAG.

Example: RAG = giving a new receptionist the latest price list every morning. Fine-tuning = sending them on a months-long training course to change how they talk.

7. RAG with tools you already use

RAG part Your world
Vector database PostgreSQL + pgvector
Saving job A NestJS cron or queue job that makes embeddings for new rows or files
Finding pieces A SQL query: ORDER BY embedding <=> $questionEmbedding LIMIT 5
Writing the answer One API call to the LLM with the pieces + the question

You can build RAG with tools you already use. Say this in interviews.

Interview questions (answer out loud)

  1. What is an embedding? Give an example.
  2. How is semantic search different from keyword search?
  3. Explain the full RAG flow (saving + answering).
  4. Why do we cut documents into pieces? What if the pieces are too big or too small?
  5. RAG vs fine-tuning: when do you use each?
  6. How does RAG reduce hallucination? Can it stop it fully? (→ No. Also tell the model to answer only from the context, show sources, and test with an eval set.)
  7. Which vector database would you pick and why? (→ pgvector if you already use PostgreSQL: one less system to run.)

Quiz

  1. A clinic changes its fees every month. RAG or fine-tuning? Why?
  2. A user asks "how much will it cost?" but the document says "Consultation fee: ₹400". Will keyword search find it? Will semantic search?
  3. Which two things are saved for each piece in the vector database?

Level 2: Embeddings, Vector Database और RAG ⭐

समस्या

LLM को आपका data नहीं पता: आपके clinic की fees, आपकी company के PDFs, आपका database। पूछोगे तो अंदाज़ा लगाएगा (hallucinate करेगा)। RAG इसका इलाज है। यह पहले सही जानकारी ढूँढता है, फिर सवाल के साथ AI को देता है।

एक line में

Text को numbers में बदलो (embeddings) → उन्हें vector database में रखो → सवाल आए तो सबसे करीबी हिस्से ढूँढो (semantic search) → वे हिस्से + सवाल LLM को दो → वह आपके data से जवाब देता है। यह पूरा flow RAG है।

1. Embedding

Text को numbers की list में बदलना, जिसमें उसका मतलब छिपा हो।

"What are the clinic fees?"        → [0.12, -0.53, 0.88, ...]
"How much is the consultation?"    → [0.11, -0.50, 0.85, ...]  ← बहुत करीबी numbers
"How is the weather today?"        → [-0.70, 0.31, -0.10, ...] ← बिल्कुल अलग numbers
  • एक जैसा मतलब = करीबी numbers, चाहे शब्द अलग हों (दूसरी भाषा में भी)।
  • Embeddings एक embedding model की API call करके बनते हैं।

उदाहरण: मतलब का map location। "Fees" और "charges" एक ही मोहल्ले में रहते हैं। "Weather" किसी दूसरे शहर में।

🎤 "An embedding is a list of numbers that stands for the meaning of a text. Texts with similar meaning get numbers that are close together."

2. Vector database

Embeddings रखने और सबसे करीबी embeddings जल्दी ढूँढने के लिए बना database।

  • उदाहरण: pgvector (PostgreSQL का add-on, जो आप पहले से जानते हो), Pinecone, Qdrant, Weaviate, Chroma।
  • Normal SQL: WHERE name = 'fees' (बिल्कुल वही शब्द)।
  • Vector database: "वे 5 rows ढूँढो जिनका मतलब इस सवाल के सबसे करीब है"।

उदाहरण: normal database = phone book (सही नाम से ही मिलेगा)। Vector database = समझदार दुकानदार: आप कहो "सिर दर्द के लिए कुछ दो", वह सही दवा दे देता है, भले आपने दवा का नाम न लिया हो।

🎤 "A vector database stores embeddings and can quickly find the ones closest to a question."

3. Keyword search vs semantic search

Keyword searchSemantic search
बिल्कुल वही शब्द match करता हैमतलब match करता है
"fees" ≠ "charges""fees" ≈ "charges" ≈ "कितना खर्च होगा"
SQL LIKE, ElasticsearchEmbeddings + vector database

करीबी आमतौर पर cosine similarity से नापी जाती है: 1 = एक ही मतलब, 0 = कोई संबंध नहीं।

Note: हमारा Kodivo demo bot keyword matching इस्तेमाल करता है। असली version semantic search करेगा, ताकि किसी भी तरह पूछा सवाल समझ सके।

4. Chunking

Embeddings बनाने से पहले बड़े documents को छोटे हिस्सों में काटना।

  • क्यों: 50 pages के PDF का एक embedding बहुत धुंधला होता है, और पूरा PDF prompt में ठीक से नहीं आता।
  • आम size: हर हिस्सा कुछ सौ tokens का, थोड़े overlap के साथ ताकि वाक्य बीच से न कटें।
  • बेहतर कटाई (heading, section या FAQ के हिसाब से) = बेहतर जवाब।

उदाहरण: किसी को पूरी किताब नहीं थमाते। सही page खोल कर देते हो।

5. RAG (Retrieval-Augmented Generation) ⭐⭐

सही जानकारी ढूँढो → prompt में जोड़ो → जवाब लिखो।

दो हिस्से

A) Data save करना (एक बार, या data बदलने पर)

Clinic PDF / FAQs / database rows
   → हिस्सों में काटो
   → हर हिस्से का embedding बनाओ
   → (हिस्से का text + embedding) vector database में save करो

B) जवाब देना (हर सवाल पर)

User: "क्या clinic रविवार को खुला है?"
   → सवाल का embedding बनाओ
   → vector database: 3 सबसे करीबी हिस्से ढूँढो
        → "Sunday: 10 AM – 1 PM"
   → LLM को prompt:
        System: Answer ONLY from the context. If it is not there, say you will confirm.
        Context: <वे 3 हिस्से>
        Question: क्या clinic रविवार को खुला है?
   → LLM: "हाँ, clinic रविवार को सुबह 10 से दोपहर 1 बजे तक खुला है। 🙂"

RAG ही क्यों (बहुत बड़ा prompt या fine-tuning क्यों नहीं)?

  • ✅ जवाब आपके असली data से आते हैं, इसलिए hallucination बहुत कम
  • ✅ Data कभी भी update करो: बस दोबारा save करो, retraining नहीं
  • ✅ सस्ता: सिर्फ़ काम के हिस्से भेजते हो, सब कुछ नहीं
  • ✅ Source दिखा सकते हो ("from: fee-list.pdf")

उदाहरण: open-book exam। Student पहले सही page ढूँढता है (retrieval), फिर उससे जवाब लिखता है (generation), और page number भी बता सकता है (source)।

🎤 "RAG finds the right pieces of my documents using embeddings, adds them to the prompt, and the LLM answers only from them. This cuts hallucination and keeps answers up to date without retraining."

6. RAG vs fine-tuning (बहुत common सवाल)

RAGFine-tuning
क्या करता हैसवाल के समय model को facts देता हैTraining से model के व्यवहार या लिखने का तरीका बदलता है
Data बार-बार बदलता है?✅ बस दोबारा save करो❌ हर बार दोबारा training
खर्चकमज़्यादा
किसके लिए सबसे अच्छाFAQs, documents, company dataतय tone, तय format, खास काम

आसान rule: facts → RAG; style → fine-tuning। ज़्यादातर business apps को RAG चाहिए।

उदाहरण: RAG = नई receptionist को हर सुबह ताज़ा price list देना। Fine-tuning = उसे बात करने का तरीका बदलने के लिए महीनों के course पर भेजना।
