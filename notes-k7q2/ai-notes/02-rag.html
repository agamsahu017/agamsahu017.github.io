Level 2: Embeddings, Vector DB & RAG ⭐

The problem this level solves

An LLM doesn't know your data: your clinic's fees, your company's PDFs, your TIFS database. Ask it, and it will guess (hallucinate). RAG fixes that by finding the right information first and then giving it to the AI with the question.

One-line summary

Turn text into numbers (embeddings) → store them in a vector DB → when a question comes, find the most similar pieces (semantic search) → give those pieces + the question to the LLM → it answers from your data. That whole flow is RAG.

1. Embedding

Converting text into a list of numbers that captures its meaning.

"Clinic fees kitni hai?"     → [0.12, -0.53, 0.88, ...]  (hundreds/thousands of numbers)
"Consultation charge kya hai?" → [0.11, -0.50, 0.85, ...]  ← very similar numbers
"Aaj mausam kaisa hai?"      → [-0.70, 0.31, -0.10, ...] ← very different numbers
  • Same meaning = numbers close together, even if the words are different (and even in different languages).
  • You create embeddings by calling an embedding model API.

Analogy: like a GPS coordinate for meaning. "Fees" and "charges" sit in the same neighbourhood; "weather" is in another city.

🎤 "An embedding is a vector representation of text where semantically similar texts are close together in vector space."

2. Vector database

A database built to store embeddings and quickly find the nearest ones.

  • Examples: pgvector (a PostgreSQL extension, which you already know), Pinecone, Qdrant, Weaviate, Chroma.
  • Normal SQL: WHERE name = 'fees' (exact match)
  • Vector DB: "find the 5 rows whose meaning is closest to this question"

🎤 "A vector database stores embeddings and supports fast similarity search, usually with approximate nearest-neighbour indexes."

3. Semantic search vs keyword search

Keyword search Semantic search
Matches exact words Matches meaning
"fees" ≠ "charges" "fees" ≈ "charges" ≈ "kitna paisa lagega"
SQL LIKE, Elasticsearch Embeddings + vector DB

Similarity is usually measured with cosine similarity: how close two vectors point in the same direction (1 = same meaning, 0 = unrelated).

Note: our Kodivo demo bot uses keyword matching. The real version will use semantic search, which is why it will understand any phrasing.

4. Chunking

Splitting big documents into small pieces before creating embeddings.

  • Why: a 50-page PDF as one embedding is too vague, and it won't fit nicely in the prompt.
  • Typical: a few hundred tokens per chunk, with a small overlap so sentences aren't cut in half.
  • Better chunking (by heading, section or FAQ) gives better answers.

Analogy: you don't hand someone a whole book. You tear out the right page.

5. RAG (Retrieval-Augmented Generation) ⭐⭐

Retrieve the right info → Augment the prompt with it → Generate the answer.

Two phases

A) Indexing (once, or whenever data changes)

Clinic PDF / FAQs / DB rows
   → split into chunks
   → create an embedding for each chunk
   → store (chunk text + embedding) in the vector DB

B) Answering (every user question)

User: "Sunday ko clinic khula hai?"
   → embed the question
   → vector DB: find the top 3 most similar chunks
        → "Sunday: 10 AM – 1 PM"
   → prompt to LLM:
        System: Answer ONLY from the context. If it's not there, say you'll confirm.
        Context: <top 3 chunks>
        Question: Sunday ko clinic khula hai?
   → LLM: "Haan, Sunday ko clinic 10 AM se 1 PM tak khula hai. 🙂"

Why RAG (and not just a huge prompt or fine-tuning)?

  • ✅ Answers from your real data → far fewer hallucinations
  • ✅ Update data anytime: just re-index, no retraining
  • ✅ Cheaper: you send only the relevant chunks, not everything
  • ✅ You can show sources ("from: fee-list.pdf")

🎤 "RAG retrieves relevant documents using embeddings and similarity search, adds them to the prompt as context, and the LLM generates an answer grounded in that context. It reduces hallucination and keeps knowledge up to date without retraining."

6. RAG vs fine-tuning (very common interview question)

RAG Fine-tuning
What it does Gives the model knowledge at question time Changes the model's behaviour/style by training
Data changes often? ✅ Just re-index ❌ Retrain each time
Cost Low Higher
Best for FAQs, documents, company data Fixed tone, format, specialised tasks

Rule of thumb: knowledge → RAG; behaviour/style → fine-tuning. Most business apps need RAG.

7. Mapping RAG to things you know

RAG piece Your world
Vector DB PostgreSQL + pgvector extension
Indexing job A NestJS cron/queue job that embeds new rows/files
Retrieval A SQL query: ORDER BY embedding <=> $questionEmbedding LIMIT 5
Generation One API call to the LLM with context + question

You can build RAG with tools you already use. That's a strong interview point.

Interview questions (answer out loud)

  1. What is an embedding? Give an example.
  2. How is semantic search different from keyword search?
  3. Explain the RAG pipeline end to end (indexing + answering).
  4. Why do we chunk documents? What happens if chunks are too big or too small?
  5. RAG vs fine-tuning: when would you use each?
  6. How does RAG reduce hallucination? Can it remove it completely? (→ No. Also use "answer only from context" instructions, show sources, and run evals.)
  7. Which vector DB would you choose and why? (→ pgvector if already on PostgreSQL: one less system to run.)

Quiz

  1. A clinic changes its fees every month. RAG or fine-tuning? Why?
  2. A user asks "kitna paisa lagega?" but the document says "Consultation fee: ₹400". Will keyword search find it? Will semantic search?
  3. What two things are stored for each chunk in the vector DB?
