Part A: The base (frontend, backend, database)

1. Next.js

  • What: a framework on top of React. You make pages by making folders and files.
  • Why use it: pages can be made on the server, so Google can read them (good SEO) and they open fast. You can also write small APIs in the same project.
  • Example: app/menu/page.tsx becomes the page /menu.
  • How it works:
    1. Server component: runs on the server, can read the database, sends ready HTML.
    2. Client component: has "use client" at the top, runs in the browser, can use buttons, state, clicks.
  • Real-life example: a server component is a thali served ready from the kitchen. A client component is the chutney jar on the table that the customer uses himself.
  • Common mistake: putting secret keys in client components. Anything in the browser can be seen by anyone.
  • Interview Q: Why Next.js instead of plain React? → Server rendering for SEO and speed, file-based routing, and API routes in one project.

2. NestJS

  • What: a Node.js backend framework with a fixed structure. Good for big projects and teams.
  • Main parts:
    • Module = a box for one feature (bookings, users).
    • Controller = gets the HTTP request (GET /bookings).
    • Service = the real business logic.
    • Guard = checks "is this user allowed?" before the controller runs.
    • DTO = the shape of the incoming data, with validation rules.
  • Real-life example: an office. Module = a department, Controller = the reception, Service = the clerk who does the real work, Guard = the gate security, DTO = a form with a fixed format.
  • Example:
@Controller('bookings')
export class BookingsController {
  constructor(private service: BookingsService) {}
  @Post() create(@Body() dto: CreateBookingDto) { return this.service.create(dto); }
}
  • Common mistake: writing all logic in the controller. Keep controllers thin, logic in services.
  • Interview Q: What is dependency injection? → Nest creates the service and gives it to the controller. You don't write new BookingsService(). This makes testing easy (you can pass a fake service).

3. PostgreSQL

  • What: a reliable SQL database. Tables, relations, indexes, transactions.
  • Things you must know:
    • Index = like a book index; makes search fast. Add one on columns you filter by (phone, tenant_id, created_at).
    • Transaction = many steps that all succeed or all fail (BEGIN ... COMMIT). Like a bank transfer: if money leaves one account it must reach the other, otherwise nothing happens.
    • Unique constraint = the database itself stops duplicates.
    • JSONB = store flexible JSON in a column, and still search it.
  • Common mistake: no index on a big table → slow pages after a few months.
  • Interview Q: How do you find a slow query? → EXPLAIN ANALYZE, look for "Seq Scan" on a big table, add the right index.

Part B: AI topics

4. Claude API (calling an LLM from your code)

  • What: you send messages to the model from your backend and get a reply back.
  • Example:
import Anthropic from '@anthropic-ai/sdk';
const client = new Anthropic(); // reads ANTHROPIC_API_KEY from .env
const reply = await client.messages.create({
  model: 'claude-sonnet-5-5',
  max_tokens: 500,
  system: 'You are the receptionist of CareWell Clinic. Answer only from the given info.',
  messages: [{ role: 'user', content: 'What time do you open on Sunday?' }],
});
console.log(reply.content[0].text);
  • Good to know:
    • Streaming = show the answer word by word, so the user does not wait.
    • Cost = you pay per token (input + output). Keep prompts short, cache the fixed part.
    • The API key stays only on the server, never in the browser or in GitHub.
  • Real-life example: calling an expert on the phone: you pay per minute (tokens), and you never give their number (API key) to anyone.
  • Common mistake: no timeout and no retry. APIs sometimes fail; retry 2–3 times with a small wait.
  • Interview Q: How do you control cost? → Short prompts, send only the top chunks (not the whole document), use a smaller model for easy tasks, cache repeated answers, set max_tokens.

5. RAG (quick recap)

  • What: find the right pieces of your data first, then give them to the LLM to answer. Full chapter: 02-rag.md.
  • Flow: question → make an embedding → search pgvector → top 5 pieces → put them in the prompt → LLM answers.

6. pgvector

  • What: an add-on for PostgreSQL that stores embeddings (lists of numbers) and finds the closest ones.
  • Example:
CREATE EXTENSION vector;
CREATE TABLE chunks (id serial PRIMARY KEY, tenant_id int, source text, page int,
                     content text, embedding vector(384));
-- find the 5 closest pieces to the question
SELECT content, source, page FROM chunks
WHERE tenant_id = $1
ORDER BY embedding <=> $2   -- <=> means cosine distance
LIMIT 5;
  • Why pgvector: you already use PostgreSQL, so there is no new system to run or pay for.
  • Common mistake: the question and the documents use different embedding models. They must use the same model. (Like comparing distances when one map is in km and the other in miles.)
  • Interview Q: When would you move from pgvector to Pinecone/Qdrant? → When you have many millions of vectors and need very fast search at scale. For small business bots, pgvector is enough.

7. Chunking

  • What: cutting a long document into small pieces before making embeddings.
  • Simple rule: 300–800 words per piece, with a small overlap (for example 50 words) so a sentence is not cut in half.
  • Better: cut by headings or paragraphs, not blindly by count. Keep the heading with the piece.
  • Save extra info (metadata) with each piece: file name, page number, section. You need this for citations.
  • Real-life example: you serve a watermelon in slices, not whole, and each plate gets a name slip.
  • Common mistake: pieces too big (search becomes fuzzy) or too small (the answer is split across pieces).

8. Citations

  • What: the bot shows where the answer came from, like "Source: Fee-Policy.pdf, page 3".
  • Why: users trust it more, and you can check if it is right.
  • Real-life example: a news report that says "according to RBI's report, page 12". You can go and check it yourself.
  • How:
    1. Give each piece a number in the prompt: [1] ...text..., [2] ...text....
    2. Tell the model: "Answer only from these pieces. After each fact, write the piece number like [2]. If the answer is not there, say you don't know."
    3. In your code, turn [2] into the file name and page from the metadata.
    4. Check: if the model writes [7] but you only sent 5 pieces, remove it.
  • Interview Q: How do you stop made-up answers? → Answer only from context, ask for citations, say "I don't know" when nothing matches, and test it with evals.

9. Evals (testing an AI system)

  • What: a fixed list of test questions with the right answers. You run it after every change to see if the bot got better or worse.
  • Example test set (20–50 rows):
Question Right answer Right source
Sunday timing? 10 AM – 2 PM timings.md
Fee for X-ray? ₹400 price-list.pdf p2
Do you do MRI? No (should say "not available") —
  • What to measure:
    • Search hit: did the right piece come in the top 5?
    • Correct: is the answer right? (check by hand, or ask another LLM to grade it)
    • Grounded: does the answer only use the given pieces?
    • "I don't know" works: for questions not in the data, does it refuse?
  • Real-life example: a mock test before the board exam. Same paper every time, so you can see if your score went up or down.
  • Common mistake: changing the prompt and checking with only 1–2 questions.
  • Interview Q: How do you know your RAG bot is good? → A test set, measure search hit and answer correctness, run it on every change, track the score over time.

10. Vision AI

  • What: the model can read images: bills, ID cards, forms, handwritten notes, screenshots.
  • Example: a shop owner sends a photo of a bill on WhatsApp → the bot reads vendor, date, items, total.
messages: [{ role: 'user', content: [
  { type: 'image', source: { type: 'base64', media_type: 'image/jpeg', data: base64Image } },
  { type: 'text', text: 'Read this bill. Return only JSON with vendor, date, items, total.' },
]}]
  • Common mistake: trusting the numbers blindly. Blurry photos → wrong digits. Always validate (next topics).

11. Structured JSON output

  • What: making the model reply in a fixed JSON shape, so your code can save it in the database.
  • Real-life example: a bank deposit slip: every box has a fixed place, so the clerk reads it instantly.
  • Example shape:
{ "vendor": "Sharma Traders", "date": "2026-11-10",
  "items": [{ "name": "Rice 5kg", "qty": 2, "price": 450 }], "total": 900 }
  • How to get it reliably:
    1. Give the exact shape (a JSON schema) in the request. The best way is to use the API's structured output / tool feature, which forces the reply to match the schema.
    2. Say "if a field is not visible, use null. Do not guess."
    3. Parse it with JSON.parse inside try/catch.
  • Interview Q: What if the JSON is broken? → Use schema-forced output, validate, and if it still fails, retry once with the error message, then send it to a human.

12. Validation

  • What: checking data before you trust or save it. Use it for user input and for AI output.
  • Real-life example: a cashier holds a note up to the light before accepting it. Check first, trust later.
  • Example with zod:
import { z } from 'zod';
const Bill = z.object({
  vendor: z.string().min(1),
  date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/),
  items: z.array(z.object({ name: z.string(), qty: z.number().positive(), price: z.number().nonnegative() })),
  total: z.number().nonnegative(),
});
const result = Bill.safeParse(aiJson);
if (!result.success) { /* retry or mark "needs review" */ }
  • Business checks too: does the sum of items equal the total? Is the date not in the future? Is GSTIN 15 characters?
  • Common mistake: only checking on the frontend. Always check on the backend; the frontend can be skipped.

13. AI agent and tool calling

  • What: the LLM can ask your code to do things (check slots, book, send a message). Your code does the work and sends the result back. Full chapter: 03-agents.md.
  • Flow: user asks → LLM says "call getSlots(date)" → your code runs it → result goes back to the LLM → LLM replies or calls the next tool.
  • Rules: give few, clear tools; check every tool input; set a step limit (for example 5) so it cannot loop forever.

14. Human approval

  • What: for risky actions, the agent prepares the action, and a person clicks Approve or Reject.
  • When: sending money, refunds, deleting data, sending a message to 500 people.
  • Real-life example: the clerk fills in the cheque, but the owner signs it.
  • How: save the action in a table with status pending → show it in the admin panel → on Approve, your code runs it → on Reject, nothing happens.
  • Interview Q: How do you make an AI agent safe? → Limited tools, input checks, role checks, human approval for risky actions, step limit, and audit logs.

15. Audit logs

  • What: a table that records who did what, when, and what changed.
  • Real-life example: the visitor register at a society gate: who came, to meet whom, at what time. Pages are never torn out.
CREATE TABLE audit_logs (id bigserial PRIMARY KEY, tenant_id int, user_id int,
  action text, entity text, entity_id text, old_data jsonb, new_data jsonb,
  created_at timestamptz DEFAULT now());
  • For AI agents: also save the tool name, the inputs, the result, and whether a human approved it.
  • Rule: only add rows, never edit or delete them.

Part C: Backend topics

16. Webhooks

  • What: another service calls your URL when something happens. "Don't call us, we'll call you."
  • Examples: WhatsApp → "a new message came"; Razorpay → "payment done".
  • Real-life example: a doorbell. You don't keep opening the door to check if someone came; the visitor rings and you go.
  • Rules for a good webhook:
    1. Check the signature (a secret code in the header), so fake requests are rejected.
    2. Reply 200 fast (within a few seconds). Put the real work in a queue.
    3. Idempotent: the same webhook can come twice. Save the event id; if you have seen it before, skip it.
  • Common mistake: calling the LLM inside the webhook. It is slow, the sender times out and sends it again → double replies.

17. Queue (and workers)

  • What: a waiting line for slow jobs. The API adds a job; a separate worker does it in the background.
  • Tool for Node: BullMQ (uses Redis).
  • Real-life example: the token system at a bank. You take a token and sit down; the counter calls you when it is free.
  • Example: webhook gets a WhatsApp message → queue.add('reply', { from, text }) → returns 200 → worker runs RAG + Claude → sends the reply.
  • Good things you get: retries with a wait (1s, 5s, 30s), limit on how many jobs run at once, failed jobs saved for checking.
  • Interview Q: Why use a queue? → The user gets a fast response, slow work runs in the background, failed jobs are retried, and you can add more workers when busy.

18. Bulk jobs

  • What: doing the same work for many items: 300 certificates, 1,000 WhatsApp messages, a big Excel import.
  • How:
    1. Make one "batch" row (batch_id, total, done, failed, status).
    2. Add one small job per item to the queue (not one giant job).
    3. Each job updates the counts. The admin page shows "245 / 300 done, 2 failed".
    4. Failed items can be retried alone.
  • Real-life example: a wedding card printer prints and packs cards in small bundles and keeps a count, instead of one huge pile that nobody can track.
  • Common mistake: a loop of 1,000 items inside one API call → timeout, and nobody knows which ones finished.

19. Cron (scheduled jobs)

  • What: code that runs on a timetable. "Every day at 9 AM", "every 5 minutes".
  • In NestJS: @Cron('0 9 * * *') from @nestjs/schedule.
  • Real-life example: a morning alarm, or the milkman who comes at 6 AM every day without being called.
  • Example (reminders): every 15 minutes → find appointments starting in the next 2 hours with reminder_sent = false → add a reminder job to the queue → set reminder_sent = true.
  • Common mistakes:
    • Running 2 copies of the server → the cron runs twice → double messages. Fix: a lock, or run cron on only one server, or use BullMQ repeat jobs.
    • Time zones: save times in UTC, show them in IST.

20. Slot locking (stop double booking)

  • Problem: two people click the same 11:00 slot at the same second. Both see "free". Both get booked. 😬
  • Real-life example: two people sitting on the last train seat at the same moment. The TTE (the database) decides who gets it, not the passengers.
  • Fix 1 (simplest, strongest): a unique rule in the database.
CREATE UNIQUE INDEX one_booking_per_slot ON bookings (doctor_id, slot_start)
WHERE status IN ('held', 'booked');

The second insert fails → show "Sorry, this slot was just taken."

  • Fix 2: a row lock in a transaction: SELECT ... FOR UPDATE on the slot row, check it is free, then book, then COMMIT.
  • Fix 3: hold during payment: mark the slot held with hold_until = now() + 10 minutes. If payment does not finish, a cron frees it.
  • Interview Q: How do you stop double booking? → Let the database decide (unique constraint or row lock), never just "check then insert" in code, and use a short hold while the user pays.

21. WebSocket (real-time)

  • What: a connection that stays open, so the server can push updates to the browser at once. Normal HTTP only answers when asked.
  • Example (restaurant): customer places an order → server sends order:new to the kitchen screen instantly → kitchen marks "Preparing" → customer's phone shows it instantly.
  • Tool: Socket.IO (works well with NestJS). Use rooms: one room per restaurant, one per order.
  • Good to know: if the connection drops, reload the latest data from the API when it reconnects. With many servers, use the Redis adapter.
  • Interview Q: WebSocket vs polling? → Polling asks every few seconds (simple, wasteful). WebSocket pushes only when something changes (fast, but you must handle reconnects).

Part D: Business app topics

22. Multi-tenant SaaS

  • What: one app, many customers (each customer = one tenant). Like one building with many flats; each family only enters its own flat.
  • Simplest way: a tenant_id column in every table, and every query filters by it.
SELECT * FROM invoices WHERE tenant_id = $1 AND id = $2;
  • How the app knows the tenant: from the logged-in user's token (or the subdomain, like sharma.yourapp.in). Never from a value the browser sends in the body.
  • Extra safety: PostgreSQL Row Level Security (RLS) can make the database itself block other tenants' rows.
  • Common mistake: forgetting tenant_id in one query → one shop sees another shop's data. This is the worst bug in SaaS.
  • Interview Q: How do you keep tenant data apart? → tenant_id from the token, filter in every query (one shared helper or RLS), indexes that start with tenant_id, and tests that try to read another tenant's data.

23. Roles and RBAC

  • What: RBAC = Role-Based Access Control. Users get a role; each role has permissions.
  • Example (school):
Role Can do
Admin everything
Teacher mark attendance, enter marks for own classes
Accountant fees and receipts
Parent see own child only
  • In NestJS: a @Roles('admin', 'teacher') decorator + a guard that checks the user's role from the token.
  • Two levels of checks:
    1. Can this role do this action? (teacher can enter marks)
    2. Can this user touch this record? (only their own class / child). People forget this one.
  • Real-life example: a hospital ID card. A nurse can enter the ward but not the pharmacy store, and can see only her own patients' files.
  • Common mistake: only hiding buttons on the frontend. The API must check too.

24. Payments (Razorpay in India)

  • Flow:
    1. Backend creates an order with Razorpay (amount, receipt id).
    2. Frontend opens Razorpay checkout; the user pays by UPI / card.
    3. Razorpay calls your webhook (payment.captured).
    4. Backend checks the signature, then marks the order paid (only once).
  • Real-life example: a shopkeeper doesn't hand over goods because the customer shows a "payment done" screenshot; he waits for the bank's SMS on his own phone (the verified webhook).
  • Golden rules:
    • Never trust the frontend saying "payment success". Only trust the verified webhook or a server check.
    • Save amounts in paise (whole numbers), not decimals.
    • Idempotent: if the order is already paid, do nothing.
    • A cron checks old "pending" orders with Razorpay, in case a webhook was lost.

25. Reports and dashboards

  • What: numbers and charts for the owner: today's sales, fees pending, attendance %, leads this week.
  • How:
    • SQL GROUP BY with date filters: SELECT date(created_at), sum(amount) FROM payments WHERE tenant_id=$1 GROUP BY 1.
    • For heavy reports, a cron fills a summary table every night (or every hour). The dashboard reads the small table, so it is fast.
    • Add filters (date range, branch, class) and export to Excel/CSV.
  • Real-life example: a shopkeeper writes one line with the day's total every night, so at month-end he doesn't add up every bill again (summary table).
  • Common mistake: running big reports on the main database during busy hours. Use a summary table or a read replica.

26. Admin panel

  • What: the owner's control room: see and edit orders, menu, users, settings.
  • Must have: login + roles, tables with search, filter, sort and pagination, add/edit forms with validation, and audit logs for changes.
  • Tip: build it once as a reusable kit (table + form + filters). Use it in every client project to save time.

27. WhatsApp Business API

  • What: the official way for a business to send and receive WhatsApp messages from code (Meta's Cloud API, directly or through a provider like Gupshup, Interakt, AiSensy).
  • Receiving: Meta calls your webhook with each new message.
  • Sending: your server calls Meta's API with the phone number and the message.
  • 24-hour rule: after a customer messages you, you can reply freely for 24 hours. After that, you can only send an approved template.
  • Cost: Meta charges for some message types (like marketing templates). Check the current price list before quoting a client.
  • Common mistake: using an unofficial WhatsApp bot on a normal number → the number gets banned.

28. WhatsApp templates

  • What: pre-approved message formats with blanks, for messages you start (reminders, offers, follow-ups).
  • Example: Hi {{1}}, your appointment at {{2}} is on {{3}}. Reply YES to confirm.
  • Real-life example: a printed wedding card: the format is fixed, you only fill in names and dates.
  • Types: Utility (reminders, order updates) and Marketing (offers). Marketing usually costs more and needs the user's opt-in.
  • Tips: keep them short and useful, add an opt-out ("Reply STOP"), and wait for Meta's approval before using.

29. Analytics (for messages and campaigns)

  • What: measuring what happened: sent, delivered, read, replied, converted.
  • How: WhatsApp sends status webhooks (sent → delivered → read). Save each one in an message_events table. Then count by day / campaign.
SELECT campaign_id,
  count(*) FILTER (WHERE status='sent')      AS sent,
  count(*) FILTER (WHERE status='read')      AS read,
  count(*) FILTER (WHERE status='replied')   AS replied
FROM message_events WHERE tenant_id=$1 GROUP BY campaign_id;
  • Show the owner simple numbers: "500 sent, 410 read, 38 replied, 9 booked". That is what makes them pay again.

30. QR verification

  • What: a QR code on a certificate (or ticket, invoice) that opens a page saying "this is real".
  • Real-life example: the code on a medicine strip: scan it and the company's site tells you if it is genuine.
  • How:
    1. Give each certificate a unique ID. Better: a random code that cannot be guessed (KOD-7F3K-92QX), not just 0001, 0002.
    2. The QR holds a link: yoursite.in/verify?id=KOD-7F3K-92QX.
    3. The verify page looks up the ID in the database and shows name, course, dates, or "not found".
  • Extra: the ability to cancel (revoke) a certificate, and logging each check.
  • Common mistake: putting all the details inside the QR itself. Anyone can make a fake QR like that. The QR must point to your website.

31. PDF generation

  • What: making PDFs from code: certificates, invoices, salary slips, reports.
  • Two easy ways:
    • HTML → PDF with Puppeteer (a headless Chrome): design in HTML/CSS, then page.pdf(). Easiest for nice designs.
    • pdfkit / pdf-lib: draw text and shapes with code. Lighter, but harder to design.
  • Tips: make PDFs in a queue worker, not in the API call. Save them to S3 and send a link. Embed the fonts (Hindi needs a Devanagari font).
  • Common mistake: starting a new Chrome for every PDF. Start it once and reuse it for many pages. (You don't buy a new machine for every photocopy.)

How to say it in an interview (one story per project)

Use this shape: Problem → what I built → one hard part → result.

"A clinic was missing calls. I built a WhatsApp AI receptionist: webhook → queue → RAG on pgvector → Claude → reply. The hard part was double replies when WhatsApp re-sent the webhook, so I made it idempotent using the message id. It now answers 80% of questions without staff."

Only use numbers that are true for your project.

Quick check (answer out loud)

  1. Why should a webhook reply fast, and where does the slow work go?
  2. Two people book the same slot at the same time. What stops it?
  3. How does the app know which tenant a request belongs to?
  4. How do you make sure AI JSON output is safe to save?
  5. Why should the QR code link to your website instead of holding all the details?
  6. Your cron sends reminders twice. Why, and how do you fix it?
  7. How do you know your RAG bot got better after a change?

Part A: नींव (frontend, backend, database)

1. Next.js

  • क्या: React के ऊपर बना framework। Folders और files बनाने से pages बन जाते हैं।
  • क्यों: pages server पर बन सकते हैं, इसलिए Google उन्हें पढ़ पाता है (अच्छा SEO) और वे जल्दी खुलते हैं। उसी project में छोटी APIs भी लिख सकते हो।
  • उदाहरण: app/menu/page.tsx page /menu बन जाता है।
  • कैसे काम करता है:
    1. Server component: server पर चलता है, database पढ़ सकता है, तैयार HTML भेजता है।
    2. Client component: ऊपर "use client" लिखा होता है, browser में चलता है, buttons, state, clicks इस्तेमाल कर सकता है।
  • असली ज़िंदगी का उदाहरण: server component = restaurant में पहले से थाली सजा कर लाना। Client component = मेज़ पर रखा chutney का डिब्बा जिसे customer खुद इस्तेमाल करे।
  • आम गलती: secret keys client components में रख देना। Browser में जो कुछ है, उसे कोई भी देख सकता है।
  • Interview Q: Why Next.js instead of plain React? → SEO और speed के लिए server rendering, file-based routing, और एक ही project में API routes।

2. NestJS

  • क्या: तय ढाँचे वाला Node.js backend framework। बड़े projects और teams के लिए अच्छा।
  • मुख्य हिस्से:
    • Module = एक feature का डिब्बा (bookings, users)।
    • Controller = HTTP request लेता है (GET /bookings)।
    • Service = असली business logic।
    • Guard = controller चलने से पहले check करता है "क्या यह user allowed है?"।
    • DTO = आने वाले data का shape, validation rules के साथ।
  • असली ज़िंदगी का उदाहरण: एक office। Module = विभाग, Controller = reception, Service = असली काम करने वाला clerk, Guard = gate का security, DTO = तय format वाला form।
  • उदाहरण:
@Controller('bookings')
export class BookingsController {
  constructor(private service: BookingsService) {}
  @Post() create(@Body() dto: CreateBookingDto) { return this.service.create(dto); }
}
  • आम गलती: सारा logic controller में लिख देना। Controllers पतले रखो, logic services में।
  • Interview Q: What is dependency injection? → Nest service बना कर controller को दे देता है। आप new BookingsService() नहीं लिखते। इससे testing आसान होती है (नकली service दे सकते हो)।

3. PostgreSQL

  • क्या: भरोसेमंद SQL database। Tables, relations, indexes, transactions।
  • ज़रूर जानने वाली बातें:
    • Index = किताब के index जैसा; search तेज़ करता है। जिन columns से filter करते हो उन पर लगाओ (phone, tenant_id, created_at)।
    • Transaction = कई steps जो या तो सब सफल हों या सब fail (BEGIN ... COMMIT)। जैसे ATM से transfer: एक खाते से कटे तो दूसरे में जुड़ना ही चाहिए, नहीं तो कुछ भी नहीं।
    • Unique constraint = database खुद duplicates रोकता है।
    • JSONB = column में flexible JSON रखो, और फिर भी उसमें search कर सको।
  • आम गलती: बड़ी table पर index नहीं → कुछ महीनों में pages धीमे।
  • Interview Q: How do you find a slow query? → EXPLAIN ANALYZE, बड़ी table पर "Seq Scan" देखो, सही index लगाओ।

Part B: AI topics

4. Claude API (अपने code से LLM call करना)

  • क्या: आप अपने backend से model को messages भेजते हो और जवाब लेते हो।
  • उदाहरण:
import Anthropic from '@anthropic-ai/sdk';
const client = new Anthropic(); // .env से ANTHROPIC_API_KEY पढ़ता है
const reply = await client.messages.create({
  model: 'claude-sonnet-5-5',
  max_tokens: 500,
  system: 'You are the receptionist of CareWell Clinic. Answer only from the given info.',
  messages: [{ role: 'user', content: 'What time do you open on Sunday?' }],
});
console.log(reply.content[0].text);
  • जानने लायक:
    • Streaming = जवाब शब्द-शब्द दिखाओ, ताकि user को इंतज़ार न करना पड़े।
    • Cost = हर token का पैसा (input + output)। Prompts छोटे रखो, तय हिस्सा cache करो।
    • API key सिर्फ़ server पर रहती है, कभी browser या GitHub में नहीं।
  • असली ज़िंदगी का उदाहरण: किसी expert को phone करके सवाल पूछना: हर minute का bill (tokens), और उसका नंबर (API key) किसी को नहीं देना।
  • आम गलती: न timeout, न retry। APIs कभी-कभी fail होती हैं; थोड़ा रुक कर 2–3 बार retry करो।
  • Interview Q: How do you control cost? → छोटे prompts, सिर्फ़ top chunks भेजो (पूरा document नहीं), आसान कामों के लिए छोटा model, दोहराए जवाब cache करो, max_tokens तय करो।

5. RAG (जल्दी से दोहराना)

  • क्या: पहले अपने data के सही हिस्से ढूँढो, फिर उन्हें LLM को जवाब देने के लिए दो। पूरा chapter: 02-rag।
  • Flow: सवाल → embedding बनाओ → pgvector में search → top 5 हिस्से → prompt में डालो → LLM जवाब देता है।

6. pgvector

  • क्या: PostgreSQL का add-on जो embeddings (numbers की lists) रखता है और सबसे करीबी ढूँढता है।
  • उदाहरण:
CREATE EXTENSION vector;
CREATE TABLE chunks (id serial PRIMARY KEY, tenant_id int, source text, page int,
                     content text, embedding vector(384));
-- सवाल के सबसे करीबी 5 हिस्से ढूँढो
SELECT content, source, page FROM chunks
WHERE tenant_id = $1
ORDER BY embedding <=> $2   -- <=> मतलब cosine distance
LIMIT 5;
  • pgvector क्यों: PostgreSQL आप पहले से इस्तेमाल करते हो, तो चलाने या पैसे देने के लिए कोई नया system नहीं।
  • आम गलती: सवाल और documents के लिए अलग-अलग embedding models। दोनों का model एक ही होना चाहिए। (जैसे एक नक्शा km में और दूसरा miles में हो, तो दूरी की तुलना बेकार।)
  • Interview Q: When would you move from pgvector to Pinecone/Qdrant? → जब कई करोड़ vectors हों और बड़े scale पर बहुत तेज़ search चाहिए। छोटे business bots के लिए pgvector काफ़ी है।

7. Chunking

  • क्या: embeddings बनाने से पहले लंबे document को छोटे हिस्सों में काटना।
  • आसान rule: हर हिस्सा 300–800 शब्द, थोड़े overlap के साथ (जैसे 50 शब्द) ताकि वाक्य बीच से न कटे।
  • बेहतर: गिनती से अंधाधुंध नहीं, headings या paragraphs के हिसाब से काटो। Heading को हिस्से के साथ रखो।
  • हर हिस्से के साथ extra info (metadata) रखो: file का नाम, page number, section। Citations के लिए ज़रूरी।
  • असली ज़िंदगी का उदाहरण: पूरा तरबूज़ नहीं, टुकड़े काट कर परोसते हैं, और हर plate पर नाम की पर्ची।
  • आम गलती: हिस्से बहुत बड़े (search धुंधला हो जाता है) या बहुत छोटे (जवाब कई हिस्सों में बँट जाता है)।

8. Citations

  • क्या: bot दिखाता है कि जवाब कहाँ से आया, जैसे "Source: Fee-Policy.pdf, page 3"।
  • क्यों: users ज़्यादा भरोसा करते हैं, और आप check कर सकते हो कि सही है या नहीं।
  • असली ज़िंदगी का उदाहरण: खबर में लिखा हो "RBI की report, page 12 के अनुसार"। आप खुद जाकर देख सकते हो।
  • कैसे:
    1. Prompt में हर हिस्से को एक number दो: [1] ...text..., [2] ...text...।
    2. Model से कहो: "सिर्फ़ इन हिस्सों से जवाब दो। हर fact के बाद हिस्से का number लिखो जैसे [2]। जवाब न मिले तो कहो पता नहीं।"
    3. अपने code में [2] को metadata से file के नाम और page में बदलो।
    4. Check: अगर model [7] लिखे पर आपने सिर्फ़ 5 हिस्से भेजे थे, तो उसे हटा दो।
  • Interview Q: How do you stop made-up answers? → सिर्फ़ context से जवाब, citations माँगो, कुछ match न हो तो "I don't know", और evals से test करो।

9. Evals (AI system की testing)

  • क्या: सही जवाबों के साथ test सवालों की एक तय list। हर बदलाव के बाद चलाओ और देखो bot बेहतर हुआ या खराब।
  • असली ज़िंदगी का उदाहरण: board exam से पहले mock test। हर बार वही paper, ताकि पता चले score बढ़ा या घटा।
  • उदाहरण test set (20–50 rows):
सवालसही जवाबसही source
रविवार का समय?10 AM – 2 PMtimings.md
X-ray की fee?₹400price-list.pdf p2
क्या MRI होता है?नहीं ("उपलब्ध नहीं" कहना चाहिए)—
  • क्या नापना है:
    • Search hit: सही हिस्सा top 5 में आया?
    • सही: जवाब सही है? (हाथ से check करो, या दूसरे LLM से grade करवाओ)
    • Grounded: जवाब सिर्फ़ दिए गए हिस्सों से है?
    • "I don't know" काम करता है: data में न होने वाले सवालों पर मना करता है?
  • आम गलती: prompt बदल कर सिर्फ़ 1–2 सवालों से check करना।
  • Interview Q: How do you know your RAG bot is good? → Test set, search hit और जवाब की सटीकता नापो, हर बदलाव पर चलाओ, समय के साथ score track करो।

10. Vision AI

  • क्या: model images पढ़ सकता है: bills, ID cards, forms, हाथ से लिखे notes, screenshots।
  • उदाहरण: दुकानदार WhatsApp पर bill की photo भेजता है → bot vendor, date, items, total पढ़ लेता है। (हमारा Bill Reader यही करता है।)
messages: [{ role: 'user', content: [
  { type: 'image', source: { type: 'base64', media_type: 'image/jpeg', data: base64Image } },
  { type: 'text', text: 'Read this bill. Return only JSON with vendor, date, items, total.' },
]}]
  • आम गलती: numbers पर आँख मूँद कर भरोसा। धुंधली photo → गलत अंक। हमेशा validate करो (अगले topics)।

11. Structured JSON output

  • क्या: model से तय JSON shape में जवाब लेना, ताकि आपका code उसे database में save कर सके।
  • असली ज़िंदगी का उदाहरण: bank का deposit slip: हर खाने की जगह तय है, इसलिए clerk तुरंत पढ़ लेता है।
  • उदाहरण shape:
{ "vendor": "Sharma Traders", "date": "2026-11-10",
  "items": [{ "name": "Rice 5kg", "qty": 2, "price": 450 }], "total": 900 }
  • भरोसे से कैसे पाएँ:
    1. Request में exact shape (JSON schema) दो। सबसे अच्छा तरीका है API का structured output / tool feature, जो जवाब को schema से match करने पर मजबूर करता है।
    2. कहो "कोई field न दिखे तो null लिखो। अंदाज़ा मत लगाओ।"
    3. try/catch के अंदर JSON.parse से parse करो।
  • Interview Q: What if the JSON is broken? → Schema-forced output इस्तेमाल करो, validate करो, फिर भी fail हो तो error message के साथ एक बार retry, फिर इंसान को भेजो।

12. Validation

  • क्या: data पर भरोसा या save करने से पहले उसे check करना। User input और AI output दोनों के लिए।
  • असली ज़िंदगी का उदाहरण: cashier नोट लेने से पहले उसे रोशनी में देखता है। भरोसा बाद में, जाँच पहले।
  • zod के साथ उदाहरण:
import { z } from 'zod';
const Bill = z.object({
  vendor: z.string().min(1),
  date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/),
  items: z.array(z.object({ name: z.string(), qty: z.number().positive(), price: z.number().nonnegative() })),
  total: z.number().nonnegative(),
});
const result = Bill.safeParse(aiJson);
if (!result.success) { /* retry करो या "needs review" mark करो */ }
  • Business checks भी: items का जोड़ total के बराबर है? Date भविष्य की तो नहीं? GSTIN 15 characters का है?
  • आम गलती: सिर्फ़ frontend पर check करना। हमेशा backend पर check करो; frontend को bypass किया जा सकता है।

13. AI agent और tool calling

  • क्या: LLM आपके code से काम करवा सकता है (slots check, booking, message भेजना)। काम आपका code करता है और result वापस भेजता है। पूरा chapter: 03-agents।
  • Flow: user पूछता है → LLM कहता है "getSlots(date) call करो" → आपका code चलाता है → result LLM के पास → LLM जवाब देता है या अगला tool call करता है।
  • Rules: कम और साफ़ tools दो; हर tool input check करो; step limit रखो (जैसे 5) ताकि हमेशा loop में न घूमे।

14. Human approval

  • क्या: risky कामों के लिए agent काम तैयार करता है, और एक इंसान Approve या Reject दबाता है।
  • कब: पैसे भेजना, refunds, data delete करना, 500 लोगों को message भेजना।
  • असली ज़िंदगी का उदाहरण: clerk cheque भर कर तैयार रखता है, पर sign मालिक करता है।
  • कैसे: काम को pending status के साथ एक table में save करो → admin panel में दिखाओ → Approve पर आपका code चलाए → Reject पर कुछ नहीं।
  • Interview Q: How do you make an AI agent safe? → सीमित tools, input checks, role checks, risky कामों पर human approval, step limit, और audit logs।

15. Audit logs

  • क्या: एक table जो record करती है कि किसने क्या किया, कब, और क्या बदला।
  • असली ज़िंदगी का उदाहरण: society के gate का visitor register: कौन आया, किससे मिलने, कितने बजे। पन्ने फाड़े नहीं जाते।
CREATE TABLE audit_logs (id bigserial PRIMARY KEY, tenant_id int, user_id int,
  action text, entity text, entity_id text, old_data jsonb, new_data jsonb,
  created_at timestamptz DEFAULT now());
  • AI agents के लिए: tool का नाम, inputs, result, और इंसान ने approve किया या नहीं, यह भी save करो।
  • Rule: सिर्फ़ rows जोड़ो, कभी edit या delete मत करो।

Part C: Backend topics

16. Webhooks

  • क्या: कुछ होने पर दूसरी service आपका URL call करती है। "हमें फ़ोन मत करो, हम आपको करेंगे।"
  • उदाहरण: WhatsApp → "नया message आया"; Razorpay → "payment हो गया"।
  • असली ज़िंदगी का उदाहरण: doorbell। आप बार-बार दरवाज़ा खोल कर नहीं देखते कि कोई आया; मेहमान bell बजाता है और आप जाते हो।
  • अच्छे webhook के rules:
    1. Signature check करो (header में एक secret code), ताकि नकली requests reject हों।
    2. 200 जल्दी लौटाओ (कुछ seconds में)। असली काम queue में डालो।
    3. Idempotent: वही webhook दो बार आ सकता है। Event id save करो; पहले देखा हुआ हो तो skip।
  • आम गलती: webhook के अंदर LLM call करना। धीमा है, भेजने वाला time out होकर दोबारा भेजता है → दो-दो जवाब।

17. Queue (और workers)

  • क्या: धीमे कामों की लाइन। API job जोड़ती है; एक अलग worker उसे background में करता है।
  • Node का tool: BullMQ (Redis इस्तेमाल करता है)।
  • असली ज़िंदगी का उदाहरण: bank का token system। Token लो और बैठ जाओ; counter खाली होने पर आपको बुलाया जाता है।
  • उदाहरण: webhook को WhatsApp message मिला → queue.add('reply', { from, text }) → 200 लौटाया → worker RAG + Claude चलाता है → जवाब भेजता है।
  • फ़ायदे: इंतज़ार के साथ retries (1s, 5s, 30s), एक साथ कितने jobs चलें इसकी सीमा, fail हुए jobs जाँच के लिए save।
  • Interview Q: Why use a queue? → User को तुरंत जवाब, धीमा काम background में, fail हुए jobs retry, और भीड़ में ज़्यादा workers जोड़ सकते हो।

18. Bulk jobs

  • क्या: बहुत सारी चीज़ों पर एक ही काम: 300 certificates, 1,000 WhatsApp messages, बड़ा Excel import।
  • असली ज़िंदगी का उदाहरण: शादी के card छापने वाला छोटे-छोटे बंडल बना कर गिनती रखता है, एक बड़ा ढेर नहीं जिसका हिसाब किसी को न पता हो।
  • कैसे:
    1. एक "batch" row बनाओ (batch_id, total, done, failed, status)।
    2. हर item का एक छोटा job queue में डालो (एक बड़ा job नहीं)।
    3. हर job गिनती update करता है। Admin page दिखाता है "300 में से 245 हो गए, 2 fail"।
    4. Fail हुए items अकेले retry हो सकते हैं।
  • आम गलती: एक API call के अंदर 1,000 items का loop → timeout, और किसी को नहीं पता कौन से पूरे हुए।

19. Cron (तय समय वाले jobs)

  • क्या: code जो समय-सारणी पर चलता है। "रोज़ सुबह 9 बजे", "हर 5 मिनट"।
  • NestJS में: @nestjs/schedule से @Cron('0 9 * * *')।
  • असली ज़िंदगी का उदाहरण: सुबह का alarm, या दूधवाला जो बिना बुलाए रोज़ 6 बजे आता है।
  • उदाहरण (reminders): हर 15 मिनट → अगले 2 घंटे में शुरू होने वाले appointments ढूँढो जिनमें reminder_sent = false → queue में reminder job डालो → reminder_sent = true करो।
  • आम गलतियाँ:
    • Server की 2 copies → cron दो बार चलता है → दो-दो messages। इलाज: lock, या cron सिर्फ़ एक server पर, या BullMQ के repeat jobs।
    • Time zones: समय UTC में save करो, IST में दिखाओ।

20. Slot locking (double booking रोकना)

  • समस्या: दो लोग एक ही second पर 11:00 वाला slot दबाते हैं। दोनों को "खाली" दिखता है। दोनों की booking हो जाती है। 😬
  • असली ज़िंदगी का उदाहरण: train की आखिरी seat पर दो लोग एक साथ बैठ जाएँ। किसे मिलेगी, यह TTE (database) तय करता है, यात्री नहीं।
  • इलाज 1 (सबसे आसान, सबसे पक्का): database में unique rule।
CREATE UNIQUE INDEX one_booking_per_slot ON bookings (doctor_id, slot_start)
WHERE status IN ('held', 'booked');

दूसरा insert fail होता है → दिखाओ "माफ़ कीजिए, यह slot अभी-अभी बुक हो गया।"

  • इलाज 2: transaction में row lock: slot की row पर SELECT ... FOR UPDATE, check करो खाली है, फिर book करो, फिर COMMIT।
  • इलाज 3: payment के दौरान hold: slot को held mark करो, hold_until = now() + 10 minutes के साथ। Payment पूरा न हो तो cron उसे खाली कर देता है।
  • Interview Q: How do you stop double booking? → Database को फ़ैसला करने दो (unique constraint या row lock), code में सिर्फ़ "check करो फिर insert करो" कभी नहीं, और user के pay करते समय छोटा hold।

21. WebSocket (real-time)

  • क्या: खुला रहने वाला connection, ताकि server तुरंत browser को updates push कर सके। Normal HTTP सिर्फ़ पूछने पर जवाब देता है।
  • उदाहरण (restaurant): customer order देता है → server तुरंत kitchen screen पर order:new भेजता है → kitchen "Preparing" mark करती है → customer के phone पर तुरंत दिखता है।
  • Tool: Socket.IO (NestJS के साथ अच्छा चलता है)। Rooms इस्तेमाल करो: हर restaurant का एक room, हर order का एक।
  • जानने लायक: connection टूटे तो दोबारा जुड़ने पर API से ताज़ा data load करो। कई servers हों तो Redis adapter।
  • Interview Q: WebSocket vs polling? → Polling हर कुछ seconds पूछता है (आसान, फ़िज़ूल)। WebSocket सिर्फ़ बदलाव पर push करता है (तेज़, पर reconnects संभालने पड़ते हैं)।

Part D: Business app topics

22. Multi-tenant SaaS

  • क्या: एक app, कई customers (हर customer = एक tenant)। जैसे एक building में कई flats; हर परिवार सिर्फ़ अपने flat में जाता है।
  • सबसे आसान तरीका: हर table में tenant_id column, और हर query उससे filter करे।
SELECT * FROM invoices WHERE tenant_id = $1 AND id = $2;
  • App को tenant कैसे पता चलता है: logged-in user के token से (या subdomain से, जैसे sharma.yourapp.in)। Browser के भेजे body वाले value से कभी नहीं।
  • Extra सुरक्षा: PostgreSQL की Row Level Security (RLS) से database खुद दूसरे tenants की rows रोक सकता है।
  • आम गलती: एक query में tenant_id भूल जाना → एक दुकान को दूसरी दुकान का data दिख जाता है। SaaS का यह सबसे बुरा bug है।
  • Interview Q: How do you keep tenant data apart? → token से tenant_id, हर query में filter (एक shared helper या RLS), tenant_id से शुरू होने वाले indexes, और ऐसे tests जो दूसरे tenant का data पढ़ने की कोशिश करें।

23. Roles और RBAC

  • क्या: RBAC = Role-Based Access Control। Users को एक role मिलता है; हर role की permissions होती हैं।
  • उदाहरण (school):
Roleक्या कर सकता है
Adminसब कुछ
Teacherअपनी classes की attendance और marks
Accountantfees और receipts
Parentसिर्फ़ अपना बच्चा देखना
  • NestJS में: @Roles('admin', 'teacher') decorator + एक guard जो token से user का role check करे।
  • Checks के दो स्तर:
    1. क्या यह role यह काम कर सकता है? (teacher marks डाल सकता है)
    2. क्या यह user यह record छू सकता है? (सिर्फ़ अपनी class / बच्चा)। लोग यही भूलते हैं।
  • असली ज़िंदगी का उदाहरण: अस्पताल का ID card। Nurse ward में जा सकती है पर दवा के store में नहीं, और सिर्फ़ अपने मरीज़ों की files देख सकती है।
  • आम गलती: सिर्फ़ frontend पर buttons छिपाना। API को भी check करना होगा।

24. Payments (India में Razorpay)

  • Flow:
    1. Backend Razorpay के साथ एक order बनाता है (amount, receipt id)।
    2. Frontend Razorpay checkout खोलता है; user UPI / card से pay करता है।
    3. Razorpay आपका webhook call करता है (payment.captured)।
    4. Backend signature check करता है, फिर order को paid mark करता है (सिर्फ़ एक बार)।
  • असली ज़िंदगी का उदाहरण: दुकानदार customer का "payment done" screenshot देख कर सामान नहीं देता; अपने phone पर bank का SMS आने का इंतज़ार करता है (verified webhook)।
  • सुनहरे rules:
    • Frontend के "payment success" पर कभी भरोसा मत करो। सिर्फ़ verified webhook या server check पर।
    • Amounts paise में (पूरे numbers) save करो, decimals में नहीं।
    • Idempotent: order पहले से paid है तो कुछ मत करो।
    • एक cron पुराने "pending" orders को Razorpay से check करे, अगर कोई webhook खो गया हो।

25. Reports और dashboards

  • क्या: मालिक के लिए numbers और charts: आज की sales, बाकी fees, attendance %, इस हफ़्ते की leads।
  • कैसे:
    • Date filters के साथ SQL GROUP BY: SELECT date(created_at), sum(amount) FROM payments WHERE tenant_id=$1 GROUP BY 1।
    • भारी reports के लिए cron हर रात (या हर घंटे) एक summary table भरता है। Dashboard छोटी table पढ़ता है, इसलिए तेज़ है।
    • Filters (date range, branch, class) और Excel/CSV export जोड़ो।
  • असली ज़िंदगी का उदाहरण: दुकानदार रात को दिन का हिसाब जोड़ कर एक line लिख लेता है, ताकि महीने के अंत में हर bill दोबारा न जोड़ना पड़े (summary table)।
  • आम गलती: busy समय में main database पर बड़ी reports चलाना। Summary table या read replica इस्तेमाल करो।

26. Admin panel

  • क्या: मालिक का control room: orders, menu, users, settings देखना और बदलना।
  • ज़रूरी: login + roles, search, filter, sort और pagination वाली tables, validation के साथ add/edit forms, और बदलावों के audit logs।
  • Tip: इसे एक बार reusable kit (table + form + filters) की तरह बनाओ। हर client project में इस्तेमाल करके समय बचाओ।

27. WhatsApp Business API

  • क्या: किसी business के लिए code से WhatsApp messages भेजने और लेने का official तरीका (Meta की Cloud API, सीधे या Gupshup, Interakt, AiSensy जैसे provider से)।
  • लेना: हर नए message पर Meta आपका webhook call करता है।
  • भेजना: आपका server phone number और message के साथ Meta की API call करता है।
  • 24 घंटे का rule: customer के message के बाद 24 घंटे तक आप खुल कर जवाब दे सकते हो। उसके बाद सिर्फ़ approved template भेज सकते हो।
  • Cost: Meta कुछ तरह के messages (जैसे marketing templates) का पैसा लेता है। Client को quote देने से पहले ताज़ा price list देखो।
  • आम गलती: normal number पर unofficial WhatsApp bot → number ban हो जाता है।

28. WhatsApp templates

  • क्या: खाली जगहों वाले पहले से approved message formats, उन messages के लिए जो आप शुरू करते हो (reminders, offers, follow-ups)।
  • उदाहरण: Hi {{1}}, your appointment at {{2}} is on {{3}}. Reply YES to confirm.
  • असली ज़िंदगी का उदाहरण: शादी का छपा हुआ card: format पहले से तय, सिर्फ़ नाम और तारीख भरनी है।
  • प्रकार: Utility (reminders, order updates) और Marketing (offers)। Marketing आमतौर पर महँगा है और user की opt-in चाहिए।
  • Tips: छोटे और काम के रखो, opt-out जोड़ो ("Reply STOP"), और इस्तेमाल से पहले Meta की approval का इंतज़ार करो।

29. Analytics (messages और campaigns के लिए)

  • क्या: नापना कि क्या हुआ: भेजा, पहुँचा, पढ़ा, जवाब आया, customer बना।
  • कैसे: WhatsApp status webhooks भेजता है (sent → delivered → read)। हर एक को message_events table में save करो। फिर दिन / campaign के हिसाब से गिनो।
SELECT campaign_id,
  count(*) FILTER (WHERE status='sent')      AS sent,
  count(*) FILTER (WHERE status='read')      AS read,
  count(*) FILTER (WHERE status='replied')   AS replied
FROM message_events WHERE tenant_id=$1 GROUP BY campaign_id;
  • मालिक को आसान numbers दिखाओ: "500 भेजे, 410 पढ़े, 38 ने जवाब दिया, 9 ने book किया"। यही उन्हें दोबारा pay करवाता है।

30. QR verification

  • क्या: certificate (या ticket, invoice) पर एक QR code जो ऐसा page खोलता है जो बताए "यह असली है"।
  • असली ज़िंदगी का उदाहरण: दवा के पत्ते या LIC policy पर code: scan करो और company की site बताती है कि असली है या नकली।
  • कैसे:
    1. हर certificate को एक unique ID दो। बेहतर: ऐसा random code जिसका अंदाज़ा न लगे (KOD-7F3K-92QX), सिर्फ़ 0001, 0002 नहीं।
    2. QR में एक link होता है: yoursite.in/verify?id=KOD-7F3K-92QX।
    3. Verify page database में ID ढूँढता है और नाम, course, dates दिखाता है, या "नहीं मिला"।
  • Extra: certificate रद्द (revoke) करने की सुविधा, और हर जाँच का log।
  • आम गलती: सारी details QR के अंदर ही डाल देना। ऐसे तो कोई भी नकली QR बना लेगा। QR को आपकी website पर ले जाना चाहिए।

31. PDF generation

  • क्या: code से PDFs बनाना: certificates, invoices, salary slips, reports।
  • दो आसान तरीके:
    • Puppeteer से HTML → PDF (headless Chrome): HTML/CSS में design करो, फिर page.pdf()। सुंदर design के लिए सबसे आसान।
    • pdfkit / pdf-lib: code से text और shapes बनाओ। हल्का, पर design करना मुश्किल।
  • Tips: PDFs queue worker में बनाओ, API call में नहीं। S3 पर save करके link भेजो। Fonts embed करो (Hindi के लिए Devanagari font चाहिए)।
  • आम गलती: हर PDF के लिए नया Chrome शुरू करना। एक बार शुरू करो और कई pages के लिए दोबारा इस्तेमाल करो। (हर photocopy के लिए नई machine नहीं खरीदते।)
