Message queues and async workMessage queues और async काम

In one line: A queue lets the API reply fast while workers do slow work in the background, with retries, and it absorbs sudden spikes.

एक लाइन में: Queue से API तुरंत जवाब देती है जबकि workers धीमा काम background में retry के साथ करते हैं, और अचानक की भीड़ queue सँभाल लेती है।

Why use a queue?Queue क्यों इस्तेमाल करें?

Beginnerशुरुआती

Think of a busy restaurant. The counter takes your order, gives you a token and serves the next customer. The kitchen cooks orders one by one. The counter never stands at the stove waiting. A message queue is that token system for software.

एक भीड़ वाले restaurant के बारे में सोचिए। Counter आपका order लेकर token देता है और अगले customer को serve करता है। Kitchen एक-एक करके orders पकाती है। Counter कभी चूल्हे के पास खड़ा इंतज़ार नहीं करता। Message queue software के लिए वही token system है।

Queue simulatorQueue simulator

A tiny queue in plain Node.js. The API replies at once, and two workers share the jobs:

Simple Node.js में एक छोटी queue। API तुरंत जवाब देती है, और दो workers jobs बाँट लेते हैं:

// A tiny job queue: the API adds jobs and replies at once; workers do the slow work.
const queue = [];
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

function placeOrder(id) {
  queue.push({ id, task: "send invoice email" });
  console.log(`API: order ${id} saved, replied to user in a few ms`);
}

async function worker(name, msPerJob) {
  while (queue.length > 0) {
    const job = queue.shift();       // take the oldest job
    await sleep(msPerJob);           // pretend the email takes time
    console.log(`${name}: done "${job.task}" for order ${job.id}`);
  }
}

[101, 102, 103, 104].forEach(placeOrder);
await Promise.all([worker("worker-1", 300), worker("worker-2", 200)]);

In production, the queue lives outside your app (in Redis, RabbitMQ, SQS or Kafka), so jobs survive restarts and many servers can share them.

Production में queue आपकी app के बाहर रहती है (Redis, RabbitMQ, SQS या Kafka में), ताकि restart होने पर jobs बचे रहें और कई servers उन्हें बाँट सकें।

Simple rule: a job queue is "do this task once" (send this email). An event stream is "this happened" (order placed), and any number of services can react to it: billing, inventory, analytics.

आसान नियम: job queue मतलब "यह काम एक बार करो" (यह email भेजो)। Event stream मतलब "यह हुआ" (order हुआ), और कितनी भी services उस पर react कर सकती हैं: billing, inventory, analytics।

When jobs failजब jobs fail हों

Senior levelSenior level
  • Retry with backoff: try again after 2s, 4s, 8s, because many failures are temporary.Backoff के साथ retry: 2s, 4s, 8s बाद फिर कोशिश, क्योंकि कई failures थोड़ी देर की होती हैं।
  • Dead letter queue (DLQ): after the last retry, park the job in a separate queue, alert someone, and fix it later instead of retrying forever.Dead letter queue (DLQ): आख़िरी retry के बाद job को अलग queue में रखिए, किसी को alert कीजिए, और हमेशा retry करने की जगह बाद में ठीक कीजिए।
  • At-least-once delivery: most queues may deliver a job twice (for example, after a worker crash). Make every job safe to run twice. See idempotency.At-least-once delivery: ज़्यादातर queues कभी job दो बार दे सकती हैं (जैसे worker crash के बाद)। हर job को दो बार चलने लायक़ सुरक्षित बनाइए। देखिए idempotency।
  • Watch the queue length: a queue that keeps growing means you need more workers or faster jobs.Queue की लंबाई पर नज़र: लगातार बढ़ती queue का मतलब है ज़्यादा workers या तेज़ jobs चाहिए।

🎤 "I'd return 202 Accepted with a job id, push the work to a queue, process it with workers that retry with backoff, send repeated failures to a dead letter queue, and make the job idempotent because delivery is at least once."

🎤 "I'd return 202 Accepted with a job id, push the work to a queue, process it with workers that retry with backoff, send repeated failures to a dead letter queue, and make the job idempotent because delivery is at least once."

📌 Remember these 3 thingsये 3 बातें याद रखिए
  1. Producer → queue → workers. The API returns fast (often 202 Accepted).Producer → queue → workers। API जल्दी लौटती है (अक्सर 202 Accepted)।
  2. If jobs arrive faster than workers finish, the queue grows: add workers.Jobs workers से तेज़ आएँ तो queue बढ़ती है: workers बढ़ाइए।
  3. Retry with backoff, then a dead letter queue. Jobs must be safe to run twice.Backoff के साथ retry, फिर dead letter queue। Jobs दो बार चलने पर भी सुरक्षित हों।

Practiceप्रैक्टिस

Exercise 1: On result day, 2 lakh students must get an SMS. Your SMS provider allows 100 SMS per second. How do you design it?Exercise 1: Result वाले दिन 2 लाख students को SMS जाना है। आपका SMS provider 100 SMS प्रति second देता है। आप इसे कैसे design करेंगे?

Show a sample answerएक sample जवाब देखें

Add 2 lakh jobs to a queue in batches. Run workers with a rate limit of 100 per second (about 33 minutes in total). Retry failures with backoff, send repeated failures to a DLQ, and use an idempotency key per student so nobody gets two SMS. Keep OTP messages in a separate, higher-priority queue so logins still work during the rush.

2 लाख jobs batches में queue में डालिए। Workers को 100 प्रति second की limit के साथ चलाइए (कुल लगभग 33 minute)। Failures को backoff के साथ retry कीजिए, बार-बार fail होने वालों को DLQ में भेजिए, और हर student के लिए idempotency key रखिए ताकि किसी को दो SMS न जाएँ। OTP messages को अलग, ज़्यादा priority वाली queue में रखिए ताकि भीड़ में भी login चलते रहें।
