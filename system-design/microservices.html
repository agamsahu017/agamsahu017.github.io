Microservices, simplyMicroservices, आसान भाषा में

⏱️ 25 min read + practice25 मिनट पढ़ाई + प्रैक्टिस🏗️ HLD + LLD🎯 Interview focusedइंटरव्यू के हिसाब से

In one line: Microservices split one app into independently deployed services that own their data. They help big teams and uneven load, but cost complexity, so start with a modular monolith.

एक लाइन में: Microservices एक app को अलग-अलग deploy होने वाली services में बाँटते हैं जो अपना data रखती हैं। ये बड़ी teams और असमान load में मदद करते हैं, पर जटिलता बढ़ाते हैं, इसलिए modular monolith से शुरू कीजिए।

Monolith vs microservicesMonolith vs microservices

Beginnerशुरुआती

A monolith is like a small dhaba where one kitchen makes everything. A microservices system is like a food court: separate counters for dosa, chaat and juice, each with its own staff and stock, working together.

Monolith एक छोटे ढाबे जैसा है जहाँ एक ही रसोई सब बनाती है। Microservices system एक food court जैसा है: dosa, chaat और juice के अलग counters, हर एक का अपना staff और सामान, जो साथ मिलकर काम करते हैं।

Start with a modular monolith: one app with clean modules (NestJS modules are perfect for this). Split out a service only when a team or a heavy feature truly needs to deploy or scale on its own.

Modular monolith से शुरू कीजिए: साफ़ modules वाली एक app (NestJS modules इसके लिए बढ़िया हैं)। कोई service तभी अलग कीजिए जब किसी team या भारी feature को सच में अलग deploy या scale करना हो।

Transactions across services: the saga patternServices के बीच transactions: saga pattern

Senior levelSenior level

In a monolith, one database transaction can reserve stock and charge the card together. Across services there is no single transaction. A saga does each step in its own service, and if a later step fails, it runs compensating steps to undo the earlier ones, like releasing reserved stock.

Monolith में एक database transaction stock reserve और card charge साथ में कर सकता है। Services के पार कोई एक transaction नहीं होता। Saga हर step अपनी service में करता है, और अगर बाद का step fail हो, तो पहले वाले steps को undo करने के लिए compensating steps चलाता है, जैसे reserve किया stock छोड़ना।

// Saga: each service does its own step; if a later step fails, earlier steps are undone.
const log = (m) => console.log(m);
const services = {
  reserveStock: () => log("Inventory: 1 phone reserved"),
  releaseStock: () => log("Inventory: reservation released (compensation)"),
  chargeCard: (ok) => { if (!ok) throw new Error("card declined"); log("Payment: ₹15,000 charged"); },
  createShipment: () => log("Shipping: shipment created"),
};

function placeOrder(cardOk) {
  log(`--- order (card ok: ${cardOk}) ---`);
  services.reserveStock();
  try {
    services.chargeCard(cardOk);
  } catch (e) {
    log(`Payment failed: ${e.message}`);
    services.releaseStock(); // undo the earlier step
    return "ORDER CANCELLED";
  }
  services.createShipment();
  return "ORDER CONFIRMED";
}

log(placeOrder(true));
log(placeOrder(false));

Real output:

असली output:

--- order (card ok: true) ---
Inventory: 1 phone reserved
Payment: ₹15,000 charged
Shipping: shipment created
ORDER CONFIRMED
--- order (card ok: false) ---
Inventory: 1 phone reserved
Payment failed: card declined
Inventory: reservation released (compensation)
ORDER CANCELLED

In real systems each step is a separate service, steps talk through events or calls, and every step is idempotent because messages can arrive twice. To publish an event reliably together with a database change, use the outbox pattern: save the event in the same database transaction, and a separate process sends it.

असली systems में हर step अलग service है, steps events या calls से बात करते हैं, और हर step idempotent होता है क्योंकि messages दो बार आ सकते हैं। Database change के साथ भरोसे से event publish करने के लिए outbox pattern इस्तेमाल कीजिए: event को उसी database transaction में save कीजिए, और एक अलग process उसे भेजता है।

To move away from a monolith safely, use the strangler pattern: put a gateway in front, move one feature at a time to a new service, route its traffic there, and slowly "strangle" the old code. Never a big-bang rewrite.

Monolith से सुरक्षित तरीक़े से हटने के लिए strangler pattern इस्तेमाल कीजिए: आगे एक gateway रखिए, एक-एक feature नई service में ले जाइए, उसका traffic वहाँ भेजिए, और धीरे-धीरे पुराने code को "strangle" कीजिए। कभी एक झटके में पूरा rewrite नहीं।

⚠️ Common mistakesआम ग़लतियाँ
  • Services sharing one database. Then they are not independent, just a distributed monolith.Services का एक ही database share करना। फिर वो स्वतंत्र नहीं, बस एक बँटा हुआ monolith हैं।
  • Long chains of sync calls (A calls B calls C calls D). One slow service slows everything.Sync calls की लंबी chains (A, B को; B, C को; C, D को call करे)। एक धीमी service सबको धीमा कर देती है।
  • No request id or tracing, so nobody can find where a request failed.न request id न tracing, इसलिए कोई नहीं ढूँढ पाता कि request कहाँ fail हुई।
📌 Remember these 4 thingsये 4 बातें याद रखिए
  1. Modular monolith first; split only for team independence or very different load.पहले modular monolith; सिर्फ़ team की आज़ादी या बहुत अलग load के लिए अलग कीजिए।
  2. Each service owns its database. Talk through APIs or events.हर service का अपना database। APIs या events से बात।
  3. Cross-service transactions use a saga with compensating steps.Services के पार transactions के लिए compensating steps वाला saga।
  4. Strangler pattern for migration; never a big-bang rewrite.Migration के लिए strangler pattern; कभी एक झटके में rewrite नहीं।

Practiceप्रैक्टिस

Exercise 1: An e-commerce monolith in NCR has 4 developers. The CTO wants 12 microservices. What do you advise?Exercise 1: NCR की एक e-commerce monolith पर 4 developers हैं। CTO 12 microservices चाहते हैं। आप क्या सलाह देंगे?

Show a sample answerएक sample जवाब देखें

With 4 developers, 12 services means more deploys, networks and dashboards than people to look after them. Better: clean up the monolith into clear modules (orders, payments, catalog, users), add a queue for slow work, and split out one service only where there's a real reason, such as heavy report generation. Revisit when the team grows.

4 developers के लिए 12 services का मतलब है देखभाल करने वालों से ज़्यादा deploys, networks और dashboards। बेहतर: monolith को साफ़ modules (orders, payments, catalog, users) में बाँटिए, धीमे काम के लिए queue जोड़िए, और सिर्फ़ वहाँ service अलग कीजिए जहाँ असली वजह हो, जैसे भारी report generation। Team बढ़ने पर फिर सोचिए।
