Load balancer: the traffic policeLoad balancer: traffic police

A load balancer sits in front of your servers and decides which server gets each request. Think of the token counter in a hospital sending each patient to a free doctor.

Load balancer आपके servers के आगे बैठता है और तय करता है कि हर request किस server को मिले। Hospital के token counter की तरह सोचिए जो हर मरीज़ को ख़ाली doctor के पास भेजता है।

Click "Send 1 request"."1 request भेजें" पर क्लिक कीजिए।

Health checks: the load balancer pings each server every few seconds. If a server stops answering, traffic goes only to healthy servers. Users don't notice.

Health checks: Load balancer हर कुछ seconds में हर server को ping करता है। कोई server जवाब देना बंद करे, तो traffic सिर्फ़ ठीक servers पर जाता है। Users को पता भी नहीं चलता।

Stateless serversStateless servers

Senior levelSenior level

If Server 1 stores a user's login session in its own memory, the next request may go to Server 2, which doesn't know the user. The user gets logged out.

अगर Server 1 user का login session अपनी memory में रखे, तो अगली request Server 2 पर जा सकती है, जो user को नहीं जानता। User logout हो जाता है।

Fix: keep servers stateless. Store sessions in a shared place like Redis, or use a signed token like a JWT that the client sends every time. Then any server can handle any request, and you can add or remove servers freely.

हल: Servers को stateless रखिए। Sessions किसी shared जगह जैसे Redis में रखिए, या JWT जैसा signed token इस्तेमाल कीजिए जो client हर बार भेजे। फिर कोई भी server कोई भी request संभाल सकता है, और आप servers आराम से जोड़-घटा सकते हैं।

Single point of failure (SPOF)Single point of failure (SPOF)

Any part with only one copy can take the whole system down: one load balancer, one database. Seniors are expected to spot these and add redundancy: two load balancers, database replicas, servers in more than one data centre (availability zone).

जिस हिस्से की सिर्फ़ एक copy हो, वो पूरा system गिरा सकता है: एक load balancer, एक database। Seniors से उम्मीद होती है कि वो इन्हें पहचानें और redundancy जोड़ें: दो load balancers, database replicas, एक से ज़्यादा data centre (availability zone) में servers।

⚠️ Common mistakesआम ग़लतियाँ
  • Storing sessions or uploaded files on the app server's disk.Sessions या uploaded files को app server की disk पर रखना।
  • Adding servers but keeping a single database that becomes the bottleneck.Servers बढ़ाना पर एक ही database रखना जो bottleneck बन जाए।
  • Forgetting that the load balancer itself can fail.यह भूल जाना कि load balancer ख़ुद भी fail हो सकता है।
  • Saying "microservices" when scaling one well-built service would be enough.जब एक अच्छी service को scale करना काफ़ी हो, तब "microservices" बोलना।

Practiceप्रैक्टिस

Exercise 1: A coaching institute's result website crashes every year on result day (50× normal traffic for a few hours). How would you fix it cheaply?Exercise 1: एक coaching institute की result website हर साल result वाले दिन crash हो जाती है (कुछ घंटों के लिए 50 गुना traffic)। इसे सस्ते में कैसे ठीक करेंगे?

Show a sample answerएक sample जवाब देखें
  • Results don't change once published, so cache them heavily, or even generate static result pages and serve them from a CDN.Results publish होने के बाद बदलते नहीं, इसलिए उन्हें ज़ोरदार तरीक़े से cache कीजिए, या static result pages बनाकर CDN से serve कीजिए।
  • Put the app behind a load balancer with auto-scaling: add servers for the result day, remove them after.App को load balancer और auto-scaling के पीछे रखिए: result वाले दिन servers जोड़िए, बाद में हटा दीजिए।
  • Keep servers stateless so new servers can help immediately.Servers stateless रखिए ताकि नए servers तुरंत मदद कर सकें।
  • Use a read replica so result lookups don't overload the main database.Read replica रखिए ताकि result ढूँढने से main database पर बोझ न पड़े।
