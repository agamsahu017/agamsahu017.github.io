Queries and cachingQueries and caching

Q1

Why use React Query instead of useEffect + useState for API calls?

3–5 yrs🔥 Very common
Show answer

With useEffect you write loading, error, cancellation, retries and caching yourself, in every component. React Query gives all of that out of the box:

  • caching: the same data isn't fetched twice,
  • request de-duplication: 5 components asking for the same key make 1 call,
  • background refetch when data is stale (on window focus or reconnect),
  • retries, pagination, and mutations with cache updates,
  • no race conditions.

It treats API data as server state: a cache of data that lives on the server, not app state you own.

🗣️ Say it in one line: It gives caching, de-duplication, retries and background refetching, so I don't hand-write loading logic in every component.

Q2

What is a queryKey and how should you design it?

3–5 yrs🔥 Very common
Show answer

The queryKey is the cache id of the data. Same key = same cached data. If any part of the key changes, it is a different query, and it fetches.

Put everything the query depends on into the key: ["employees", { page, search, status }]. Then changing the page fetches the new page automatically.

Keep keys in one place (a key factory), so invalidation is easy and has no typos.

export const employeeKeys = {
  all: ["employees"],
  list: (filters) => ["employees", "list", filters],
  detail: (id) => ["employees", "detail", id],
};

const { data, isPending, isError } = useQuery({
  queryKey: employeeKeys.list({ page, search }),
  queryFn: () => api.getEmployees({ page, search }),
});

🗣️ Say it in one line: The key is the cache id, so it must include every input of the query; I keep keys in a factory.

Q3

staleTime vs gcTime: what is the difference?

3–5 yrs🔥 Very common
Show answer
  • staleTime: how long data is treated as fresh. While fresh, React Query doesn't refetch. The default is 0, so data is stale immediately and refetches on mount, focus or reconnect.
  • gcTime (called cacheTime before v5): how long unused data stays in memory after the last component using it unmounts. The default is 5 minutes.

For master data like the list of states or departments, set a long staleTime (like 30 minutes). For live data like an approval queue, keep it short.

💡 Easy example: staleTime is the 'best before' time on milk: within it, you drink it without checking. gcTime is how long the empty milk packet stays in the kitchen before it goes in the bin.

🗣️ Say it in one line: staleTime decides when to refetch; gcTime decides when unused cache is deleted.

Q4

In v5, what is the difference between isPending, isLoading and isFetching?

5–8 yrs
Show answer
  • isPending: there is no data yet (status is pending). Show a skeleton.
  • isFetching: a request is running right now, including background refetches. Show a small spinner.
  • isLoading: isPending && isFetching, meaning the very first load is happening.

In v5 the old loading status was renamed to pending. Other v5 changes: only the object syntax useQuery({ queryKey, queryFn }) is allowed, cacheTime became gcTime, keepPreviousData became placeholderData: keepPreviousData, and onSuccess/onError were removed from useQuery (they still exist on mutations).

🗣️ Say it in one line: isPending means no data yet, isFetching means a request is in flight, isLoading is both together.

Q5

How do you build pagination and infinite scroll with React Query?

5–8 yrs
Show answer

Pagination: put page in the key and use placeholderData: keepPreviousData, so the old page stays visible while the next one loads, instead of the table flashing empty.

Infinite scroll: useInfiniteQuery with initialPageParam (required in v5) and getNextPageParam. Call fetchNextPage() when the user reaches the bottom (an IntersectionObserver).

const list = useQuery({
  queryKey: ["orders", page],
  queryFn: () => api.orders(page),
  placeholderData: keepPreviousData,
});

const feed = useInfiniteQuery({
  queryKey: ["feed"],
  queryFn: ({ pageParam }) => api.feed(pageParam),
  initialPageParam: 1,
  getNextPageParam: (lastPage) => lastPage.nextPage ?? undefined, // undefined = no more pages
});

🗣️ Say it in one line: Page in the key plus keepPreviousData for tables; useInfiniteQuery with getNextPageParam for feeds.

Mutations and cache updatesMutations and cache updates

Q6

How do you update the list after creating or editing something?

3–5 yrs🔥 Very common
Show answer

Use useMutation, and in onSuccess invalidate the related queries. Invalidation marks them stale and refetches the ones on screen.

If the API returns the updated object, you can also put it straight into the cache with setQueryData and skip one network call.

const queryClient = useQueryClient();
const approve = useMutation({
  mutationFn: (id) => api.approveLeave(id),
  onSuccess: () => {
    queryClient.invalidateQueries({ queryKey: ["leaves"] }); // every query starting with "leaves"
  },
});

<button disabled={approve.isPending} onClick={() => approve.mutate(leave.id)}>Approve</button>

🗣️ Say it in one line: useMutation, then invalidateQueries on success so the lists refetch; setQueryData when the API returns the new object.

Q7

How do you do an optimistic update with rollback?

5–8 yrs🔥 Very common
Show answer

Update the screen before the server replies, and undo it if the request fails:

  • onMutate: cancel running fetches for that key, save a snapshot of the old data, write the new data with setQueryData, and return the snapshot.
  • onError: put the snapshot back.
  • onSettled: invalidate, to sync with the real server data.
useMutation({
  mutationFn: api.toggleDone,
  onMutate: async (id) => {
    await queryClient.cancelQueries({ queryKey: ["todos"] });
    const previous = queryClient.getQueryData(["todos"]);
    queryClient.setQueryData(["todos"], (old) =>
      old.map((t) => (t.id === id ? { ...t, done: !t.done } : t)));
    return { previous }; // passed to onError
  },
  onError: (err, id, snapshot) => queryClient.setQueryData(["todos"], snapshot.previous),
  onSettled: () => queryClient.invalidateQueries({ queryKey: ["todos"] }),
});

🗣️ Say it in one line: Snapshot in onMutate, write the new value, roll back in onError, invalidate in onSettled.

Q8

How do you set up global error handling and retries?

5–8 yrs
Show answer

Set defaults on the QueryClient: a sensible staleTime, and a retry function that doesn't retry 4xx errors (a 403 won't fix itself) but retries network and 5xx errors up to 2–3 times.

For global error toasts, use a QueryCache / MutationCache with an onError callback, since onError was removed from useQuery in v5. Show page-level errors with an error boundary or the isError state.

const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 30_000,
      retry: (count, error) => error?.status >= 500 && count < 2,
    },
  },
  queryCache: new QueryCache({ onError: (error) => toast.error(error.message) }),
});

🗣️ Say it in one line: Defaults on the QueryClient: no retries on 4xx, a few on 5xx, and a QueryCache onError for toasts.

Practiceप्रैक्टिस

Answer these as if you are explaining your current project.

Mock task 1: A dropdown of 36 states is fetched on every page. Fix it.

Show a sample answer

Use one shared useStates() hook with queryKey: ["master", "states"] and a long staleTime (for example 1 hour) and gcTime. Every component reads the same cache, so there is one network call per hour. You can also prefetch it after login.

Mock task 2: After approving a leave, the count badge in the header doesn't update. Why?

Show a sample answer

The badge uses a different query key (for example ["leave-count"]) that wasn't invalidated. Either invalidate both keys in onSuccess, or design keys hierarchically (["leaves", "count"] and ["leaves", "list", ...]) so invalidateQueries({ queryKey: ["leaves"] }) covers both.
