App Router and componentsApp Router and components

Q1

What is the difference between a Server Component and a Client Component?

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: Server Components run on the server and send no JavaScript. Client Components run in the browser and need "use client" for state, clicks and browser APIs.

In the App Router, every component is a Server Component by default. It runs only on the server, sends no JavaScript to the browser, and can read a database or use secrets directly.

A Client Component runs in the browser. You opt in by writing "use client" at the top of the file. You need it for hooks (useState, useEffect), event handlers (onClick), and browser APIs (window, localStorage).

The rule of thumb: keep most of the tree as Server Components for speed, and make only the small interactive leaves Client Components.

💡 Easy example: Think of Server Components as the printed page sent from the server, and Client Components as the buttons and form fields you can actually press and type into.

// app/page.tsx  — Server Component (default)
async function Page() {
  const posts = await db.posts.findMany(); // runs on the server
  return <PostList posts={posts} />;
}

// app/like-button.tsx
"use client";                              // opt in to the browser
import { useState } from "react";
export function LikeButton() {
  const [liked, setLiked] = useState(false);
  return <button onClick={() => setLiked(!liked)}>{liked ? "♥" : "♡"}</button>;
}

🗣️ Say it in one line: Server Components run on the server and send no JS; Client Components run in the browser and need "use client" for state and events.

↪️ Follow-up: Can a Server Component import a Client Component? Yes. A Server Component can render a Client Component. The other way is limited: a Client Component cannot import a Server Component, but it can receive one as a children prop.

Q2

Can a Client Component contain a Server Component?

5–8 yrs
Show answer

🟢 In simple words: You can't import a server component into client code, but you can pass one in as children — like sliding a printed photo into a frame.

Not by importing it. A Client Component cannot import a Server Component, because the client bundle has no way to run server code.

But you can pass a Server Component into a Client Component as a prop, usually children. Next renders the Server Component on the server and hands the finished result to the Client Component as a slot.

This pattern lets you wrap server content inside a client layout, like a client-side theme provider around server-rendered pages.

💡 Easy example: The client component is a picture frame. You can slide an already-printed photo (server content) into the frame, but the frame cannot print the photo itself.

// client-shell.tsx
"use client";
export function ClientShell({ children }) {
  // state, context, etc. live here
  return <div className="shell">{children}</div>;
}

// page.tsx (server)
export default function Page() {
  return (
    <ClientShell>
      <ServerContent />   {/* rendered on the server, passed as children */}
    </ClientShell>
  );
}

🗣️ Say it in one line: Pass a Server Component as children to a Client Component; you cannot import one into client code.

↪️ Follow-up: Why is this useful? It keeps big data-heavy parts on the server while still using a client-only wrapper like a provider or an animation layout.

Q3

What is the App Router, and how do layout.tsx and page.tsx differ?

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: Folders are routes. page.tsx is the page; layout.tsx is the shared frame around it that stays put when you navigate.

The App Router is Next.js's routing system based on folders inside the app/ directory. A folder is a route, and special files give it behaviour.

  • page.tsx is the unique UI for that route (the actual page).
  • layout.tsx is shared UI that wraps a page and all routes below it (header, sidebar). It keeps its state on navigation and does not re-render.
  • Other special files: loading.tsx (instant loading UI), error.tsx (error boundary), not-found.tsx, and route.ts (an API endpoint).

💡 Easy example: A layout is the fixed frame of a shop — the signboard and shelves. The page is the product on display that changes as you walk from aisle to aisle.

app/
  layout.tsx        // root layout: <html> and <body>, shared header
  page.tsx          // home page "/"
  dashboard/
    layout.tsx      // wraps everything under /dashboard
    page.tsx        // "/dashboard"
    settings/
      page.tsx      // "/dashboard/settings"

🗣️ Say it in one line: Folders are routes; page.tsx is the page, layout.tsx is shared UI that persists across navigation.

↪️ Follow-up: Does a layout re-render when you move between its child pages? No. The layout stays mounted and keeps its state; only the page part swaps. That is why layouts are great for nav bars and providers.

Q4

What are the benefits of Server Components?

3–5 yrs
Show answer

🟢 In simple words: Server Components mean less JavaScript, direct data access and safe secrets — but no state or clicks.

  • Smaller bundle: their code never ships to the browser, so less JavaScript to download and run.
  • Direct data access: you can await a database or an API inside the component, with no extra endpoint.
  • Secrets stay safe: API keys used in a Server Component never reach the browser.
  • Faster first paint: the HTML comes ready from the server.

The trade-off is that Server Components cannot use state, effects or event handlers, so anything interactive must be a Client Component.

💡 Easy example: It is like getting food cooked in the kitchen and served ready, instead of being handed raw ingredients to cook at your table.

🗣️ Say it in one line: Less JavaScript, direct and safe data access, and a faster first paint — at the cost of no interactivity.

↪️ Follow-up: When should you still reach for a Client Component? Whenever you need useState/useEffect, event handlers, or browser-only APIs.

Q5

Explain SSR, SSG, ISR and CSR. How do you choose?

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: SSG = built once, SSR = built every request, ISR = static but refreshed on a timer, CSR = filled in by the browser. Pick by freshness and how personal the data is.

  • SSG (Static Site Generation): the page is built once at build time. Fast and cheap. Good for blogs and marketing pages.
  • SSR (Server-Side Rendering): the page is built on every request. Good for personalised or always-fresh pages.
  • ISR (Incremental Static Regeneration): static, but refreshed in the background after a set time. You get SSG speed with data that updates.
  • CSR (Client-Side Rendering): the browser fetches data after load. Good for private dashboards behind a login.

Choose by two questions: how often does the data change, and how personal is it? Rarely + public → SSG/ISR. Every request + personal → SSR. Behind auth and very interactive → CSR.

💡 Easy example: SSG is a printed newspaper, SSR is a fresh print for each reader, ISR is a newspaper reprinted every hour, and CSR is a blank page that fills in once you log in.

// ISR in the App Router: revalidate this data every 60 seconds
export const revalidate = 60;

async function Page() {
  const data = await fetch("https://api.example.com/prices", {
    next: { revalidate: 60 },
  }).then((r) => r.json());
  return <Prices data={data} />;
}

🗣️ Say it in one line: SSG builds once, SSR builds per request, ISR refreshes static pages on a timer, CSR fetches in the browser — pick by freshness and how personal the data is.

↪️ Follow-up: How do you force a page to always be dynamic (SSR)? Use cache: "no-store" on the fetch, or export const dynamic = "force-dynamic".

Q6

How does caching and revalidation work in the App Router?

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: Next caches data to stay fast. Control it with revalidate (timer), no-store (always fresh), or revalidateTag/revalidatePath (clear now).

Next caches data and rendered output to stay fast, and you control how fresh it is:

  • Time-based: fetch(url, { next: { revalidate: 60 } }) re-fetches at most once a minute. Or set export const revalidate = 60 for the whole route.
  • No cache: fetch(url, { cache: "no-store" }) always fetches fresh (dynamic).
  • On-demand: after a change, call revalidatePath("/blog") or revalidateTag("posts") to clear the cache immediately.

Tagging is the cleanest for mutations: tag a fetch with { next: { tags: ["posts"] } }, then revalidateTag("posts") after you add a post.

💡 Easy example: Revalidate is like a 'best before' time on cached data. On-demand revalidation is throwing out the old stock the moment new stock arrives.

// read, tagged
const posts = await fetch(url, { next: { tags: ["posts"] } }).then(r => r.json());

// after creating a post (Server Action or route handler)
import { revalidateTag } from "next/cache";
await db.posts.create({ data });
revalidateTag("posts"); // the list refreshes on the next visit

🗣️ Say it in one line: Cache by time with revalidate, skip with no-store, and clear on demand with revalidatePath or revalidateTag after a change.

↪️ Follow-up: Why prefer tags over paths? A tag can cover many pages that use the same data, so one revalidateTag refreshes all of them.

Q7

What are Server Actions? When would you use one?

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: A Server Action is a "use server" function you call straight from a form to save data — no separate API route needed.

A Server Action is a function marked "use server" that runs on the server and can be called straight from a form or a client event, without writing a separate API route.

Use them for mutations: creating, updating or deleting data. They receive the form data, do the work on the server (database write, validation), and can then revalidatePath or redirect.

Benefits: less boilerplate, data stays on the server, and forms work even before JavaScript loads (progressive enhancement).

💡 Easy example: Instead of mailing a request to a separate office (an API route) and waiting for a reply, you hand the form directly to the clerk standing behind the counter.

// app/todos/actions.ts
"use server";
import { revalidatePath } from "next/cache";

export async function addTodo(formData: FormData) {
  const title = String(formData.get("title"));
  await db.todo.create({ data: { title } });
  revalidatePath("/todos");
}

// app/todos/page.tsx
import { addTodo } from "./actions";
export default function Page() {
  return (
    <form action={addTodo}>
      <input name="title" />
      <button>Add</button>
    </form>
  );
}

🗣️ Say it in one line: A Server Action is a "use server" function you call from a form or event to mutate data without a separate API route.

↪️ Follow-up: How do you show a pending state while it runs? Use the useFormStatus hook in a client component, or useTransition around the call.

Q8

What is a route handler, and how is it different from a Server Action?

5–8 yrs
Show answer

🟢 In simple words: Route handlers are public API endpoints for outside callers; Server Actions are for your own UI's saves.

A route handler is a file route.ts that exports HTTP methods (GET, POST, …) and gives you a real API endpoint, like /api/users. It returns a Response.

Use a route handler when something outside your own UI needs the endpoint: a webhook, a mobile app, a third-party service, or a public API.

Use a Server Action when your own Next.js form or component triggers a mutation. For internal form submits, Server Actions are less code; for external callers, route handlers are the right tool.

💡 Easy example: A Server Action is an internal office memo. A route handler is a public reception desk that anyone outside can walk up to.

// app/api/users/route.ts
export async function GET() {
  const users = await db.user.findMany();
  return Response.json(users);
}
export async function POST(req: Request) {
  const body = await req.json();
  const user = await db.user.create({ data: body });
  return Response.json(user, { status: 201 });
}

🗣️ Say it in one line: Route handlers are real HTTP endpoints for external callers; Server Actions are for your own UI's mutations.

↪️ Follow-up: Can you still use route handlers for your own frontend? Yes, but for internal mutations Server Actions are usually simpler and need no fetch call.

Q9

How do loading and error states work in the App Router?

3–5 yrs
Show answer

🟢 In simple words: loading.tsx shows a skeleton instantly (via Suspense) and error.tsx catches errors for that route with a retry button.

Next uses special files as automatic boundaries:

  • loading.tsx shows instantly while a Server Component is fetching. Behind the scenes Next wraps the page in React <Suspense>, so the shell appears at once and the slow part streams in.
  • error.tsx is an error boundary for that route. It must be a Client Component and gets error and a reset function to try again.
  • not-found.tsx renders when you call notFound().

This means you get loading skeletons and error screens without wiring Suspense or boundaries by hand.

💡 Easy example: loading.tsx is the 'food is being prepared' card shown the moment you order, so you are never staring at a blank table.

// app/dashboard/loading.tsx
export default function Loading() {
  return <Skeleton rows={5} />;
}

// app/dashboard/error.tsx
"use client";
export default function Error({ error, reset }) {
  return <button onClick={reset}>Something went wrong. Retry</button>;
}

🗣️ Say it in one line: loading.tsx streams a skeleton via Suspense, and error.tsx is a per-route error boundary with a reset function.

↪️ Follow-up: What is streaming here? Next sends the ready HTML first and streams the slow parts as they finish, so users see content sooner.

Q10

What does middleware do in Next.js? Give a common use.

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: Middleware is the guard at the door — it runs before the page and usually redirects users who aren't logged in.

Middleware is code in middleware.ts that runs before a request is completed, on the edge. It can rewrite or redirect the request, or change headers and cookies.

The most common use is auth: check for a session cookie and redirect to /login if it is missing, before the page even renders. Other uses are A/B testing, locale redirects, and basic bot or geo rules.

Keep it light — it runs on every matched request, so do not put heavy logic or database calls there.

💡 Easy example: Middleware is the security guard at the entrance who checks your pass before letting you into any room.

// middleware.ts
import { NextResponse } from "next/server";
export function middleware(req) {
  const token = req.cookies.get("session")?.value;
  if (!token) return NextResponse.redirect(new URL("/login", req.url));
  return NextResponse.next();
}
export const config = { matcher: ["/dashboard/:path*"] }; // where it runs

🗣️ Say it in one line: Middleware runs before a request finishes, mainly to redirect or rewrite — most often for auth checks.

↪️ Follow-up: Why not do the final auth check only in middleware? Middleware is a first gate, but you should still verify the user in the page or action, because middleware can be bypassed for some requests.

Q11

What changed with cookies, headers and params in Next.js 15?

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: In Next 15 you must await cookies(), headers(), params and searchParams. They used to be instant.

In Next.js 15 the request-based APIs became asynchronous. You now have to await them:

  • cookies(), headers() and draftMode()
  • the params and searchParams props passed to pages and layouts

Before, these were synchronous. The change lets Next start rendering earlier and prepare for more streaming. If you upgrade and forget to await, you get warnings or errors.

💡 Easy example: The counter now says 'please take a token and wait' instead of handing you the value instantly — a tiny extra step that keeps the queue moving smoothly.

// Next.js 15: await the request APIs
import { cookies } from "next/headers";

export default async function Page({ params }) {
  const { id } = await params;              // params is now a Promise
  const session = (await cookies()).get("session");
  return <Profile id={id} session={session} />;
}

🗣️ Say it in one line: In Next 15, cookies(), headers(), params and searchParams are async — you must await them.

↪️ Follow-up: Is this a breaking change? Yes. It is the main thing to fix when migrating a Next 14 app to 15.

Q12

How would you migrate a project from the Pages Router to the App Router?

8–10 yrs
Show answer

🟢 In simple words: Move from Pages to App one route at a time; both can run together. Fetch in server components and switch to next/navigation.

Do it incrementally — both routers can run in the same app, so you move route by route.

1. Create the app/ folder and a root layout.tsx (this replaces _app and _document). 2. Move one route at a time; the rest keep working under pages/. 3. Replace data functions: getServerSideProps → fetch inside a Server Component (or cache: "no-store"); getStaticProps → default caching or revalidate. 4. Add "use client" to components that use hooks or events. 5. Swap next/router for next/navigation (useRouter, usePathname, useSearchParams).

Test each moved route before doing the next, and keep shared UI in layouts.

💡 Easy example: It is like renovating a house one room at a time while still living in it, instead of knocking the whole thing down at once.

🗣️ Say it in one line: Migrate route by route since both routers coexist: move data fetching into Server Components, add "use client" where needed, and switch to next/navigation.

↪️ Follow-up: What is the biggest mindset change? Thinking 'server first': most components do not need to be client components, and data is fetched where it is used.

Q13

How do you keep secrets safe and manage environment variables?

3–5 yrs
Show answer

🟢 In simple words: Env vars are server-only unless they start with NEXT_PUBLIC_. Never put a secret behind that prefix.

By default, environment variables are server-only and never reach the browser. You can read them in Server Components, Server Actions and route handlers.

Only variables prefixed with NEXT_PUBLIC_ are sent to the browser, so never put a secret behind that prefix.

So API keys and database URLs stay as plain DATABASE_URL (server-only), while safe public values like an analytics ID can be NEXT_PUBLIC_ANALYTICS_ID.

💡 Easy example: NEXT_PUBLIC_ is like writing something on a public noticeboard. Anything without it stays locked in the back office.

// .env
DATABASE_URL=postgres://...        // server-only, safe
NEXT_PUBLIC_SITE_URL=https://...   // shipped to the browser

// server code
const db = connect(process.env.DATABASE_URL);        // ok
// client code
const url = process.env.NEXT_PUBLIC_SITE_URL;        // ok, public only

🗣️ Say it in one line: Env vars are server-only unless they start with NEXT_PUBLIC_, so keep secrets without that prefix.

↪️ Follow-up: Can a Client Component read DATABASE_URL? No. Without the NEXT_PUBLIC_ prefix it is undefined in the browser, which is exactly what you want for a secret.

Q14

How does Next.js help with images and performance?

5–8 yrs
Show answer

🟢 In simple words: next/image and next/font stop layout shift and shrink downloads; next/dynamic lazy-loads heavy client parts.

The next/image component optimises images automatically: it resizes them, serves modern formats, lazy-loads below-the-fold images, and reserves space to avoid layout shift.

Other built-in wins: - next/font loads fonts with no layout shift and no extra network request to Google. - Automatic code splitting per route, plus next/dynamic to lazy-load heavy client components. - Server Components cut the JavaScript sent to the browser.

Together these improve the Core Web Vitals (LCP, CLS) that interviewers like to ask about.

💡 Easy example: next/image is like a smart photo lab that prints each picture in exactly the size and format each reader's screen needs.

import Image from "next/image";
import dynamic from "next/dynamic";

const Chart = dynamic(() => import("./Chart"), { ssr: false }); // lazy, client-only

export default function Page() {
  return <Image src="/hero.jpg" width={1200} height={600} alt="Hero" priority />;
}

🗣️ Say it in one line: next/image and next/font remove layout shift and heavy payloads, and route-level code splitting plus next/dynamic cut the JavaScript shipped.

↪️ Follow-up: What does priority do on an image? It preloads that image, which is useful for the large hero image that decides your LCP score.

Q15

What are common Next.js mistakes you have seen?

8–10 yrs
Show answer

🟢 In simple words: Most Next.js bugs are server-vs-client mix-ups: over-using "use client", leaking secrets, or forgetting caching and revalidation.

  • Adding "use client" too high in the tree, which turns a whole page into a client bundle and loses the Server Component benefits.
  • Calling a database or using secrets inside a Client Component.
  • Expecting fetch to always be fresh — forgetting that Next caches by default and not setting revalidate or no-store.
  • Doing heavy work or database calls in middleware.
  • After a mutation, not calling revalidatePath/revalidateTag, so the UI shows stale data.
  • Forgetting to await cookies()/params after upgrading to Next 15.

💡 Easy example: Most Next.js bugs come from forgetting which side of the fence — server or client — a piece of code is standing on.

🗣️ Say it in one line: The usual mistakes are over-using "use client", leaking secrets to the client, forgetting caching rules, and not revalidating after a mutation.

↪️ Follow-up: How do you catch the "use client" creep? Push "use client" down to the smallest interactive leaf components, not the page or layout.

Mock task 1: Explain Server vs Client Components and give one example of each.

Show a sample answer

Server Component (default): runs on the server, no JavaScript shipped, can read the database — for example a product list that fetches data. Client Component ("use client"): runs in the browser for state and events — for example a like button with useState. Keep most of the tree on the server and make only the interactive leaves client components.

Mock task 2: A product list still shows old data after you add a product. How do you fix it with the App Router cache?

Show a sample answer

The list fetch is cached. Tag it with { next: { tags: ["products"] } }, then after the insert (in a Server Action or route handler) call revalidateTag("products"). revalidatePath("/products") also works. Without this, Next keeps serving the cached list.

"use server";
import { revalidateTag } from "next/cache";
export async function addProduct(data) {
  await db.product.create({ data });
  revalidateTag("products"); // list refreshes next visit
}

Mock task 3: Turn a Pages Router page that used getServerSideProps into an App Router page.

Show a sample answer

Make it a Server Component and fetch directly inside it. For per-request freshness use cache: "no-store" (the SSR equivalent). Move any interactive part into a child component marked "use client", and use next/navigation instead of next/router.

// app/orders/page.tsx
export default async function Orders() {
  const orders = await fetch(API, { cache: "no-store" }).then(r => r.json());
  return <OrderTable orders={orders} />;
}
