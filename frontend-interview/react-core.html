Rendering and reconciliationRendering and reconciliation

Q1

What is the virtual DOM and reconciliation?

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: React keeps a light copy of the screen in memory, compares the new copy with the old one, and changes only what's different.

🖼️ Picture it

The virtual DOM is a plain JavaScript copy of the UI. When state changes, React builds a new copy, compares it with the old one (this is reconciliation, or diffing), and updates only the real DOM parts that changed.

Two rules make the comparison fast: if the element type changes (div to span), React replaces that whole part; and in lists, keys tell React which item is which.

💡 Easy example: Like checking a revised Excel sheet against the old one and only re-printing the changed rows, instead of re-printing the whole file.

🗣️ Say it in one line: React compares the new UI description with the old one and updates only what changed in the real DOM.

Q2

Why do we need keys in lists? What goes wrong with index as key?

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: Keys are name tags for list items. If you use the position as the name tag, items get mixed up when the list changes.

Keys tell React which item is which between renders. With a stable key (like order.id), React can move, add or remove items correctly.

With the index as key, inserting or deleting at the top shifts every index. React then thinks item 0 is still item 0, so state stays with the wrong row: a typed input or a checkbox appears on the wrong item. Index keys are only safe for static lists that never reorder.

// Bad: delete the first row and the input text jumps to the wrong person
{users.map((u, i) => <Row key={i} user={u} />)}

// Good: stable id from the data
{users.map((u) => <Row key={u.id} user={u} />)}

🗣️ Say it in one line: Keys give items identity; index keys break state when the list reorders.

Q3

When does a React component re-render?

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: A component redraws when its state changes, its parent redraws, or a context it reads changes.

A component re-renders when:

  • its own state changes,
  • its parent re-renders (by default, all children re-render too, even with the same props),
  • a context it uses changes.

A re-render is not always slow: React still updates only the changed DOM. It becomes a problem when the component is heavy or the list is long. Then use memo, move state down, or split context.

🗣️ Say it in one line: State change, parent re-render or context change; children re-render with the parent unless memoised.

↪️ Follow-up: Does changing a ref re-render? No. Changing ref.current never triggers a render; that is why refs are used for timers and DOM nodes.

Q4

Controlled vs uncontrolled components?

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: Controlled: React holds the input's value. Uncontrolled: the input holds its own value and you read it when needed.

Controlled: React state holds the value (value={name} + onChange). Easy to validate on every key press, but each key press re-renders.

Uncontrolled: the DOM holds the value, and you read it when needed (a ref, or FormData on submit). Fewer re-renders.

react-hook-form is fast because it is mostly uncontrolled.

🗣️ Say it in one line: Controlled means React state owns the value; uncontrolled means the DOM owns it and we read it when needed.

Q5

Why does my component render twice, and why does useEffect run twice in development?

3–5 yrs
Show answer

🟢 In simple words: In development only, StrictMode runs things twice on purpose to catch missing cleanup. Production runs them once.

That is StrictMode in development. React renders components twice and runs effects as mount → unmount → mount to catch bugs like missing cleanup or impure render code.

It does not happen in production. The fix is not to remove StrictMode, but to write effects with proper cleanup (cancel the request, remove the listener).

🗣️ Say it in one line: StrictMode double-runs render and effects in development only, to expose missing cleanup.

Q6

What is lifting state up? What is prop drilling?

3–5 yrs
Show answer

🟢 In simple words: If two children need the same data, keep it in their parent. Passing props through many layers that don't need them is prop drilling.

Lifting state up: when two siblings need the same data, move the state to their nearest common parent and pass it down.

Prop drilling: passing props through many layers that don't use them, just to reach a deep child. Fix it with composition (pass components as children), Context for app-wide values like the logged-in user, or a state library.

🗣️ Say it in one line: Lift shared state to the common parent; fix deep prop drilling with composition or context.

What's new in React 19What's new in React 19

If your resume says React 19, expect at least one question here. Even on React 18 projects, interviewers like candidates who know what changed.

Q7

What are the main new features in React 19?

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: React 19 handles form loading and errors for you (Actions), shows results instantly (useOptimistic), and lets you pass ref like any prop.

  • Actions: you can pass an async function to a transition or to <form action={fn}>. React tracks the pending state, errors and form reset for you.
  • New hooks: useActionState (state and pending for an action), useFormStatus (pending state of the parent form), useOptimistic (show the result before the server replies).
  • The use() API: read a promise or context, and it can even be called inside an if.
  • ref as a normal prop: function components no longer need forwardRef.
  • <Context> can be used directly as the provider.
  • <title> and <meta> tags inside components are moved into the document head automatically.
  • Server Components and Server Actions are stable (used through frameworks like Next.js).

🗣️ Say it in one line: Actions with useActionState, useFormStatus and useOptimistic, the use() API, and ref as a prop.

Q8

Show a form using useActionState. Why is it better than manual loading state?

5–8 yrs
Show answer

🟢 In simple words: Instead of writing your own loading and error state, useActionState gives you the result and an 'isPending' flag.

🖼️ Picture it

Before, we wrote const [loading, setLoading] = useState(false), set it before and after the call, and handled errors ourselves. useActionState gives you the last result and a pending flag for an async action, with much less code.

import { useActionState } from "react";

function ChangeName({ updateName }) {
  const [error, submitAction, isPending] = useActionState(
    async (prevState, formData) => {
      const err = await updateName(formData.get("name"));
      return err ?? null; // whatever we return becomes the new state
    },
    null,
  );

  return (
    <form action={submitAction}>
      <input name="name" />
      <button disabled={isPending}>{isPending ? "Saving..." : "Save"}</button>
      {error && <p className="error">{error}</p>}
    </form>
  );
}

🗣️ Say it in one line: useActionState wraps an async action and gives me its result and pending state, so I write no manual loading flags.

Q9

What does useOptimistic do? Give a use case.

5–8 yrs
Show answer

🟢 In simple words: Show the change on screen right away, and quietly fix it if the server says no.

🖼️ Picture it

It shows a temporary result straight away while the real request is running. When the request finishes, React replaces it with the real state, or rolls back if it failed.

Use cases: a like button, sending a chat message, or ticking a to-do item. The user sees the change instantly instead of waiting 500 ms.

💡 Easy example: Like WhatsApp showing your message with a clock icon before the tick arrives.

🗣️ Say it in one line: useOptimistic shows the expected result immediately and swaps in the real result when the server answers.

Q10

What is the React Compiler? Do we still need useMemo and useCallback?

5–8 yrs
Show answer

🟢 In simple words: The React Compiler adds the 'remember this' optimisations for you, so you write fewer useMemo and useCallback by hand.

The React Compiler is a build-time tool that adds memoisation automatically. It understands your components and skips work that doesn't need to rerun, which is what we did by hand with useMemo, useCallback and memo.

With the compiler on, you need much less manual memoisation. But many existing projects don't use it yet, so you must still know when and why to use these hooks. A safe answer: "If the project has the compiler, I rely on it and remove noisy memo code; if not, I memoise only after measuring with the Profiler."

🗣️ Say it in one line: The compiler memoises automatically; without it, I memoise only where the Profiler shows a real cost.

Practiceप्रैक्टिस

Explain out loud as if the interviewer is sharing their screen.

Mock task 1: A list of 5,000 rows is slow when typing in a search box above it. What do you do?

Show a sample answer

1) Debounce or use useDeferredValue for the search text so typing stays fast. 2) Wrap the row in memo with stable props. 3) Virtualise the list (react-window or TanStack Virtual) so only ~20 visible rows are in the DOM. 4) Filter on the server for very big data. Measure before and after with the React Profiler.

Mock task 2: Why does this input lose focus on every key press? function Form() { function Field() { return <input/> } return <Field/> }

Show a sample answer

Field is defined inside Form, so each render creates a new component type. React sees a different type, unmounts the old input and mounts a new one, which loses focus. Move Field outside Form.
