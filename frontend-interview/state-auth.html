Q1

What is the Context API and when should you use it?

3–5 yrs🔥 Very common
Show answer

Context lets you share a value with any component below a provider without passing props through every level.

Good for values that many components read and that change rarely: the logged-in user, roles and permissions, theme, language. It is not a full state manager, and it is not good for values that change many times per second.

const AuthContext = createContext(null);

export function AuthProvider({ children }) {
  const [user, setUser] = useState(null);
  const value = useMemo(() => ({ user, setUser }), [user]);
  return <AuthContext value={value}>{children}</AuthContext>; // React 19: Context as provider
}

export function useAuth() {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error("useAuth must be used inside AuthProvider");
  return ctx;
}

🗣️ Say it in one line: Context shares rarely-changing app-wide values like the user and roles without prop drilling.

Q2

What is the performance problem with Context, and how do you fix it?

5–8 yrs🔥 Very common
Show answer

When the provider's value changes, every component that uses that context re-renders, even if it only needed one field.

Fixes:

  • memoise the value with useMemo, so it doesn't change on every provider render,
  • split contexts: AuthContext separate from ThemeContext, or state separate from actions,
  • keep fast-changing state (form input, filters) local, not in context,
  • for heavy shared state, use a store with selectors (Zustand, Redux Toolkit).

🗣️ Say it in one line: Every consumer re-renders when the value changes, so I memoise the value, split contexts and keep fast state local.

Q3

Context vs Redux vs Zustand vs TanStack Query: how do you choose?

5–8 yrs🔥 Very common
Show answer

First separate two kinds of state:

  • Server state (employees, orders from the API): use TanStack Query. It gives caching, refetching and loading states. This is usually 80% of the "state".
  • Client state (sidebar open, selected tab, the logged-in user):
  • small and rarely changing → Context
  • large, shared and frequently changing → Zustand (simple) or Redux Toolkit (strict structure, great dev tools, common in older big projects).

A strong answer: "In my project we use React Query for API data and Context for auth and RBAC, so we didn't need Redux."

🗣️ Say it in one line: React Query for server state, Context for small app-wide state, Zustand or Redux only for large shared client state.

Q4

How does login with Keycloak (OIDC) work in a React app?

5–8 yrs🔥 Very common
Show answer

Keycloak is an identity server. The React app never sees the password:

  • The user clicks Login, and the app redirects to the Keycloak login page.
  • After login, Keycloak redirects back with a short-lived code.
  • The code is exchanged for an access token (and a refresh token). For browser apps, use the Authorization Code flow with PKCE.
  • The app sends the access token in the Authorization: Bearer header to the backend.
  • The token holds roles (for example realm_access.roles). Before it expires, refresh it in the background.

The keycloak-js adapter does most of this. We wrap it in an AuthProvider so the whole app can read the user and roles.

💡 Easy example: Like DigiLocker login: the government site checks your identity, not the app. The app only receives a signed 'pass' that says who you are and what you may do.

const keycloak = new Keycloak({ url: KC_URL, realm: "my-company", clientId: "web" });
await keycloak.init({ onLoad: "login-required", pkceMethod: "S256" });

// before API calls: refresh if the token expires in under 30 seconds
await keycloak.updateToken(30);
api.defaults.headers.Authorization = `Bearer ${keycloak.token}`;

🗣️ Say it in one line: Redirect to Keycloak, get a code back, swap it for tokens with PKCE, send the access token as a Bearer header and refresh it before expiry.

Q5

How do you implement role-based access (RBAC) in the UI?

5–8 yrs🔥 Very common
Show answer

Keep permissions in one place (the AuthContext), and build small helpers on top:

  • a usePermission("leave:approve") hook,
  • a <Can permission="..."> component that shows or hides buttons,
  • a route guard that blocks whole pages,
  • a menu built from config, filtered by permission.

Check permissions, not role names, inside components. Then a new role only needs config changes, not code changes.

Most important: frontend RBAC is only for user experience. Anyone can call the API with Postman, so the backend must check permissions on every request.

function usePermission(permission) {
  const { user } = useAuth();
  return !!user?.permissions.includes(permission);
}

function Can({ permission, children }) {
  return usePermission(permission) ? children : null;
}

// usage
<Can permission="leave:approve"><button onClick={approve}>Approve</button></Can>

🗣️ Say it in one line: One AuthContext, a usePermission hook, a Can component and route guards; the backend still enforces every rule.

Q6

Where do you store the token: localStorage, memory or a cookie?

5–8 yrs🔥 Very common
Show answer
  • localStorage: easy and survives refresh, but any XSS script can steal it.
  • Memory (a JavaScript variable or context): safer from XSS stealing it later, but lost on refresh, so you need a silent refresh.
  • HttpOnly cookie: JavaScript can't read it at all, which is the safest against XSS. It needs SameSite and CSRF protection, and the backend must be built for it.

A balanced answer: "Access token in memory, short expiry; refresh via an HttpOnly cookie or the Keycloak session. And we prevent XSS in the first place."

🗣️ Say it in one line: HttpOnly cookies or memory are safer than localStorage; the real defence is preventing XSS.

Q7

How do you handle a 401 when the token expires in the middle of using the app?

5–8 yrs
Show answer

Use an axios interceptor (or a fetch wrapper):

  • On a 401, try one token refresh.
  • If several requests fail at the same time, make them wait for the same refresh promise instead of refreshing 5 times.
  • Retry the original request with the new token.
  • If the refresh fails, clear the auth state and send the user to login, remembering the page they were on.

🗣️ Say it in one line: An interceptor refreshes once, queues parallel requests on the same refresh, retries, and logs out if the refresh fails.

Practiceप्रैक्टिस

This is a favourite L2 scenario for enterprise projects.

Mock task 1: Design RBAC for an app with 6 roles (Admin, HQ, Head, Staff, Vendor, Viewer) and 40 screens.

Show a sample answer

Store a permission list per role on the backend (for example leave:approve). After login, the API (or token) returns the user's permissions. The frontend keeps a config of routes and menu items, each with a required permission, filters the menu, guards routes, and uses <Can> for buttons. Adding a new role is then a data change only. The backend checks the same permissions on every API call.

Mock task 2: The app logs users out randomly after 5 minutes. How do you debug it?

Show a sample answer

Check the token expiry in the JWT, whether the refresh is called before expiry, whether parallel 401s trigger many refreshes and one invalidates the other (refresh token rotation), whether the device clock is wrong, and the Keycloak session idle timeout settings. Reproduce with the Network tab open and look at the first failing request.
