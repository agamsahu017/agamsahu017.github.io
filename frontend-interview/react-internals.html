Render and commit phasesRender and commit phases

Q1

What are the two phases React works in?

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: React works in two steps: render (figure out changes, can be paused, no DOM yet) then commit (apply to the DOM at once, run effects).

React updates the screen in two phases:

1. Render phase — React calls your components to build a new "work-in-progress" tree and works out what changed. This phase is pure and interruptible: React can pause it, do higher-priority work, and even throw the result away and start again. No DOM changes happen yet. 2. Commit phase — React applies the computed changes to the real DOM in one synchronous, uninterruptible step. Refs are set, and layout effects then passive effects (useEffect) run here.

The key interview point: because the render phase can run multiple times or be discarded, your component's render must have no side effects.

💡 Easy example: Render phase is drafting and editing a document; commit phase is hitting print. You can redraft as many times as you like, but printing happens once, all at once.

// Render phase: pure, may run many times → no side effects here
function Profile({ user }) {
  // ❌ side effect during render: network call, DOM write, subscription
  // ✅ just compute and return UI
  return <h1>{user.name}</h1>;
}
// Commit phase: refs set, then effects run
useEffect(() => { /* side effects live here */ }, []);

🗣️ Say it in one line: Render phase builds the new tree and is interruptible and side-effect-free; commit phase applies changes to the DOM synchronously and runs effects.

↪️ Follow-up: Why does React call my component twice in development? StrictMode intentionally double-invokes render-phase logic to surface impure components and unsafe side effects. It only happens in development.

Q2

Why must the render phase be pure?

5–8 yrs
Show answer

🟢 In simple words: Render can run many times or be thrown away, so it must be pure — no fetches or DOM writes during render.

Because React may call it more than once for the same update, pause it, resume it, or throw the work away and redo it — especially with concurrent rendering. If rendering had side effects (a fetch, a counter increment, a DOM write), those effects would fire unpredictably: twice, or for work that is never committed.

So a component must be a pure function of its props and state: same inputs → same JSX, with no observable side effects. Side effects belong in event handlers or in useEffect (which runs in the commit phase).

💡 Easy example: A pure render is a recipe you can re-read safely any number of times. A side effect during render is like actually cooking every time someone just reads the recipe.

🗣️ Say it in one line: React can run, pause or discard a render, so rendering must be a pure function of props and state; side effects go in effects or event handlers.

↪️ Follow-up: Where do side effects go instead? Event handlers for user-triggered effects, and useEffect/useLayoutEffect for effects tied to the committed render.

The Fiber architectureThe Fiber architecture

Q3

What is a Fiber?

8–10 yrs🔥 Very common
Show answer

🟢 In simple words: A fiber is a small JS object for one node of work, with links to child/sibling/parent, so React can build the UI piece by piece.

A Fiber is a plain JavaScript object that represents one unit of work — roughly one node in the component tree (a component, a DOM element, etc.). Each fiber holds the element's type, its props, its state, and pointers to other fibers: child, sibling and return (its parent).

Together the fibers form a linked tree React can walk one node at a time. React keeps two trees: the current tree (on screen) and a workInProgress tree it builds during render. Each fiber has an alternate pointer to its counterpart — this "double buffering" lets React build the next UI without touching what's shown, then swap the trees on commit.

💡 Easy example: Think of fibers as index cards, one per component, linked into a tree. React can put a card down mid-way and pick it back up, which a plain recursive call stack can't do.

// Simplified shape of a fiber node
const fiber = {
  type: Profile,          // function/class/'div'
  props: { user },
  child: /* first child fiber */ null,
  sibling: /* next sibling fiber */ null,
  return: /* parent fiber */ null,
  alternate: /* the other tree's fiber */ null,
  // plus state, effect flags, etc.
};

🗣️ Say it in one line: A fiber is a JS object for one unit of work in the tree, with child/sibling/parent links and an alternate, so React can build a work-in-progress tree and walk it incrementally.

↪️ Follow-up: What are the two trees called? current (what's on screen) and workInProgress (being built). On commit, React swaps them, so the finished work-in-progress becomes current.

Q4

Why did React move from the old reconciler to Fiber?

8–10 yrs🔥 Very common
Show answer

🟢 In simple words: The old reconciler couldn't stop mid-render; Fiber splits work into units React can pause, prioritize and resume.

The old "stack reconciler" rendered the whole tree with recursive, synchronous function calls. Once it started, it couldn't stop until the entire tree was processed. For large updates this blocked the main thread, so input and animations felt janky.

Fiber (React 16+) turns rendering into incremental units of work. React processes a few fibers, then can yield to the browser to handle a click or paint a frame, then resume. This makes rendering: - Interruptible — pause and resume, - Prioritizable — urgent updates (typing) can jump ahead of non-urgent ones, - Abortable — throw away in-progress work if something more important arrives.

This is the foundation that makes concurrent features (useTransition, Suspense) possible.

💡 Easy example: The old way was reading a whole book in one sitting without looking up. Fiber reads a few pages at a time, so it can glance up when someone calls, then carry on.

🗣️ Say it in one line: The old reconciler was recursive and synchronous, so it couldn't be interrupted; Fiber splits work into units React can pause, prioritize and resume, enabling concurrent rendering.

↪️ Follow-up: Did Fiber change the API I write? No. Fiber is an internal rewrite of the reconciler; your components look the same. It enabled later features like concurrent rendering and Suspense.

Q5

How does React process the fiber tree (the work loop)?

8–10 yrs
Show answer

🟢 In simple words: React walks fibers one at a time (down then up) and steps aside for urgent browser work between units.

React walks the work-in-progress tree one fiber at a time in a loop, with two steps per fiber:

  • beginWork (going down) — render this fiber (call the component), create or reconcile its children.
  • completeWork (coming back up) — once a fiber's children are done, build its DOM/effect info and bubble up to the sibling or parent.

Between units, React checks a scheduler: if the browser needs the main thread (a frame is due, input arrived), React yields and resumes later. When the whole tree is complete, React has a finished effect list and moves to the single, synchronous commit.

💡 Easy example: Like a worker going down each branch of a tree marking what to do, then climbing back up gathering the finished pieces — and stepping aside whenever a more urgent job rings.

🗣️ Say it in one line: React loops over fibers with beginWork going down and completeWork coming up, yielding to the scheduler between units, then commits the finished tree in one step.

↪️ Follow-up: What decides when React yields? A cooperative scheduler using time slicing — React works for a few milliseconds, then yields if the browser has more urgent work, keeping the UI responsive.

Reconciliation and diffingReconciliation and diffing

Q6

How does React's diffing algorithm decide what changed?

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: Diffing is fast and simple: different type → rebuild (state lost), same type → update in place, lists → match by key.

A perfect tree diff is O(n³), which is too slow. React uses an O(n) heuristic based on two assumptions:

1. Different element type → tear down and rebuild. If a node changes from <div> to <span>, or from one component to another, React destroys the old subtree (and its state) and builds a new one. 2. Same type → keep the node and update it. React reuses the DOM node and only applies the changed props. It then recurses into children. 3. Lists use keys. For children in a list, React matches old and new items by their key to detect moves, inserts and removes without rebuilding everything.

So changing a component's type throws away its state; keeping the type preserves it.

💡 Easy example: Renovating a house: same structure → you just repaint and swap furniture (update). Different structure → you demolish and rebuild that room (remount).

// Same type → updated in place (input keeps focus/state)
cond ? <input className="a" /> : <input className="b" />

// Different type → fully remounted (state lost, input loses focus)
cond ? <input /> : <textarea />

🗣️ Say it in one line: React uses an O(n) heuristic: different type remounts the subtree and loses its state, same type updates in place, and lists are matched by key.

↪️ Follow-up: What happens to component state when the type changes? It's thrown away. The old fiber and its hooks are discarded and a fresh component instance is mounted.

Q7

Why are keys important to the diff, and why is index as key risky?

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: Keys are stable name tags for list items. Index keys follow the position, so on reorder the wrong state sticks to the wrong row.

Keys give list items a stable identity across renders so React can tell which item moved, which was added, and which was removed — instead of diffing by position.

Using the array index as the key ties identity to position. If the list reorders, filters, or you insert at the top, the indexes shift, so React thinks item 0 just "changed props" rather than "a new item appeared". This causes wrong state staying on the wrong row: a checked checkbox, focused input or local state attaches to the wrong item.

Use a stable, unique id from the data. Index keys are only safe for a static list that never reorders or changes length.

💡 Easy example: Index keys are like numbering seats instead of naming people. If everyone shifts one seat, the labels follow the seat, not the person — so the wrong data sticks to the wrong row.

🗣️ Say it in one line: Keys are stable identity for list diffing; index keys break on reorder or insertion because identity follows position, attaching state to the wrong item.

↪️ Follow-up: When is an index key acceptable? Only for a list that is static — never reordered, filtered or added to in the middle.

Q8

What is a bailout in rendering?

8–10 yrs
Show answer

🟢 In simple words: A bailout is React skipping a re-render when nothing changed; memo and stable references make it happen.

A bailout is when React skips re-rendering a fiber (and often its subtree) because nothing relevant changed. If a fiber's props and state are the same (by reference) and there's no pending update, React can reuse the previous result instead of calling the component again.

This is why referential stability matters: React.memo lets a component bail out when its props are shallowly equal, and useMemo/useCallback keep prop references stable so a child can bail out. Without stable references, new objects/functions each render defeat the bailout and the child re-renders anyway.

💡 Easy example: Like a reviewer who sees the document is unchanged since last time and stamps 'no change' instead of re-reading it.

🗣️ Say it in one line: A bailout skips re-rendering when props and state are unchanged by reference; memo and stable references (useMemo/useCallback) enable it.

↪️ Follow-up: Does a parent re-render force children to re-render? By default yes, but a child wrapped in React.memo with unchanged props bails out and skips its own re-render.

How hooks work internallyHow hooks work internally

Q9

How does React store hook state internally?

8–10 yrs🔥 Very common
Show answer

🟢 In simple words: Hooks live as a linked list on the fiber, created in call order; that's how useState remembers its value.

Each component's hooks are stored as a singly linked list of hook objects on that component's fiber, in the exact order the hooks are called. The first useState/useEffect/… call creates the first node, the next call creates the second, and so on.

On a re-render, React walks this list in the same order, matching each hook call to its stored node by position (not by any name or key). That's how useState "remembers" its value between renders: the value lives on the fiber's hook list, and React lines up calls to nodes by call order.

💡 Easy example: Hooks are like numbered lockers filled in order. On every render React opens locker 1, then 2, then 3 — so the order of calls has to be identical each time.

function Form() {
  const [name, setName] = useState("");   // hook node 1
  const [age, setAge] = useState(0);      // hook node 2
  useEffect(() => {}, []);                // hook node 3
  // React matches these by order to the fiber's hook list each render
}

🗣️ Say it in one line: Hooks are a linked list of nodes on the fiber, created in call order; React matches each call to its node by position on every render.

↪️ Follow-up: Where is this list stored? On the fiber (memoizedState points to the first hook node). The work-in-progress fiber rebuilds the list each render in the same order.

Q10

Why must hooks be called in the same order every render (rules of hooks)?

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: React matches hooks by position, so a hook inside an if breaks the order — always call hooks at the top level.

Because React identifies each hook by its position in the call order, not by name. If you call a hook inside an if, a loop, or after an early return, the number or order of hooks can change between renders. Then React lines up the wrong stored node with the wrong hook call — so useState returns another hook's value, or effects attach to the wrong slot.

That's why the rules are: only call hooks at the top level, and only from React functions. Calling them unconditionally keeps the order stable so the position-based matching stays correct.

💡 Easy example: It's like a checklist you must read top to bottom in the same order every time. Skip or reorder a line and every item after it points to the wrong thing.

// ❌ breaks the order when 'open' changes
if (open) { const [x] = useState(0); }
// ✅ always called, same order every render
const [x] = useState(0);
if (open) { /* use x */ }

🗣️ Say it in one line: React matches hooks by call position, so conditional or reordered hooks misalign the stored state; always call hooks at the top level in the same order.

↪️ Follow-up: What enforces this in practice? The eslint-plugin-react-hooks lint rules catch conditional hooks and missing dependencies at build time.

Concurrent rendering and SuspenseConcurrent rendering and Suspense

Q11

What is concurrent rendering?

8–10 yrs🔥 Very common
Show answer

🟢 In simple words: Concurrent rendering lets React pause, resume or drop renders and put urgent updates (typing) ahead of heavy ones.

Concurrent rendering is React's ability to work on more than one version of the UI at once and to interrupt, pause, resume or abandon a render. Because the render phase runs on interruptible fibers, React can start rendering an update, pause it to handle an urgent event (like typing), and come back to it later — or throw it away if it's now stale.

This unlocks prioritized updates: urgent updates (input, clicks) stay responsive while heavy, non-urgent updates (filtering a big list) render in the background without blocking the user.

💡 Easy example: Like a chef preparing a big order in the background but instantly pausing to serve a quick coffee, then resuming the big order — the counter never feels stuck.

🗣️ Say it in one line: Concurrent rendering lets React pause, resume or drop renders and prioritize urgent updates over heavy ones, keeping the UI responsive.

↪️ Follow-up: Is concurrent rendering automatically on? The machinery is always there in React 18+, but concurrent behaviour kicks in for updates marked non-urgent, e.g. via useTransition, useDeferredValue or startTransition.

Q12

How do useTransition and useDeferredValue use concurrent rendering?

5–8 yrs
Show answer

🟢 In simple words: useTransition and useDeferredValue mark heavy work as non-urgent so the input stays smooth.

Both mark work as non-urgent so React can keep urgent updates (what the user is typing) responsive:

  • useTransition gives you startTransition to wrap a state update that can be interrupted, plus an isPending flag. The urgent update (the input value) commits immediately; the heavy update (re-filtering a list) renders in the background.
  • useDeferredValue lets you defer a value: the UI keeps using the old value until React has time to render with the new one, so a slow list doesn't block typing.

Under the hood, both schedule their work at a lower priority, which concurrent rendering can interrupt for urgent input.

💡 Easy example: Typing is the VIP in the fast lane; re-rendering a huge list is cargo in the slow lane. Both move, but the VIP is never stuck behind the cargo.

const [isPending, startTransition] = useTransition();
function onChange(e) {
  setText(e.target.value);              // urgent: input stays snappy
  startTransition(() => setQuery(e.target.value)); // non-urgent: heavy list
}

🗣️ Say it in one line: They mark updates as non-urgent so React renders them at low priority in the background, keeping urgent input responsive.

↪️ Follow-up: When would you reach for these? When a heavy render (big list, charts) tied to fast input causes lag — defer the heavy part so typing stays smooth.

Q13

What does Suspense do under the hood?

8–10 yrs
Show answer

🟢 In simple words: A suspending component throws a promise; React shows a fallback and retries when it resolves — that powers lazy loading and streaming.

Suspense lets a component "suspend" — pause rendering — while it waits for something (data or lazy code). Internally, a suspending component throws a promise; React catches it, shows the nearest <Suspense fallback>, and retries that subtree when the promise resolves.

Because the render phase is interruptible, React can hold the suspended work without blocking the rest of the tree, and commit the real content once it's ready. This is how React.lazy code-splitting and data-fetching libraries integrate with concurrent rendering, and how streaming SSR shows a shell first and fills slots as they load.

💡 Easy example: Suspense is a 'loading…' placeholder a component raises when it isn't ready; React shows the fallback, then swaps in the real thing once the wait is over.

🗣️ Say it in one line: A suspending component throws a promise; React shows the nearest fallback and retries the subtree when it resolves, which powers lazy loading and streaming.

↪️ Follow-up: How does this relate to streaming SSR? On the server React streams the ready HTML and the Suspense fallbacks, then streams each slot's real HTML as its data resolves.

Practiceप्रैक्टिस

These come up in senior React rounds. Answer out loud first, then check.

Mock task 1: Explain the difference between the render phase and the commit phase, and why it matters for side effects.

Show a sample answer

Render phase builds the work-in-progress tree and figures out changes; it is pure and can be paused, repeated or discarded, so no side effects are allowed there. Commit phase applies the changes to the DOM in one synchronous step and runs refs and effects. Side effects must go in useEffect (commit) or event handlers, not in render, because render may run multiple times.

Mock task 2: A list uses the array index as key. Users report that after reordering, the wrong row stays checked. Explain the cause and the fix.

Show a sample answer

Index keys tie identity to position. When the list reorders, the indexes stay 0,1,2… so React matches old fibers to new items by position and keeps each row's state (the checkbox) on whatever item now sits at that index. Fix: use a stable unique id from the data as the key, so React tracks items by identity and moves state with the item.

Mock task 3: Why can't you call a hook inside an if? Tie it to how hooks are stored.

Show a sample answer

Hooks are stored as a linked list on the fiber, matched to calls by order, not by name. A hook inside an if changes how many hooks run between renders, so the position-based matching lines up the wrong stored node with the wrong call — useState returns the wrong value or effects misfire. Always call hooks at the top level so the order is stable.
