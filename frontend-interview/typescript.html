Q1

What is the difference between interface and type?

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: Both describe the shape of data. Use interface for objects, and type when you need 'this OR that'.

Both describe the shape of an object, and for most props they work the same.

  • interface can be extended with extends and can be re-opened (declaration merging), which is useful for libraries.
  • type can describe anything: unions ("admin" | "user"), tuples, function types, and mapped types.

A simple team rule: interface for object shapes like props and API responses, type for unions and combinations. Being consistent matters more than the choice.

interface User { id: number; name: string }
interface Admin extends User { permissions: string[] }

type Role = "admin" | "manager" | "viewer"; // only 'type' can do unions
type ApiState = { status: "loading" } | { status: "done"; data: User[] };

🗣️ Say it in one line: Interface for object shapes and extension; type for unions and anything more complex.

Q2

any vs unknown vs never?

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: any = 'don't check anything'. unknown = 'check before you use it'. never = 'this can't happen'.

  • any switches type checking off. You can do anything with it, so bugs slip through.
  • unknown means "I don't know the type yet". You must check it before using it. Use it for API responses and catch errors.
  • never means "this can never happen". It is used for functions that always throw, and for exhaustive checks in a switch.
function parse(raw: unknown) {
  if (typeof raw === "string") return raw.toUpperCase(); // checked, so allowed
  return "not text";
}

type Status = "paid" | "pending";
function label(s: Status) {
  switch (s) {
    case "paid": return "Paid";
    case "pending": return "Pending";
    default: {
      const check: never = s; // compile error here if a new status is added and not handled
      return check;
    }
  }
}

🗣️ Say it in one line: any turns checking off, unknown forces you to check first, never means impossible.

Q3

What are generics? Give a real example.

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: A generic is a blank in a type that you fill later, like Box<Order> or Box<User>.

Generics let you write one function or type that works with many types while keeping type safety. The type is passed like a parameter.

Real example: an API response wrapper. Every API returns { data, total }, but data differs. One generic type covers all of them.

💡 Easy example: A generic is like a courier box with a label slot. The box is the same, but the label says what is inside: 'Books' or 'Mobile'. TypeScript reads the label for you.

interface Paged<T> { data: T[]; total: number; page: number }

async function getPage<T>(url: string): Promise<Paged<T>> {
  const res = await fetch(url);
  return res.json();
}

interface Order { id: number; amount: number }
const orders = await getPage<Order>("/api/orders"); // orders.data is Order[]

🗣️ Say it in one line: Generics are type parameters, so one function or type stays type-safe for many shapes.

Q4

Which utility types do you use daily?

3–5 yrs
Show answer

🟢 In simple words: Ready-made type tools: make all fields optional (Partial), pick some (Pick), remove some (Omit), or build a map (Record).

  • Partial<T>: all fields optional. Good for an "update" form.
  • Required<T>: all fields required.
  • Pick<T, "a" | "b">: only some fields.
  • Omit<T, "password">: everything except some fields.
  • Record<K, V>: an object map, like Record<Role, string[]>.
  • ReturnType<typeof fn>: the type a function returns.
interface Employee { id: number; name: string; salary: number; password: string }

type EmployeeUpdate = Partial<Omit<Employee, "id" | "password">>;
type PublicEmployee = Omit<Employee, "password" | "salary">;
const menuByRole: Record<"admin" | "hr", string[]> = { admin: ["All"], hr: ["Leaves"] };

🗣️ Say it in one line: Partial for updates, Pick and Omit to reshape, Record for maps.

Q5

Enum or union type? Which do you prefer?

5–8 yrs
Show answer

🟢 In simple words: A list of allowed strings like "open" | "closed" is simpler than an enum, and adds no extra code.

Many teams now prefer union types of strings (type Status = "open" | "closed") because they add no extra JavaScript code and work directly with API JSON.

enum creates a real object at runtime. It is fine, but numeric enums can accept wrong numbers silently. If you need a list you can loop over, use a const object with as const and derive the type from it.

const STATUS = ["open", "in_progress", "closed"] as const;
type Status = (typeof STATUS)[number]; // "open" | "in_progress" | "closed"

🗣️ Say it in one line: I prefer string unions or as const objects: zero runtime cost and they match API JSON.

Q6

How do you type React props, state and events?

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: Describe props with an interface, tell useState the type when it's not obvious, and use React's event types in handlers.

  • Props: an interface and destructure it in the function signature. In React 19 you don't need React.FC.
  • State: useState<User | null>(null) when the start value doesn't show the full type.
  • Events: React.ChangeEvent<HTMLInputElement>, React.FormEvent<HTMLFormElement>, React.MouseEvent<HTMLButtonElement>.
  • Children: children: React.ReactNode.
interface ButtonProps { label: string; onClick: () => void; disabled?: boolean }

function SaveButton({ label, onClick, disabled = false }: ButtonProps) {
  return <button onClick={onClick} disabled={disabled}>{label}</button>;
}

function Search() {
  const [q, setQ] = useState("");
  const onChange = (e: React.ChangeEvent<HTMLInputElement>) => setQ(e.target.value);
  return <input value={q} onChange={onChange} />;
}

🗣️ Say it in one line: Interface for props, a generic on useState when needed, and React's event types for handlers.

Q7

What is type narrowing? What are type guards?

5–8 yrs
Show answer

🟢 In simple words: After an if check, TypeScript understands the exact type. A type guard is your own checking function that TypeScript trusts.

Narrowing is TypeScript making a type more specific after a check. typeof, instanceof, in, and checking a shared field (a discriminated union) all narrow types.

A type guard is your own function that returns value is SomeType, so TypeScript trusts your check.

type Result = { ok: true; data: string[] } | { ok: false; error: string };

function show(r: Result) {
  if (r.ok) return r.data.length; // TypeScript knows data exists here
  return r.error;                  // and error exists here
}

function isError(e: unknown): e is Error {
  return e instanceof Error;
}

🗣️ Say it in one line: Narrowing lets TypeScript pick the exact type after a check; a type guard is a custom check it trusts.

Mock task 2: The team has any in 300 places. How would you clean it up?

Show a sample answer

Turn on noImplicitAny and strict step by step, folder by folder. Type the API layer first, since bad data enters there. Use unknown plus validation (for example with zod) at the boundary. Add an ESLint rule (@typescript-eslint/no-explicit-any) so new any can't come in, and track the count going down each sprint.
