Q1

Design the frontend of an admin portal with 6 roles, 50 screens and big forms. How do you start?

8–10 yrs🔥 Very common
Show answer

Use a simple structure and talk through it:

  • Clarify: users, roles, number of screens, devices, languages, data size, offline needs.
  • Stack: React + TypeScript + Vite, React Router, TanStack Query for API data, Context for auth/RBAC, react-hook-form + zod for forms, a component library or a small design system.
  • Structure: feature-based folders, a shared UI kit, an API layer with typed clients, and route config with permissions.
  • Cross-cutting: auth and token refresh, RBAC (menu, routes, buttons), error boundaries, toasts, logging (Sentry), i18n, accessibility.
  • Performance: lazy routes, virtualised tables, server-side pagination and filtering.
  • Quality: ESLint, Prettier, tests, CI checks, preview deploys.

Finish with the trade-offs you made and what you would change at 10x scale.

🗣️ Say it in one line: Clarify, then stack, structure, cross-cutting concerns, performance and quality, and end with trade-offs.

Q2

How do you organise folders in a large React app?

5–8 yrs🔥 Very common
Show answer

Organise by feature, not by file type. Everything for "leaves" lives together, so a developer working on leaves stays in one folder.

src/
  app/            # providers, router, query client
  features/
    leaves/       # components, hooks, api.ts, types.ts, routes.tsx
    employees/
  shared/
    ui/           # Button, Modal, DataTable (no business logic)
    lib/          # http client, formatters
    hooks/        # useDebounce, usePermission

🗣️ Say it in one line: Feature-based folders plus a shared UI kit and lib; features never import each other's internals.

Q3

What are micro-frontends? Would you use them?

8–10 yrs
Show answer

Micro-frontends split one big frontend into separately built and deployed apps (for example with Module Federation), often owned by different teams.

Benefits: independent deploys, and teams don't block each other. Costs: duplicate dependencies, version mismatches, shared state and auth getting harder, inconsistent UI, and more DevOps work.

An honest answer: "Only when several teams have to deploy independently. For one or two teams, a well-structured monorepo with feature folders is simpler and faster."

🗣️ Say it in one line: Useful for many independent teams; for a single team, a modular monolith is simpler.

Q4

How would you migrate an old app (CRA, class components, Redux) to a modern stack?

8–10 yrs
Show answer

Step by step, never a big-bang rewrite:

  • Move the build from Create React App (deprecated in 2025) to Vite first. It is mostly config, with a big speed gain.
  • Turn on TypeScript with allowJs, and type new and changed files only.
  • Move API data from Redux to TanStack Query one feature at a time; keep Redux for what is left.
  • Write new screens with hooks; convert class components only when you touch them.
  • Keep tests and the release going; measure bundle size and errors before and after.

🗣️ Say it in one line: Incremental: Vite first, then TypeScript, then React Query feature by feature, never a big rewrite.

Q5

Tell me about a production issue you handled.

5–8 yrs🔥 Very common
Show answer

They check if you stay calm and follow a process. A good structure:

  • Contain: limit the damage first (roll back, feature flag, hotfix).
  • Communicate: update the lead or client with clear timings.
  • Find the root cause: logs, Sentry, reproduce it.
  • Fix and prevent: add a test or an alert, and write a short post-mortem without blaming anyone.

💡 Easy example: "After a release, the approvals page went blank for one role. I rolled back within 15 minutes, found a null permissions array from the API, added a safe default and a test, and we added an error boundary per page so one widget can't blank the screen again."

🗣️ Say it in one line: Contain, communicate, find the root cause, then fix and prevent.

Q6

How do you estimate a feature? What if the deadline is too tight?

5–8 yrs🔥 Very common
Show answer

Break the feature into small tasks (UI, API integration, validation, edge cases, tests, review), estimate each, and add a buffer for unknowns. Share assumptions along with the number.

If the deadline is too tight, don't just say yes. Offer options: reduce the scope (an MVP first), add people where it actually helps, or move the date. Raise the risk early, not on the last day.

🗣️ Say it in one line: Break it down, estimate with assumptions and a buffer, and offer scope-versus-date options instead of a silent yes.

Q7

How do you do code reviews and mentor juniors?

8–10 yrs
Show answer

Code reviews: automate style with ESLint and Prettier so reviews focus on logic, edge cases, security, naming and tests. Keep PRs small, give reasons ("this re-renders on every key press because..."), and separate must-fix comments from suggestions.

Mentoring: pair on tricky tasks, give juniors ownership of small features, share a checklist, and review their PRs quickly so they aren't blocked.

🗣️ Say it in one line: Automate style, review for logic and risk, explain the why, and unblock juniors quickly.

Q8

How do you handle a disagreement with a teammate or a client?

5–8 yrs
Show answer

Listen first, then move the discussion to facts: data, a small prototype, or a quick spike. Agree on the goal (user, deadline, cost), list the options with trade-offs, and decide together or escalate politely. Once decided, commit fully, even if your option wasn't chosen.

In a client round (common in service companies), be clear and confident, and never criticise your current employer or client.

🗣️ Say it in one line: Listen, use facts and a quick prototype, agree on the goal, then commit to the decision.

Q9

Why do you want to switch?

3–5 yrs🔥 Very common
Show answer

Give a positive, forward-looking reason: more ownership, a bigger scale of product, a new tech stack, or a growth path. Don't complain about your manager or company.

💡 Easy example: "I've built and delivered the full React frontend of an enterprise portal, including auth and role-based access. I now want to work on a larger product with bigger scale and lead a module end to end."

🗣️ Say it in one line: I'm moving towards bigger ownership and scale, not running away from something.

Q10

What is your notice period? Can you join early?

3–5 yrs🔥 Very common
Show answer

Say the exact official notice period (60–90 days is common in service companies). If you can negotiate it, say so honestly: "Official 90 days, I can try for an early release after handover." Ask whether they offer a notice buyout.

Don't promise a date you can't meet. A missed joining date damages trust before you even start.

🗣️ Say it in one line: Give the official period, what you can realistically negotiate, and ask about buyout.

Q11

What are your current and expected CTC?

3–5 yrs🔥 Very common
Show answer

Give your current CTC honestly, split into fixed and variable. It will be checked with payslips.

For the expected CTC, research the range for your role, experience and city on AmbitionBox, Glassdoor, LinkedIn and through friends. Give a range with the reason ("based on my role as a module lead with React 19, React Query and RBAC experience"). If you have another offer, you may mention it politely.

🗣️ Say it in one line: Honest current CTC with the fixed/variable split, and a researched expected range with reasons.

Q12

Are you okay with Noida/Gurugram office, hybrid or shifts? Do you have other offers?

3–5 yrs
Show answer

Know your real limits before the call: office days per week, commute (for example Noida ↔ Gurugram can take 1.5–2 hours each way), shifts for client time zones, and relocation.

About other offers: be honest, without bluffing. If you plan to accept a counter offer from your current company, think about it before taking their offer. Backing out late harms your reputation with recruiters, who talk to each other.

🗣️ Say it in one line: I share my real location and shift preferences, and I'm honest about other offers.
