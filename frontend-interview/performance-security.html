PerformancePerformance

Q1

What are Core Web Vitals?

3–5 yrs🔥 Very common
Show answer

Google's three user-experience numbers:

  • LCP (Largest Contentful Paint): how fast the main content appears. Good: 2.5 s or less.
  • INP (Interaction to Next Paint): how fast the page responds to clicks and typing. Good: 200 ms or less. It replaced FID in 2024.
  • CLS (Cumulative Layout Shift): how much the layout jumps around. Good: 0.1 or less.

Check them with Lighthouse, PageSpeed Insights, or the web-vitals library for real users.

🗣️ Say it in one line: LCP is loading, INP is responsiveness, CLS is visual stability; targets 2.5 s, 200 ms and 0.1.

Q2

A React page is slow. How do you find and fix the problem?

5–8 yrs🔥 Very common
Show answer

Measure first, don't guess:

  • Network tab: big bundles, slow or repeated API calls, waterfalls.
  • Lighthouse / Performance tab: long tasks blocking the main thread.
  • React DevTools Profiler: which components re-render, and how long they take.

Then fix what you find:

  • Big bundle → lazy-load routes, remove heavy libraries (moment → date-fns or dayjs), import only what you use, and check with a bundle analyser.
  • Too many re-renders → move state down, split context, use memo and useCallback.
  • Long lists → virtualise (react-window, TanStack Virtual).
  • Slow typing → debounce, or useDeferredValue / useTransition.
  • Images → correct size, loading="lazy", WebP/AVIF, and fixed width and height to avoid CLS.

Then measure again and quote the numbers: "LCP went from 4.1 s to 1.8 s".

🗣️ Say it in one line: Measure with the Network tab, Lighthouse and the Profiler, fix the biggest cause, then measure again.

Q3

What is useTransition / useDeferredValue used for?

5–8 yrs
Show answer

They mark some updates as not urgent. Typing in the input stays instant (urgent), while filtering a big list (non-urgent) can lag behind and be interrupted.

useTransition wraps the state update you control. useDeferredValue gives a "lagging" copy of a value you received.

const [query, setQuery] = useState("");
const deferredQuery = useDeferredValue(query);
const results = useMemo(() => bigList.filter((x) => x.name.includes(deferredQuery)), [deferredQuery]);

🗣️ Say it in one line: They keep typing urgent and let heavy re-renders run at lower priority.

SecuritySecurity

Q4

What is XSS and how does React protect you? When are you still at risk?

3–5 yrs🔥 Very common
Show answer

XSS (Cross-Site Scripting) is when an attacker's script runs on your page, for example through a comment field, and steals tokens or acts as the user.

React escapes values in JSX by default, so {comment} shows text, not HTML. You are still at risk with:

  • dangerouslySetInnerHTML: sanitise with DOMPurify first,
  • user-supplied URLs in href, like javascript:...: allow only http/https,
  • third-party scripts, and directly editing the DOM.

Add a Content Security Policy (CSP) header as a second layer.

import DOMPurify from "dompurify";
<div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(article.html) }} />

🗣️ Say it in one line: React escapes JSX output; the risks are dangerouslySetInnerHTML, javascript: URLs and third-party scripts.

Q5

What is CORS? Can the frontend fix a CORS error?

3–5 yrs🔥 Very common
Show answer

CORS is a browser rule. A page from app.example.com can't read responses from api.other.com unless that server says it's allowed with the Access-Control-Allow-Origin header. For some requests the browser first sends an OPTIONS preflight request.

The frontend cannot fix it in production. The backend must allow the origin. In development you can use the Vite dev-server proxy. Postman works because it is not a browser.

🗣️ Say it in one line: CORS is the browser enforcing the server's allowed origins, so the fix is on the server; a dev proxy is only for local work.

Q6

What is CSRF and when do you need to worry about it?

5–8 yrs
Show answer

CSRF (Cross-Site Request Forgery) tricks a logged-in user's browser into sending a request to your site from another site, using the browser's cookies automatically.

It matters when auth uses cookies. Defences: SameSite=Lax or Strict cookies, a CSRF token, and checking the Origin header. If you send a Bearer token in a header from JavaScript, classic CSRF doesn't apply, but then you must protect that token from XSS.

🗣️ Say it in one line: CSRF abuses cookies sent automatically; SameSite cookies and CSRF tokens prevent it.

Q7

Can we keep an API key in a .env file in React?

3–5 yrs🔥 Very common
Show answer

No secret is safe in frontend code. VITE_* (or REACT_APP_*) variables are copied into the JavaScript bundle at build time, and anyone can read them in DevTools.

Only put public config there: the API base URL, the Keycloak client id, a public analytics id. Secrets like payment keys or AI API keys must stay on the backend, which calls the third party for you.

🗣️ Say it in one line: Frontend env variables are baked into the bundle and public; secrets stay on the backend.

Errors and testingErrors and testing

Q8

What is an error boundary? What doesn't it catch?

5–8 yrs
Show answer

An error boundary catches errors during rendering in its child tree and shows a fallback UI instead of a blank white screen. Put one around each major page or widget, and log the errors to a tool like Sentry.

It still needs a class component (or the react-error-boundary package). It does not catch errors in event handlers, async code (setTimeout, promises), or in the boundary itself. Use try/catch there.

🗣️ Say it in one line: Error boundaries catch render errors in their subtree and show a fallback; event and async errors need try/catch.

Q9

How do you test React components?

5–8 yrs🔥 Very common
Show answer

Use React Testing Library with Vitest or Jest. Test what the user sees and does, not internal state:

  • find elements by role and label (getByRole("button", { name: /save/i })),
  • interact with userEvent,
  • assert on visible results.

Mock the network with MSW (Mock Service Worker), so components use their real fetch code. Test hooks with renderHook. Add a few Playwright end-to-end tests for critical flows like login and submit.

test("shows error when name is empty", async () => {
  render(<EmployeeForm />);
  await userEvent.click(screen.getByRole("button", { name: /save/i }));
  expect(await screen.findByText(/name is required/i)).toBeInTheDocument();
});

🗣️ Say it in one line: React Testing Library tests behaviour by role and label, MSW mocks the network, and Playwright covers key flows.

Practiceप्रैक्टिस

Senior rounds love 'tell me about a time' versions of these.

Mock task 1: 'Our bundle is 4 MB. What would you do?'

Show a sample answer

Run a bundle analyser to see the biggest packages. Lazy-load routes and heavy widgets (charts, editors, PDF viewers). Replace or tree-shake big libraries (moment, all of lodash, icon packs). Check that the production build is minified and compressed (gzip or brotli), and that source maps aren't served publicly. Set a size budget in CI so it can't grow back.

Mock task 2: A tester finds that a comment with <img src=x onerror=alert(1)> shows an alert. Fix it.

Show a sample answer

Find where the comment is rendered with dangerouslySetInnerHTML or direct innerHTML. Render it as plain text, or sanitise with DOMPurify if rich text is needed. Also sanitise on the backend before saving, add a CSP header, and add a test case with this input.
