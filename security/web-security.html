Broken access control (IDOR)Broken access control (IDOR)

Beginnerशुरुआती

The most common serious bug in real apps: the API checks that you are logged in, but not that the record is yours. Change /api/orders/1051 to /1052 and you see a stranger's order. The OWASP Top 10 (the best-known list of web risks) puts broken access control at the top.

असली apps का सबसे आम गंभीर bug: API check करती है कि आप logged in हैं, पर यह नहीं कि record आपका है। /api/orders/1051 को /1052 करिए और किसी अजनबी का order दिख जाता है। OWASP Top 10 (web risks की सबसे मशहूर list) broken access control को सबसे ऊपर रखती है।

// UNSAFE: any logged-in user can read any order
app.get("/api/orders/:id", requireLogin, async (req, res) => {
  const order = await db.orders.findById(req.params.id);
  res.json(order);
});

// SAFE: the order must belong to the logged-in user
app.get("/api/orders/:id", requireLogin, async (req, res) => {
  const order = await db.orders.findOne({ id: req.params.id, userId: req.user.id });
  if (!order) return res.status(404).json({ message: "Order not found" });
  res.json(order);
});

Rule: every query that loads a user's data includes who is asking (user id, or their branch/region for staff). Hiding a button on the frontend is not security.

नियम: user का data लाने वाली हर query में कौन पूछ रहा है शामिल हो (user id, या staff के लिए उनकी branch/region)। Frontend पर button छिपाना security नहीं है।

SQL injectionSQL injection

Beginnerशुरुआती

If you build SQL by gluing user input into a string, a user can type SQL code instead of data. Try it below: type a normal email, then a quote mark.

अगर आप user input को string में जोड़कर SQL बनाते हैं, तो user data की जगह SQL code टाइप कर सकता है। नीचे आज़माइए: पहले normal email टाइप कीजिए, फिर एक quote mark।

Real code on a real (in-memory) database. Save as sqli.mjs and run node sqli.mjs (Node.js 22.5 or newer):
असली (in-memory) database पर असली code। sqli.mjs नाम से save कीजिए और node sqli.mjs चलाइए (Node.js 22.5 या नया):

        
// SQL injection: the unsafe way and the safe way, on a tiny in-memory database.
import { DatabaseSync } from "node:sqlite";

const db = new DatabaseSync(":memory:");
db.exec("CREATE TABLE users (id INTEGER, email TEXT, password_hash TEXT)");
db.exec("INSERT INTO users VALUES (1, 'priya@shop.in', 'x1'), (2, 'rahul@shop.in', 'x2')");

const typed = "' OR '1'='1"; // what an attacker types in the email box

// UNSAFE: user input is glued into the SQL text
const unsafeSql = `SELECT id, email FROM users WHERE email = '${typed}'`;
console.log("Unsafe SQL:", unsafeSql);
console.log("Unsafe result:", db.prepare(unsafeSql).all().length, "users leaked");

// SAFE: a placeholder (?) keeps input as data, never as SQL code
const safe = db.prepare("SELECT id, email FROM users WHERE email = ?").all(typed);
console.log("Safe result:", safe.length, "users");

असली output:

Safe result: 0 users

        
ORMs like TypeORM and Prisma use placeholders for you, but raw queries built with string templates are still unsafe. Always pass values as parameters.
TypeORM और Prisma जैसे ORMs आपके लिए placeholders इस्तेमाल करते हैं, पर string templates से बनी raw queries अब भी unsafe हैं। Values हमेशा parameters के रूप में भेजिए।

      

      

        
XSS: someone else's script on your pageXSS: आपके page पर किसी और की script
 Beginnerशुरुआती
        
Cross-site scripting (XSS) happens when user text (a comment, a name) is shown as HTML, so a script inside it runs for every visitor and can steal their session. React and most template engines escape text by default, so {comment} is safe. The risks are raw HTML (dangerouslySetInnerHTML, innerHTML) and user-supplied links like javascript:....
Cross-site scripting (XSS) तब होता है जब user का text (comment, नाम) HTML की तरह दिखाया जाए, जिससे उसमें छिपी script हर visitor के लिए चलती है और उनका session चुरा सकती है। React और ज़्यादातर template engines text को default रूप से escape करते हैं, इसलिए {comment} सुरक्षित है। ख़तरा raw HTML (dangerouslySetInnerHTML, innerHTML) और javascript:... जैसे user के दिए links में है।

        
  • Show user text as text. If you must allow rich text, clean it with a sanitizer like DOMPurify.User का text, text की तरह दिखाइए। Rich text ज़रूरी हो तो DOMPurify जैसे sanitizer से साफ़ कीजिए।
  • Allow only http: and https: links from users.Users से सिर्फ़ http: और https: links स्वीकार कीजिए।
  • Add a Content Security Policy (CSP) header as a second wall.दूसरी दीवार के रूप में Content Security Policy (CSP) header जोड़िए।
