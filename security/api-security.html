Why APIs are the main targetAPIs सबसे बड़ा निशाना क्यों हैं

Beginnerशुरुआती

Your React app, your Android app and your partners all talk to the same API. The screen hides buttons and checks forms, but an attacker doesn't use your screen. They open the browser's Network tab, copy the request, and replay it with Postman or curl, changing ids, fields and limits. So every rule must be checked on the server.

आपकी React app, Android app और partners सब एक ही API से बात करते हैं। Screen buttons छिपाती है और forms check करती है, पर attacker आपकी screen इस्तेमाल नहीं करता। वह browser का Network tab खोलता है, request copy करता है, और Postman या curl से ids, fields और limits बदलकर दोबारा भेजता है। इसलिए हर नियम server पर check होना चाहिए।

Think of the API as a bank counter. The form at the entrance helps honest customers, but the cashier still checks your ID, your account and your balance before handing over money.

API को bank counter समझिए। दरवाज़े पर रखा form ईमानदार customers की मदद करता है, पर cashier पैसा देने से पहले आपकी ID, account और balance फिर भी check करता है।

Authentication: tokens and JWT done rightAuthentication: tokens और JWT सही तरीक़े से

Beginnerशुरुआती

Most APIs use a JWT (JSON Web Token) as the login pass. It has three parts separated by dots: header, payload and signature. The payload is only encoded, like writing in a different script, not locked. Anyone can read it. The signature is the tamper seal: if one letter of the payload changes, the seal no longer matches.

ज़्यादातर APIs login pass के रूप में JWT (JSON Web Token) इस्तेमाल करती हैं। इसके तीन हिस्से dots से अलग होते हैं: header, payload और signature। Payload सिर्फ़ encode होता है, जैसे किसी दूसरी लिपि में लिखना, ताला नहीं लगा होता। उसे कोई भी पढ़ सकता है। Signature tamper seal है: payload का एक भी अक्षर बदला तो seal मेल नहीं खाती।

Real code with only Node.js built-ins. Save as jwt.mjs and run node jwt.mjs:

सिर्फ़ Node.js built-ins वाला असली code। jwt.mjs नाम से save कीजिए और node jwt.mjs चलाइए:

// A JWT is readable by anyone, but it can't be changed without the secret.
import { createHmac, timingSafeEqual } from "node:crypto";

const SECRET = "keep-this-in-env-not-in-code"; // demo only
const b64 = (obj) => Buffer.from(JSON.stringify(obj)).toString("base64url");
const sign = (data) => createHmac("sha256", SECRET).update(data).digest("base64url");

function makeToken(payload) {
  const head = b64({ alg: "HS256", typ: "JWT" });
  const body = b64(payload);
  return `${head}.${body}.${sign(`${head}.${body}`)}`;
}

function verify(token) {
  const [head, body, sig] = token.split(".");
  const header = JSON.parse(Buffer.from(head, "base64url"));
  if (header.alg !== "HS256") return "rejected: wrong algorithm";      // pin the algorithm
  const good = Buffer.from(sign(`${head}.${body}`));
  const given = Buffer.from(sig || "");
  if (good.length !== given.length || !timingSafeEqual(good, given)) return "rejected: bad signature";
  const payload = JSON.parse(Buffer.from(body, "base64url"));
  if (payload.exp < Date.now() / 1000) return "rejected: expired";
  return `ok, user ${payload.sub} with role ${payload.role}`;
}

const token = makeToken({ sub: "u42", role: "user", exp: Math.floor(Date.now() / 1000) + 900 });

// 1. Anyone can read the payload. It is only encoded, not encrypted.
console.log("Payload:", Buffer.from(token.split(".")[1], "base64url").toString());

// 2. The real token works.
console.log("Real token:", verify(token));

// 3. An attacker edits the payload to become admin, keeping the old signature.
const [h, , s] = token.split(".");
const forged = `${h}.${b64({ sub: "u42", role: "admin", exp: 9999999999 })}.${s}`;
console.log("Edited token:", verify(forged));

// 4. An attacker says "no signature needed" (the old alg: none trick).
const none = `${b64({ alg: "none", typ: "JWT" })}.${b64({ sub: "u42", role: "admin" })}.`;
console.log("alg none token:", verify(none));

In real projects, use a tested library (jose, jsonwebtoken, @nestjs/jwt) or let Keycloak, Auth0 or Cognito issue tokens. The rules stay the same:

असली projects में tested library (jose, jsonwebtoken, @nestjs/jwt) इस्तेमाल कीजिए या tokens Keycloak, Auth0 या Cognito से बनवाइए। नियम वही रहते हैं:

  • Always verify the signature, never just decode. Pin the allowed algorithm.हमेशा verify कीजिए, सिर्फ़ decode नहीं। Allowed algorithm तय कर दीजिए।
  • Short life: access tokens for about 5 to 15 minutes, with a refresh token to get a new one.छोटी उम्र: access tokens लगभग 5 से 15 minute के, नया पाने के लिए refresh token के साथ।
  • Nothing secret in the payload: no passwords, Aadhaar or PAN numbers. Anyone holding the token can read it.Payload में कुछ secret नहीं: कोई password, Aadhaar या PAN number नहीं। Token जिसके पास है, वह पढ़ सकता है।
  • Check exp, and for tokens from an identity provider also check iss (who issued it) and aud (who it is for).exp check कीजिए, और identity provider वाले tokens में iss (किसने बनाया) और aud (किसके लिए है) भी।

Mass assignment: the field nobody meant to allowMass assignment: वह field जिसे किसी ने allow नहीं करना चाहा था

An "update profile" API copies the whole request body into the database row. The form only has a name box, but the attacker adds role and walletBalance to the request. Save as mass.mjs:

एक "update profile" API पूरी request body को database row में copy कर देती है। Form में सिर्फ़ name का box है, पर attacker request में role और walletBalance जोड़ देता है। mass.mjs नाम से save कीजिए:

// Mass assignment: copying the whole request body into the database row.
const user = { id: 7, name: "Rahul", email: "rahul@shop.in", role: "user", walletBalance: 0 };
const body = { name: "Rahul K", role: "admin", walletBalance: 50000 }; // sent by the user

// UNSAFE: every field the user sends is saved
const unsafe = { ...user, ...body };
console.log("Unsafe:", unsafe.role, unsafe.walletBalance);

// SAFE: only fields on an allowlist can be changed
const EDITABLE = ["name"];
const changes = Object.fromEntries(Object.entries(body).filter(([k]) => EDITABLE.includes(k)));
const safe = { ...user, ...changes };
console.log("Safe:", safe.role, safe.walletBalance, safe.name);

Input validation: check shape, type and sizeInput validation: shape, type और size check कीजिए

Beginnerशुरुआती

Treat every request as written by a stranger. Before your logic runs, check that each field has the right type, a sensible length or range, and that no unknown fields came in. In NestJS this is a DTO with class-validator plus a global ValidationPipe (this code is type-checked against NestJS 10):

हर request को किसी अजनबी की लिखी मानिए। आपका logic चलने से पहले check कीजिए कि हर field का type सही है, लंबाई या range ठीक है, और कोई अनजान field नहीं आया। NestJS में यह class-validator वाला DTO और global ValidationPipe है (यह code NestJS 10 पर type-check किया गया है):

import { ValidationPipe } from "@nestjs/common";
import { NestFactory } from "@nestjs/core";
import { IsEmail, IsInt, IsOptional, IsString, Length, Max, Min } from "class-validator";

// Only these fields are accepted. Anything else in the body is rejected.
export class UpdateProfileDto {
  @IsString() @Length(2, 60) name!: string;
  @IsOptional() @IsEmail() email?: string;
  @IsOptional() @IsInt() @Min(1) @Max(100) pageSize?: number;
}

export async function bootstrap(AppModule: any) {
  const app = await NestFactory.create(AppModule);
  app.useGlobalPipes(new ValidationPipe({
    whitelist: true,              // strip fields that are not in the DTO
    forbidNonWhitelisted: true,   // or reject the request with 400
    transform: true,
  }));
  await app.listen(3000);
}
  • Cap everything: page size (?limit=100000 can pull your whole table), body size, upload size and file type.हर चीज़ की सीमा: page size (?limit=100000 पूरी table खींच सकता है), body size, upload size और file type।
  • Allowlist, don't blocklist: say what is allowed (digits only, these 3 statuses) instead of trying to list every bad input.Allowlist, blocklist नहीं: हर ख़राब input गिनाने की जगह बताइए कि क्या allowed है (सिर्फ़ digits, ये 3 statuses)।
  • URLs from users (webhooks, "import from link"): allow only https and known hosts, and block internal addresses, to avoid SSRF.Users के दिए URLs (webhooks, "link से import"): सिर्फ़ https और जाने-पहचाने hosts allow कीजिए, और internal addresses block कीजिए, ताकि SSRF न हो।
  • Validation stops bad shapes; it does not replace parameterised SQL or ownership checks. You need all of them.Validation ग़लत shape रोकता है; यह parameterised SQL या ownership checks की जगह नहीं लेता। सब चाहिए।

Rate limits: stop floods and guessingRate limits: बाढ़ और guessing रोकिए

Beginnerशुरुआती

Without limits, a bot can try 10,000 OTPs, send 50,000 SMS on your bill, or scrape every product. The most common method is the token bucket: each user (or IP) gets a bucket of tokens. Every request uses one token, and tokens slowly refill. Empty bucket means HTTP 429 Too Many Requests. Play with it:

Limits के बिना bot 10,000 OTPs आज़मा सकता है, आपके bill पर 50,000 SMS भेज सकता है, या हर product scrape कर सकता है। सबसे आम तरीक़ा token bucket है: हर user (या IP) को tokens की एक बाल्टी मिलती है। हर request एक token लेती है, और tokens धीरे-धीरे भरते हैं। बाल्टी ख़ाली मतलब HTTP 429 Too Many Requests। इससे खेलिए:

Try it: 5 tokens in the bucket, 1 refills every secondख़ुद देखें: बाल्टी में 5 tokens, हर second 1 भरता है

The same idea in code, with time simulated so the output is fixed. Save as ratelimit.mjs:

यही बात code में, time को simulate करके ताकि output तय रहे। ratelimit.mjs नाम से save कीजिए:

// Token bucket rate limiter: 5 requests in a burst, then 1 more every second.
function makeLimiter({ capacity, refillPerSec }) {
  const buckets = new Map(); // key: user id or IP
  return function allow(key, now) {
    const b = buckets.get(key) ?? { tokens: capacity, last: now };
    b.tokens = Math.min(capacity, b.tokens + ((now - b.last) / 1000) * refillPerSec);
    b.last = now;
    buckets.set(key, b);
    if (b.tokens < 1) return false; // answer with HTTP 429 Too Many Requests
    b.tokens -= 1;
    return true;
  };
}

const allow = makeLimiter({ capacity: 5, refillPerSec: 1 });

// A bot sends 8 login attempts in the same second
const burst = Array.from({ length: 8 }, () => (allow("bot-ip", 0) ? 200 : 429));
console.log("Bot, 8 requests at once:", burst.join(" "));

// 3 seconds later, 3 tokens have refilled
const later = Array.from({ length: 4 }, () => (allow("bot-ip", 3000) ? 200 : 429));
console.log("Same bot, 3 seconds later:", later.join(" "));

// A normal user has their own bucket and is not affected
console.log("Normal user:", allow("priya", 0) ? 200 : 429);

In NestJS, the official @nestjs/throttler package does this, and an API gateway or Nginx can limit before requests even reach your code.यह in-memory version एक server के लिए चलता है। कई servers हों तो counters Redis में रखिए ताकि सब servers share करें। NestJS में official @nestjs/throttler package यह करता है, और API gateway या Nginx requests के आपके code तक पहुँचने से पहले ही limit लगा सकते हैं।
  • Use stricter limits on costly or risky endpoints: login, OTP, password reset, search, export and anything that sends SMS or email.महँगे या risky endpoints पर कड़ी limits: login, OTP, password reset, search, export और जो कुछ भी SMS या email भेजता है।
  • Limit by user id when logged in, and by IP (plus phone number for OTP) when not.Logged in हो तो user id से limit, न हो तो IP से (और OTP के लिए phone number से भी)।

Think like the attacker, so you defend the right thingAttacker की तरह सोचिए, ताकि सही चीज़ बचाएँ

An attacker's "bot" is nothing clever: it is a small script that repeats the same request in a loop and reads whether the answer was success or failure. It can only win when the server lets it try endlessly. So a defender doesn't chase the bot; they remove the thing that lets any loop succeed. For a 6-digit OTP (only 10 lakh possible codes), these four server-side limits together make guessing pointless:

Attacker का "bot" कोई चालाक चीज़ नहीं: यह एक छोटी script है जो एक ही request को loop में दोहराती है और पढ़ती है कि जवाब success था या failure। यह तभी जीत सकती है जब server उसे बार-बार कोशिश करने दे। इसलिए defender bot के पीछे नहीं भागता; वह उस चीज़ को हटाता है जो किसी भी loop को सफल होने देती है। 6-digit OTP (सिर्फ़ 10 लाख संभव codes) के लिए ये चार server-side limits मिलकर guessing को बेकार कर देती हैं:

  • Few tries per OTP: after 3 to 5 wrong guesses the OTP is thrown away. The 10 lakh codes never get a chance.हर OTP पर गिनी-चुनी कोशिशें: 3 से 5 ग़लत guesses के बाद OTP फेंक दिया जाए। 10 लाख codes को मौक़ा ही नहीं मिलता।
  • Rate limit on verify and send: per phone number and per IP, so the loop is throttled to a crawl and can't flood your SMS bill.Verify और send पर rate limit: per phone number और per IP, ताकि loop रेंगने लगे और आपका SMS bill न भर सके।
  • Short validity: 5 minutes instead of 10 shrinks the window to attack.छोटी validity: 10 की जगह 5 minute, attack का window छोटा।
  • Monitoring and alerts: 500 verify attempts on one number is an alarm, not normal traffic.Monitoring और alerts: एक number पर 500 verify attempts alarm है, normal traffic नहीं।

Writing a script to hammer someone else's login or OTP endpoint, even "just to see", is an offence under India's IT Act. To learn how these attacks work, run them only against your own test app on your own machine, or on deliberately vulnerable practice targets like OWASP crAPI and the authentication labs in the free PortSwigger Web Security Academy.

किसी और के login या OTP endpoint पर request ठोकने वाली script लिखना, चाहे "बस देखने के लिए" हो, भारत के IT Act के तहत अपराध है। ये attacks कैसे चलते हैं यह सीखने के लिए इन्हें सिर्फ़ अपनी test app पर, अपनी ही machine पर चलाइए, या जान-बूझकर कमज़ोर बनाए गए practice targets जैसे OWASP crAPI और free PortSwigger Web Security Academy की authentication labs पर।

⚠️ Common mistakesआम ग़लतियाँ
  • Checking roles only in the frontend (hidden buttons, hidden menu).Roles सिर्फ़ frontend में check करना (छिपे buttons, छिपा menu)।

  • Saving req.body straight into the database.req.body को सीधे database में save करना।
  • Rate-limiting login but forgetting OTP, password reset and export.Login पर rate limit लगाना पर OTP, password reset और export भूल जाना।
  • Thinking CORS protects the API from attackers.यह सोचना कि CORS API को attackers से बचाता है।

The golden rule: only test systems you own, or where you have written permission (your own lab, practice sites made for hacking, or a company's official bug bounty program). Accessing someone else's account or system without permission is a crime under India's IT Act, even if you "only looked".

सुनहरा नियम: सिर्फ़ वही systems test कीजिए जो आपके अपने हैं, या जहाँ लिखित permission है (आपकी अपनी lab, hacking सीखने के लिए बनी practice sites, या किसी company का official bug bounty program)। बिना permission किसी और का account या system खोलना भारत के IT Act के तहत अपराध है, चाहे आपने "सिर्फ़ देखा" हो।

📌 Remember these 4 thingsये 4 बातें याद रखिए
  1. Attackers skip your UI. Every rule lives on the server.Attackers आपकी UI छोड़ देते हैं। हर नियम server पर होता है।
  2. A JWT is readable by anyone. Verify the signature, pin the algorithm, keep it short-lived.JWT कोई भी पढ़ सकता है। Signature verify कीजिए, algorithm तय कीजिए, उम्र छोटी रखिए।
  3. Right user, right record, right field: BOLA, function level and property level checks.सही user, सही record, सही field: BOLA, function level और property level checks।

Exercise 1: Review this NestJS handler: @Patch('users/:id') update(@Param('id') id: string, @Body() body: any) { return this.repo.update(id, body); }. List the problems.Exercise 1: इस NestJS handler को review कीजिए: @Patch('users/:id') update(@Param('id') id: string, @Body() body: any) { return this.repo.update(id, body); }। Problems गिनाइए।

Show a sample answerएक sample जवाब देखें
  • BOLA: any logged-in user can update any user by changing :id. Check that id is the caller's own id, or that the caller is an admin.BOLA: कोई भी logged-in user :id बदलकर किसी भी user को update कर सकता है। Check कीजिए कि id caller की अपनी id है, या caller admin है।
  • Mass assignment: body: any is saved as it is, so role or isActive can be changed. Use a DTO with only the editable fields and whitelist: true.Mass assignment: body: any जैसा है वैसा save होता है, तो role या isActive बदला जा सकता है। सिर्फ़ बदलने लायक fields वाला DTO और whitelist: true इस्तेमाल कीजिए।
  • No validation: lengths and formats are not checked.Validation नहीं: लंबाई और format check नहीं होते।
  • No guard visible: make sure an auth guard runs on this route (or globally).कोई guard नहीं दिखता: पक्का कीजिए कि इस route पर (या globally) auth guard चलता है।

Exercise 2: Your OTP endpoint has no limit and a 6-digit OTP is valid for 10 minutes. What can go wrong, and what limits would you add?Exercise 2: आपके OTP endpoint पर कोई limit नहीं है और 6 अंकों का OTP 10 minute तक valid है। क्या ग़लत हो सकता है, और आप कौन सी limits जोड़ेंगे?

Show a sample answerएक sample जवाब देखें

A bot can try all 1,000,000 codes and log in as anyone, and it can also request OTPs nonstop and run up your SMS bill. Add: at most 3 to 5 wrong tries per OTP (then it expires), a limit on OTP sends per phone number and per IP (for example 3 per 10 minutes), a shorter validity like 5 minutes, and alerts when limits are hit often.

Bot सभी 10,00,000 codes आज़माकर किसी के भी नाम से login कर सकता है, और लगातार OTP मँगवाकर आपका SMS bill भी बढ़ा सकता है। जोड़िए: हर OTP पर ज़्यादा से ज़्यादा 3 से 5 ग़लत कोशिशें (फिर वह expire), हर phone number और IP पर OTP भेजने की limit (जैसे 10 minute में 3), 5 minute जैसी छोटी validity, और limits बार-बार टकराने पर alerts।
