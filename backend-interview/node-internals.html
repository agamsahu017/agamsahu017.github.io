What Node.js is made ofWhat Node.js is made of

Q1

What is Node.js actually made of?

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: Node is V8 (runs your JavaScript) + libuv (does the event loop and async I/O) + C++ glue, bundled into one program.

Node.js is not a language; it's a runtime that glues a few C/C++ pieces together:

  • V8 — Google's JavaScript engine (also in Chrome). It parses and runs your JS and manages the JS heap and garbage collection.
  • libuv — a C library that provides the event loop, asynchronous I/O (files, network, DNS) and the thread pool. This is what makes non-blocking I/O work.
  • C++ bindings — glue that exposes libuv and OS features to JavaScript (the fs, net, crypto built-ins call into C++).
  • Core JS libraries — the parts of the standard library written in JavaScript.

So "Node" = V8 (runs JS) + libuv (async I/O + event loop) + bindings, bundled into one executable.

💡 Easy example: Think of V8 as the engine of a car and libuv as the gearbox and wheels that let it actually move and respond — Node bolts them together into one vehicle.

🗣️ Say it in one line: Node is a runtime made of V8 (runs JS and GC), libuv (event loop, async I/O, thread pool) and C++ bindings that connect JS to the OS.

↪️ Follow-up: Which part makes Node non-blocking? libuv — its event loop and thread pool let Node start I/O and continue running JS, then run your callback when the I/O finishes.

Q2

If JavaScript runs on one thread, how does Node handle thousands of connections?

5–8 yrs
Show answer

🟢 In simple words: The one thread never waits on I/O — libuv and the OS do the waiting, so one thread can serve thousands of connections (until you block it with heavy CPU work).

Your JavaScript runs on a single main thread, but the I/O does not block it. When you start I/O (read a file, query a DB, handle a socket), Node hands it to libuv, which uses either the OS's own async facilities or its thread pool, and your JS keeps running.

When the I/O completes, libuv puts your callback on a queue, and the event loop runs it when the main thread is free. So one thread juggles thousands of connections because it only ever does quick, non-blocking work and lets the OS/thread pool do the waiting.

The catch: if you run CPU-heavy JS on the main thread, nothing else can proceed, because there's only one thread for your code.

💡 Easy example: One waiter (the main thread) can serve a full restaurant because they never stand and wait at the kitchen — they take orders, hand them off, and come back when food is ready.

🗣️ Say it in one line: The single thread never waits on I/O: libuv and the OS do the waiting, and the event loop runs your callback when done, so one thread serves many connections — unless you block it with CPU-heavy work.

↪️ Follow-up: What breaks this model? A long synchronous loop or heavy computation on the main thread blocks every other request; move it to worker_threads or a separate process.

The event loop, deeplyThe event loop, deeply

Q3

Explain the event loop phases, and where microtasks run.

8–10 yrs🔥 Very common
Show answer

🟢 In simple words: The loop goes through phases (timers, poll, check, close), and between each it empties the urgent queues: nextTick first, then promises.

libuv's event loop runs in phases, in order, each with its own callback queue:

1. timers — setTimeout / setInterval callbacks whose time is due. 2. pending callbacks — some deferred system callbacks. 3. poll — retrieve new I/O events and run their callbacks (this is where most I/O callbacks fire). 4. check — setImmediate callbacks. 5. close — close events (e.g. a socket closing).

Crucially, the microtask queues run between each phase (and after each callback): first the process.nextTick queue, then the Promise microtask queue, are fully drained before moving on. So microtasks always jump ahead of the next macrotask.

💡 Easy example: The loop is a cleaning route through rooms (phases). After finishing each room, the worker empties the urgent inbox (microtasks) completely before walking to the next room.

🗣️ Say it in one line: The loop cycles through timers, pending, poll, check and close phases; between each phase it fully drains the nextTick queue then the promise microtask queue, so microtasks run before the next macrotask.

↪️ Follow-up: Where do most I/O callbacks run? In the poll phase, when libuv collects completed I/O events.

Q4

What is the output order: setTimeout, setImmediate, process.nextTick and a resolved Promise?

8–10 yrs🔥 Very common
Show answer

🟢 In simple words: Order: normal code, then process.nextTick, then promises, then setTimeout/setImmediate. Microtasks always jump ahead.

Microtasks run before macrotasks, and within microtasks process.nextTick runs before Promise callbacks:

  • process.nextTick — runs first, before any other queue, as soon as the current operation finishes.
  • Promise .then — the Promise microtask queue, drained right after nextTick.
  • Then macrotasks: a due setTimeout(…, 0) (timers phase) and setImmediate (check phase). Their relative order from the main module can vary, but inside an I/O callback, setImmediate reliably runs before a setTimeout(0).

💡 Easy example: nextTick is 'do this the instant I pause'; promises are 'do this next'; setTimeout and setImmediate are 'do this on a later lap of the track'.

setTimeout(() => console.log("timeout"), 0);
setImmediate(() => console.log("immediate"));
Promise.resolve().then(() => console.log("promise"));
process.nextTick(() => console.log("nextTick"));
console.log("sync");
// sync
// nextTick
// promise
// (then) timeout / immediate  (order can vary from the main module)

🗣️ Say it in one line: Synchronous code first, then process.nextTick, then promise microtasks, then macrotasks (setTimeout/setImmediate); inside an I/O callback setImmediate beats setTimeout(0).

↪️ Follow-up: Why can nextTick and promise order surprise people? Both are microtasks that run before timers, so a setTimeout(0) you expected 'immediately' actually runs after all pending microtasks.

Q5

Why can process.nextTick starve the event loop?

8–10 yrs
Show answer

🟢 In simple words: nextTick jumps the queue; if nextTick keeps scheduling more nextTicks, real I/O never gets a turn — it starves.

Because the entire nextTick queue is drained before the loop is allowed to continue to the next phase (and even before the Promise queue). If a nextTick callback schedules another nextTick, which schedules another, the loop never gets to run timers, I/O or setImmediate — it's stuck emptying an endless nextTick queue.

This "starves" I/O: your server stops responding even though it looks busy. The guidance is to prefer setImmediate for "run after I/O gets a turn", and use process.nextTick only for short, finite work that must run before anything else.

💡 Easy example: nextTick is a queue-jumper. If jumpers keep letting in more jumpers, the people actually waiting in line (I/O) never get served.

🗣️ Say it in one line: The nextTick queue is fully drained before the loop proceeds, so recursive nextTick calls block timers and I/O forever; use setImmediate for yielding work.

↪️ Follow-up: When is nextTick the right tool? For small, finite tasks that must run right after the current operation, like emitting an error on the next tick so handlers can attach first.

libuv and the thread poollibuv and the thread pool

Q6

What is the libuv thread pool, and what uses it?

8–10 yrs🔥 Very common
Show answer

🟢 In simple words: libuv keeps 4 background threads (UV_THREADPOOL_SIZE) for fs, crypto, dns.lookup and zlib — jobs with no non-blocking OS option.

libuv keeps a small pool of background OS threads (default 4, set by UV_THREADPOOL_SIZE) to run operations that have no non-blocking OS API, so they don't block the main thread.

What uses it: - File system operations (fs.*). - crypto CPU work like pbkdf2, scrypt, randomBytes. - dns.lookup (which uses the system resolver). - zlib compression.

So "async" in Node is two different mechanisms: true OS async for network sockets, and the thread pool for the operations above.

💡 Easy example: The main thread is the manager; the thread pool is 4 assistants who handle the jobs that can only be done by sitting and waiting (or grinding CPU), so the manager stays free.

// All four share the default pool of 4 threads;
// heavy crypto can make file reads wait behind it.
process.env.UV_THREADPOOL_SIZE = 8; // must be set before the pool is created

🗣️ Say it in one line: libuv has a thread pool (default 4, UV_THREADPOOL_SIZE) that runs fs, crypto (pbkdf2/scrypt), dns.lookup and zlib, because those have no non-blocking OS API.

↪️ Follow-up: How do you raise it, and what's the catch? Set UV_THREADPOOL_SIZE before the app starts using it; raising it helps if many pool-bound ops contend, but it won't help pure network I/O, which doesn't use the pool.

Q7

Does network I/O use the thread pool?

8–10 yrs
Show answer

🟢 In simple words: Network sockets use the OS's own async doorbell (epoll/kqueue/IOCP), not the thread pool; only files, DNS and crypto use the pool.

No. Network sockets use the operating system's own non-blocking I/O — epoll on Linux, kqueue on macOS/BSD, IOCP on Windows — which libuv wraps. The OS notifies libuv when a socket is readable/writable, so no extra thread is needed to wait.

The thread pool is only for operations that have no async OS interface: file system, DNS (dns.lookup), and CPU-bound crypto/zlib. This is a favourite senior question because people assume "all async = thread pool", but most networking scales without touching the pool at all.

💡 Easy example: The OS has a doorbell for network sockets (epoll/kqueue/IOCP), so Node just waits for the bell. Files have no doorbell, so Node sends a thread to stand and wait.

🗣️ Say it in one line: Network I/O uses the OS's async notifications (epoll/kqueue/IOCP), not the thread pool; the pool is only for fs, DNS lookup and CPU-bound crypto/zlib.

↪️ Follow-up: So why does a file-heavy app sometimes stall under load? Because fs shares the 4-thread pool; many concurrent file or crypto ops queue up behind each other even though network handling is fine.

V8 memory and garbage collectionV8 memory and garbage collection

Q8

How does V8 manage memory and garbage collection?

8–10 yrs🔥 Very common
Show answer

🟢 In simple words: V8 bins young objects fast (Scavenge) and tidies long-lived ones less often (Mark-Sweep-Compact); you never free memory by hand.

V8 stores objects on a heap split by age (generational GC), because most objects die young:

  • Young / new space — new objects. Collected very often by a fast Scavenge (copying) collector. Survivors get promoted.
  • Old space — long-lived objects. Collected less often by Mark-Sweep-Compact: mark reachable objects, sweep the rest, compact to reduce fragmentation.

Modern V8 does much of this concurrently and incrementally so GC pauses stay small. The idea to state in an interview: GC is automatic and generational, you don't free memory yourself, but you can still cause leaks by holding references.

💡 Easy example: Like a desk: scratch notes (young space) are binned constantly; important files (old space) are reviewed and tidied occasionally.

🗣️ Say it in one line: V8 uses a generational heap: young space collected often with a fast copying Scavenge, old space collected with mark-sweep-compact, much of it concurrent to keep pauses short.

↪️ Follow-up: If GC is automatic, how do leaks happen? By keeping references the GC can still reach — global arrays that grow, caches without eviction, timers or listeners never removed, closures holding big objects.

Q9

What's the default heap limit, and how do you diagnose a memory leak?

8–10 yrs
Show answer

🟢 In simple words: Raise memory with --max-old-space-size; find leaks by watching heapUsed climb and comparing two heap snapshots.

V8's old-space heap has a default limit (historically around ~1.5–2 GB for 64-bit, version-dependent). You raise it with --max-old-space-size=4096 (MB). Hitting the limit throws "JavaScript heap out of memory".

To diagnose a leak: - Watch RSS and heapUsed (process.memoryUsage()) over time — a steady climb that never drops after GC signals a leak. - Take heap snapshots with --inspect in Chrome DevTools (or heapdump) and compare two snapshots to see which objects keep growing. - Use tools like clinic.js to profile. - Common culprits: unbounded caches/maps, event listeners and timers not cleaned up, and references kept in module-level variables.

💡 Easy example: A leak is a bucket with a slow drip in: each GC empties what it can, but the water level keeps rising because something keeps adding and never lets go.

🗣️ Say it in one line: Raise the limit with --max-old-space-size; find leaks by watching heapUsed over time and diffing heap snapshots to see which objects keep growing.

↪️ Follow-up: Name three classic Node leak sources. Global/module arrays or maps that only grow, listeners/timers never removed, and closures or caches holding large objects.

Q10

What's the difference between the V8 heap, the call stack and a Buffer?

8–10 yrs
Show answer

🟢 In simple words: Stack = what you're holding now, V8 heap = GC-managed objects, Buffer = raw binary memory outside the heap.

  • Call stack — where function calls and their local primitives/references live; small and fast, and a runaway recursion overflows it ("Maximum call stack size exceeded").
  • V8 heap — where JavaScript objects, arrays, closures and strings live; managed by V8's garbage collector.
  • Buffer — raw binary memory allocated outside the V8 heap (off-heap, via libuv/C++), so large binary data (files, network payloads) doesn't pressure the JS GC. Buffers are freed when their JS handle is collected.

Interview point: because Buffers are off-heap, a process can use far more memory (RSS) than its V8 heap limit suggests.

💡 Easy example: The stack is your hands (what you're holding right now), the heap is your managed cupboard, and Buffers are a separate warehouse outside the house for bulk goods.

🗣️ Say it in one line: The call stack holds call frames, the V8 heap holds GC-managed JS objects, and Buffers are raw binary memory allocated off the V8 heap so big binary data doesn't stress the GC.

↪️ Follow-up: Why does RSS exceed the heap limit sometimes? Because RSS includes off-heap memory like Buffers, native allocations and the binary itself, not just the V8 heap.

The module systemThe module system

Q11

How does require() work under the hood (CommonJS)?

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: require resolves the file, reuses the cached exports if already loaded, else wraps and runs the file once, then caches module.exports.

When you require('./x'), Node:

1. Resolves the path (file, folder with index.js/package.json, or a node_modules lookup). 2. Checks the module cache — if already loaded, returns the cached module.exports immediately (so a module runs only once). 3. Otherwise wraps the file's code in a function that provides exports, require, module, __filename and __dirname — that's why those "globals" exist in every file. 4. Executes the wrapped function, letting the module fill module.exports. 5. Caches and returns module.exports.

So require is synchronous and cached by module.exports.

💡 Easy example: require is like fetching a book from a library: if it's already checked out to you (cache), you reuse your copy; otherwise the library fetches, stamps and hands it over, then remembers you have it.

// This wrapper is why exports/require/module/__dirname exist per file:
(function (exports, require, module, __filename, __dirname) {
  // your module code runs here
});

🗣️ Say it in one line: require resolves the path, returns the cached module.exports if present, else wraps the file in a function exposing exports/require/module/__dirname, runs it, then caches and returns module.exports.

↪️ Follow-up: What does the require cache mean in practice? A module's top-level code runs once; later requires get the same exports object, so module state is effectively a singleton.

Q12

CommonJS vs ES Modules: what are the real differences?

5–8 yrs
Show answer

🟢 In simple words: require is synchronous and gives a snapshot; ESM import is static/async with live bindings and allows tree-shaking and top-level await.

  • Loading: CommonJS require is synchronous and can be called anywhere; ESM import is static and asynchronous, hoisted and resolved before the module runs (dynamic import() is the async escape hatch).
  • Bindings: CommonJS exports a copy of a value (the module.exports object at require time); ESM exports live bindings — importers see later updates to an exported variable.
  • Syntax / files: ESM uses import/export, enabled by "type": "module" or .mjs; CommonJS uses require/module.exports, the historical default.
  • ESM gives static analysis (tree-shaking) and top-level await; interop exists but mixing them has sharp edges.

💡 Easy example: CommonJS hands you a photocopy taken at require time; ES Modules give you a live window into the other file, so changes show through.

🗣️ Say it in one line: require is synchronous and exports a snapshot value; ESM import is static/async with live bindings, supports tree-shaking and top-level await, and is enabled by type:module or .mjs.

↪️ Follow-up: Why does ESM allow tree-shaking but CommonJS mostly doesn't? ESM imports/exports are static, so bundlers can see at build time which exports are unused; CommonJS require is dynamic, so usage can't be known statically.

Streams and BuffersStreams and Buffers

Q13

How do streams and backpressure work internally?

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: Streams move data in chunks; when the buffer is full, write() returns false and the producer pauses until 'drain' — that's backpressure.

Node streams are built on EventEmitter and process data in chunks instead of loading everything into memory. Each stream has an internal buffer with a highWaterMark (a size threshold).

Backpressure is the flow-control mechanism: when you writable.write(chunk) and its internal buffer is at or above highWaterMark, write returns false, meaning "slow down". A well-behaved producer pauses until the writable emits a 'drain' event, then resumes. pipe() and pipeline() handle this pause/resume for you automatically.

Without backpressure, a fast source (reading a huge file) would overwhelm a slow destination (a network socket) and blow up memory.

💡 Easy example: Backpressure is a factory conveyor that stops the belt when the next station's tray is full, and restarts it when there's room — so nothing piles up on the floor.

const fs = require("fs");
fs.createReadStream("big.mp4")
  .pipe(fs.createWriteStream("copy.mp4")); // pipe() applies backpressure for you

// Manual: if (!dst.write(chunk)) { src.pause(); dst.once("drain", () => src.resume()); }

🗣️ Say it in one line: Streams are EventEmitters that move data in chunks; when a writable's buffer hits highWaterMark, write() returns false, the producer pauses until 'drain' — and pipe/pipeline automate this backpressure.

↪️ Follow-up: Why prefer pipeline() over pipe()? pipeline() propagates errors and cleans up all streams on failure, which chained pipe() calls don't do well.

Practiceप्रैक्टिस

Senior backend rounds probe these. Answer out loud first, then check.

Mock task 1: Explain why a CPU-heavy function hurts a Node server, and two ways to fix it.

Show a sample answer

Node runs your JavaScript on one thread. A CPU-heavy function keeps the call stack busy, so the event loop can't run any other callbacks — every request stalls until it finishes. Fixes: move the work to a worker_threads pool (or a separate process/microservice), and/or break it into chunks that yield to the loop (e.g. via setImmediate) so I/O gets turns. Offloading to a queue (BullMQ) is another common answer.

Mock task 2: A service's memory keeps climbing and never drops after GC. Walk through how you'd find the leak.

Show a sample answer

Confirm the trend with process.memoryUsage() (heapUsed/RSS rising over time). Reproduce under load, take two heap snapshots a few minutes apart with --inspect in Chrome DevTools, and compare them to see which object types keep growing. Inspect those for retained references: unbounded caches/Maps, event listeners or timers never removed, or module-level arrays. Fix by bounding caches, removing listeners/timers, and dropping references; re-measure.

Mock task 3: Why does setImmediate beat setTimeout(fn, 0) inside an I/O callback, but not always from the main module?

Show a sample answer

Inside an I/O callback you're already in the poll phase; the next phase is check, where setImmediate runs, so immediate fires before the loop comes back around to the timers phase. From the main module, whether a 0ms timer is 'due' when the first timers phase runs is a race with loop startup timing, so the order can vary.
