Indexes and query speedIndexes and query speed

Q1

How does an index work? When will PostgreSQL not use it?

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: An index is like a book's index: jump straight to the page instead of reading the whole book.

A normal index is a B-tree: a sorted structure that lets the database jump to matching rows instead of reading the whole table (a sequential scan). Lookups become roughly O(log n).

The index may not be used when:

  • you wrap the column in a function: WHERE LOWER(email) = ... (fix: an expression index on LOWER(email)),
  • LIKE '%text' with a leading wildcard,
  • the query matches a large part of the table anyway, so a scan is cheaper,
  • the types don't match, or the statistics are out of date (run ANALYZE).

Indexes cost space and slow down writes, so add them for real query patterns, not on every column.

💡 Easy example: A phone's contact list sorted by name: you jump to 'R' for Rahul. Searching for everyone whose name ends with 'ul' means reading the whole list.

🗣️ Say it in one line: A B-tree lets the DB jump to rows; functions on the column, leading wildcards and low selectivity stop it being used.

Q2

What is a composite index? Does column order matter?

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: An index on (department, status) is sorted by department first, like a phone book sorted by surname, then first name.

A composite index covers multiple columns, like (department_id, status). Order matters: it is sorted by the first column, then the second.

So it helps WHERE department_id = 5 and WHERE department_id = 5 AND status = 'active', but is not efficient for WHERE status = 'active' alone. (PostgreSQL 18 can sometimes "skip scan", but don't design around it.)

Rule of thumb: equality columns first, then range or sort columns.

Other useful types: a partial index (WHERE deleted_at IS NULL), a covering index with INCLUDE, and GIN for JSONB and full-text search.

CREATE INDEX idx_emp_dept_status ON employees (department_id, status);
CREATE INDEX idx_users_email_lower ON users (LOWER(email));
CREATE INDEX idx_active_orders ON orders (created_at) WHERE status = 'active'; -- partial

🗣️ Say it in one line: Multi-column indexes follow the leftmost-prefix rule, so put equality columns first.

Q3

A query is slow in production. How do you investigate?

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: Find the slow query, ask the database how it runs it (EXPLAIN), fix the reason, and measure again.

🖼️ Picture it

  • Find it: the slow query log, or pg_stat_statements (sort by total time).
  • Run EXPLAIN (ANALYZE, BUFFERS) on it (carefully on production, since ANALYZE really executes the query).
  • Look for a Seq Scan on a big table, a large gap between estimated and actual rows (stale statistics), expensive sorts or hash joins spilling to disk, and nested loops over many rows.
  • Fix: add the right index, rewrite the query (avoid SELECT *, use joins instead of N+1 queries), paginate, cache, or move the report to a read replica.
  • Measure again, and record the before/after numbers.
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, name FROM employees WHERE department_id = 5 AND status = 'active';
-- Before: Seq Scan on employees ... actual time=0.02..412.7 ms
-- After the composite index: Index Scan using idx_emp_dept_status ... actual time=0.03..0.9 ms

🗣️ Say it in one line: pg_stat_statements to find it, EXPLAIN ANALYZE to see why, then index or rewrite and measure again.

Transactions, isolation and locksTransactions, isolation and locks

Q4

What is a transaction? Explain ACID simply.

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: A transaction is a pack of changes that all happen or none happen, like a bank transfer.

🖼️ Picture it

A transaction groups statements so they all succeed or all fail.

  • Atomicity: all or nothing. Money is never debited without being credited.
  • Consistency: rules (constraints) always hold.
  • Isolation: transactions running at the same time don't see each other's half-finished work.
  • Durability: once committed, it survives a crash.
BEGIN;
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
UPDATE accounts SET balance = balance + 500 WHERE id = 2;
COMMIT; -- or ROLLBACK if anything failed

🗣️ Say it in one line: All-or-nothing groups of statements; ACID means atomic, consistent, isolated and durable.

Q5

What are the isolation levels? What is PostgreSQL's default?

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: Isolation decides how much two transactions running together can see of each other. Postgres's default shows only committed data.

From weakest to strongest:

  • Read Uncommitted: in PostgreSQL it behaves like Read Committed (no dirty reads ever).
  • Read Committed (PostgreSQL's default): each statement sees data committed before that statement started. Two reads in one transaction can differ.
  • Repeatable Read: the whole transaction sees one snapshot.
  • Serializable: as if transactions ran one at a time. It may fail with a serialization error, which you must retry.

PostgreSQL uses MVCC: readers don't block writers, because each transaction sees a version of the row. (MySQL InnoDB's default is Repeatable Read.)

🗣️ Say it in one line: Postgres defaults to Read Committed, uses MVCC so readers don't block writers, and Serializable needs retries.

Q6

Two users book the last seat at the same time. How do you prevent double booking?

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: Lock the seat row so only one person can change it at a time; the second person waits and then sees 'sold out'.

🖼️ Picture it

Several correct options; name one and its trade-off:

  • Pessimistic lock: SELECT ... FOR UPDATE locks the row inside a transaction, so the second user waits, then sees 0 seats.
  • Atomic conditional update: UPDATE ... SET seats = seats - 1 WHERE id = $1 AND seats > 0, then check that 1 row was affected. Simple and fast.
  • Optimistic locking: a version column; the update fails if someone changed it first, and you retry.
  • Unique constraint: on (show_id, seat_no), so the database itself refuses the duplicate.

💡 Easy example: Tatkal booking at 10 AM: thousands click at once for the last berth. Only one update can succeed; everyone else must get 'not available', never a double booking.

BEGIN;
SELECT seats_left FROM shows WHERE id = 42 FOR UPDATE; -- other bookers wait here
UPDATE shows SET seats_left = seats_left - 1 WHERE id = 42 AND seats_left > 0;
INSERT INTO bookings (show_id, user_id) VALUES (42, 7);
COMMIT;

🗣️ Say it in one line: Lock the row with FOR UPDATE, or use a conditional atomic update, with a unique constraint as the final safety net.

Q7

What is a deadlock? How does PostgreSQL handle it, and how do you avoid it?

5–8 yrs
Show answer

🟢 In simple words: Two transactions each hold something the other needs, so both wait forever. Postgres stops one of them.

Transaction A locks row 1 and wants row 2; transaction B locks row 2 and wants row 1. Both wait forever.

PostgreSQL detects this (after deadlock_timeout, 1 second by default) and cancels one transaction with an error.

Avoid it: always lock rows in the same order (for example by id), keep transactions short (no API calls inside a transaction), and retry on deadlock errors.

🗣️ Say it in one line: Two transactions wait on each other; Postgres kills one, and we prevent it with consistent lock order and short transactions.

Q8

Find the 2nd highest salary (and the Nth highest).

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: Rank salaries from high to low with DENSE_RANK, then pick rank 2.

Use DENSE_RANK(), which gives equal salaries the same rank with no gaps. Change = 2 to = N for any N. This works in PostgreSQL, MySQL 8+ and SQLite.

LIMIT 1 OFFSET 1 on distinct salaries also works for a fixed N.

SELECT DISTINCT salary
FROM (SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk FROM employees) t
WHERE rnk = 2;

🗣️ Say it in one line: DENSE_RANK over salary descending, then filter rank = N.

Q9

Find the highest-paid employee in each department.

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: Rank salaries inside each department separately (PARTITION BY), then keep rank 1.

Use a window function with PARTITION BY. This keeps ties (two people with the same top salary) and is easier to read than a correlated subquery.

SELECT dept, name, salary
FROM (
  SELECT dept, name, salary, RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS rnk
  FROM employees
) t
WHERE rnk = 1
ORDER BY dept, name;

🗣️ Say it in one line: RANK() OVER (PARTITION BY dept ORDER BY salary DESC) and keep rank 1.

Q10

Find duplicate emails, then delete the duplicates and keep the oldest row.

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: Group by email and count. Keep the row with the smallest id for each email, delete the rest.

Find them with GROUP BY ... HAVING COUNT(*) > 1. Delete every row whose id is not the smallest id for its email. Then add a unique index so it can't happen again.

SELECT email, COUNT(*) AS cnt FROM users GROUP BY email HAVING COUNT(*) > 1;

DELETE FROM users
WHERE id NOT IN (SELECT MIN(id) FROM users GROUP BY email);

SELECT id, email FROM users ORDER BY id;

🗣️ Say it in one line: GROUP BY with HAVING COUNT > 1 to find them, delete where id isn't the MIN per group, then add a unique index.

Q11

What is the difference between WHERE and HAVING? And between the JOIN types?

3–5 yrs
Show answer

🟢 In simple words: WHERE filters single rows, HAVING filters groups. INNER JOIN keeps only matches; LEFT JOIN keeps all rows from the left table.

WHERE filters rows before grouping. HAVING filters groups after GROUP BY, so it can use COUNT or SUM.

Joins:

  • INNER JOIN: only rows that match in both tables.
  • LEFT JOIN: all rows from the left table, with NULLs where the right side has no match. "All employees, even those without a department."
  • RIGHT JOIN: the opposite (rarely used).
  • FULL JOIN: everything from both sides.

🗣️ Say it in one line: WHERE filters rows, HAVING filters groups; INNER keeps matches, LEFT keeps every left row.

Q12

Why use a connection pool? How many connections?

5–8 yrs
Show answer

🟢 In simple words: Opening a database connection is slow, so keep a few open and share them, like a taxi stand instead of buying a car for each trip.

Opening a PostgreSQL connection is slow and each one uses server memory (a process per connection). A pool keeps some connections open and reuses them.

Size it from the database's max_connections divided across all app instances: 10 pods × 20 connections = 200, which may already be too many. With many instances or serverless, put PgBouncer (or RDS Proxy) in front.

Symptoms of a pool that is too small: requests waiting for a connection. Too big: the database runs out of connections or memory.

🗣️ Say it in one line: A pool reuses expensive connections; size it across all instances, and use PgBouncer when there are many.

Practiceप्रैक्टिस

Write each query on paper first. Interviewers care about the approach more than exact syntax.

Mock task 1: Show each employee's salary next to their department's average salary.

Show a sample answer

Use AVG(...) OVER (PARTITION BY dept), a window function that doesn't collapse rows like GROUP BY does.

SELECT name, dept, salary,
       AVG(salary) OVER (PARTITION BY dept) AS dept_avg
FROM employees;

Mock task 2: A table has 5 crore rows and COUNT(*) on it takes 20 seconds for a dashboard. What do you do?

Show a sample answer

Exact counts on huge Postgres tables are slow because of MVCC. Options: keep a counter table updated by the app or a trigger; use an estimate from pg_class.reltuples when exactness isn't needed; precompute dashboard numbers with a cron job into a summary table; or count with a filter that uses an index. Run dashboards on a read replica.
