Redis and cachingRedis and caching

Q1

What is Redis and what do you use it for?

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: Redis is a super-fast memory store, used for caching, OTPs, counters, locks and job queues.

Redis is an in-memory key-value store, very fast (well under a millisecond for simple operations), with data types beyond strings:

  • String: cache values, counters (INCR for rate limits), OTPs with expiry.
  • Hash: an object with fields, like a session.
  • List: simple queues.
  • Set: unique items, like online user ids.
  • Sorted set: leaderboards, or "top 10 by score".
  • Streams and Pub/Sub: events and messaging.

Common uses: caching, sessions, rate limiting, OTP storage, distributed locks, and job queues (BullMQ is built on Redis).

🗣️ Say it in one line: A fast in-memory store for caching, sessions, OTPs, rate limits, locks and queues.

Q2

Explain the cache-aside pattern. How do you keep the cache correct?

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: Look in the cache first. If it's not there, read the database and keep a copy for a few minutes.

🖼️ Picture it

Cache-aside (lazy loading): the app checks Redis first; on a miss, it reads the database, saves the result in Redis with a TTL, and returns it.

Keeping it correct, which is the hard part:

  • Always set a TTL, so wrong data fixes itself eventually.
  • On update, delete the key (don't update it), so the next read loads fresh data.
  • Use clear key names: employee:42, master:states:v2.
  • Cache what is read often and changes rarely: master data, permissions, config.
import Redis from "ioredis";

const redis = new Redis();

export async function getEmployee(id: number, loadFromDb: (id: number) => Promise<object>) {
  const key = `employee:${id}`;
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);

  const employee = await loadFromDb(id);
  await redis.set(key, JSON.stringify(employee), "EX", 300); // 5 minute TTL
  return employee;
}

export async function onEmployeeUpdated(id: number) {
  await redis.del(`employee:${id}`); // next read reloads fresh data
}

🗣️ Say it in one line: Read from cache, on a miss load from the DB and set it with a TTL, and delete the key on update.

Q3

What is a cache stampede and how do you prevent it?

5–8 yrs
Show answer

🟢 In simple words: A popular cache key expires and thousands of requests hit the database at the same second. Let one request rebuild it.

A popular key expires, and thousands of requests miss at the same moment and all hit the database together, which can take it down.

Prevention:

  • lock / single flight: only one request rebuilds the cache, the others wait briefly or use the old value,
  • random jitter on TTLs (300 s ± 30), so keys don't all expire together,
  • refresh early in the background before expiry for very hot keys,
  • serve stale data while refreshing.

💡 Easy example: The moment a result is announced on a university website, lakhs of students refresh together. If the cache expires at that second, the database gets all of them.

🗣️ Say it in one line: Many requests rebuild the same expired key at once; prevent it with a rebuild lock, TTL jitter and early refresh.

Q4

How do you build a distributed lock with Redis?

8–10 yrs
Show answer

🟢 In simple words: A shared 'occupied' sign in Redis, so only one server does the job at a time. The sign removes itself after a timeout.

When you run 5 copies of a service, an in-memory lock isn't enough. Use Redis:

  • Acquire: SET lock:key <random-token> NX PX 30000. NX means only if it doesn't exist; PX sets an expiry, so a crashed holder doesn't block others forever.
  • Release: delete the key only if the token is still yours, using a small Lua script, so you don't delete someone else's lock after yours expired.

Use it for things like "only one instance runs this cron job". For money-critical correctness, still rely on database constraints and transactions; a Redis lock is a helper, not a guarantee.

import Redis from "ioredis";
import { randomUUID } from "node:crypto";

const redis = new Redis();
const RELEASE = `if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) else return 0 end`;

export async function withLock(key: string, ttlMs: number, work: () => Promise<void>) {
  const token = randomUUID();
  const ok = await redis.set(key, token, "PX", ttlMs, "NX");
  if (ok !== "OK") return false; // someone else holds it
  try {
    await work();
    return true;
  } finally {
    await redis.eval(RELEASE, 1, key, token);
  }
}

🗣️ Say it in one line: SET with NX and an expiry plus a random token, and release with a Lua compare-and-delete.

BullMQ job queuesBullMQ job queues

Q5

Why use a job queue like BullMQ? What work goes there?

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: A queue is a token system: the API takes the order and replies fast, and workers do the slow work in the background.

🖼️ Picture it

A queue moves slow or unreliable work out of the request. The API adds a job and replies fast; a worker process picks it up and does the work, with retries.

Good candidates: emails, SMS and WhatsApp messages, PDF and Excel generation, report exports, image processing, calling slow third-party APIs, webhooks, scheduled reminders.

Benefits: fast APIs, automatic retries, spreading load over time, and scaling workers separately from the API.

💡 Easy example: At a restaurant counter you get a token and sit down; the kitchen (worker) cooks orders one by one. The counter (API) keeps serving new customers instead of waiting at the stove.

🗣️ Say it in one line: The API enqueues and replies fast; workers process slow work with retries and scale separately.

Q6

Show a BullMQ queue and worker in NestJS with retries.

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: Add jobs with retry settings; a worker class picks them up. A failing job is tried again after 2, 4, 8 seconds.

Register the queue, add jobs from a service, and process them in a class that extends WorkerHost. Set attempts and exponential backoff, so temporary failures (an SMTP timeout) are retried after 2 s, 4 s, 8 s...

A custom jobId stops duplicate jobs for the same thing.

import { InjectQueue, Processor, WorkerHost } from "@nestjs/bullmq";
import { Injectable } from "@nestjs/common";
import { Job, Queue } from "bullmq";

// In the module: BullModule.forRoot({ connection: { host: "localhost", port: 6379 } }),
//                BullModule.registerQueue({ name: "emails" })

@Injectable()
export class WelcomeMailer {
  constructor(@InjectQueue("emails") private readonly emails: Queue) {}

  async queueWelcome(userId: number, to: string) {
    await this.emails.add(
      "welcome",
      { userId, to },
      {
        jobId: `welcome-${userId}`, // the same id is not added twice
        attempts: 5,
        backoff: { type: "exponential", delay: 2000 },
        removeOnComplete: 1000,
        removeOnFail: 5000,
      },
    );
  }
}

@Processor("emails", { concurrency: 5 })
export class EmailProcessor extends WorkerHost {
  async process(job: Job<{ userId: number; to: string }>): Promise<void> {
    // throw to trigger a retry; return normally when done
    await sendWelcomeEmail(job.data.to);
  }
}

declare function sendWelcomeEmail(to: string): Promise<void>;

🗣️ Say it in one line: Add jobs with attempts and exponential backoff; a WorkerHost processor handles them with set concurrency.

Q7

A job may run twice. How do you make jobs idempotent?

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: A job can run twice, so before acting it checks 'did I already do this?'.

Queues guarantee at-least-once delivery: after a crash or a stalled job, a job can run again. So design every job to be safe to repeat:

  • before sending, check a "sent" flag or a unique row (notification_id with a unique constraint),
  • use upserts instead of blind inserts,
  • pass an idempotency key to payment and SMS providers,
  • use a deterministic jobId to avoid adding duplicates.

🗣️ Say it in one line: Delivery is at-least-once, so jobs check a unique record or flag before acting and use upserts and idempotency keys.

Q8

What happens to jobs that keep failing? What about delayed and repeating jobs?

5–8 yrs
Show answer

🟢 In simple words: Jobs that fail every retry go to a 'failed' list for checking. Jobs can also wait (delayed) or repeat on a schedule.

After all attempts fail, the job moves to the failed set, which works like a dead letter queue. Keep failed jobs (removeOnFail with a limit), alert on them (a failed count above a threshold), inspect them in a dashboard (like Bull Board), and retry them after fixing the cause.

  • Delayed jobs: { delay: 24 * 3600 * 1000 } for "send a reminder after 24 hours".
  • Repeatable / scheduled jobs: cron-like schedules (BullMQ's job schedulers), for example a daily 8 AM report. Only one scheduled job runs per schedule, even with many workers.

🗣️ Say it in one line: Failed jobs act as a dead letter queue with alerts and manual retry; delays and job schedulers handle timing.

Practiceप्रैक्टिस

These scenario questions are common for 5+ years.

Mock task 1: Send 2 lakh SMS reminders at 9 AM without getting blocked by the SMS provider.

Show a sample answer

Create the jobs in batches ahead of time (bulk add), and use a BullMQ rate limiter on the worker (for example limiter: { max: 100, duration: 1000 }) to match the provider's limit. Retry with backoff on 429/5xx, use idempotency per user per day, track delivery status in the DB, and alert on the failed count. Spread the sending over a window instead of one second.

Mock task 2: Users see an old permission after an admin changes their role.

Show a sample answer

The permissions are cached (in Redis, or in the token) and not invalidated. On a role change, delete that user's permission cache key. If permissions are in the JWT, keep access tokens short-lived, or check a 'permissions version' on each request so the change applies quickly.
