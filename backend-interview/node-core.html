Event loop and threadsEvent loop and threads

Q1

Node.js is single-threaded. How does it handle thousands of requests?

3–5 yrs🔥 Very common
Show answer

Your JavaScript runs on one main thread, but most of a request's time is spent waiting: for the database, another API, or a file. Node.js doesn't wait. It hands the I/O to the operating system (or the libuv thread pool), moves on to the next request, and runs the callback when the result is ready.

So one thread can juggle thousands of requests, as long as each piece of JavaScript is short. If one request does heavy CPU work (a big loop, image processing, huge JSON), everyone waits. That is called blocking the event loop.

💡 Easy example: One waiter in a busy dhaba. He takes your order, gives it to the kitchen and serves the next table. He doesn't stand at the kitchen waiting for your paneer. But if he sits down to chop onions himself, every table waits.

🗣️ Say it in one line: Non-blocking I/O: Node.js hands waiting work to the OS and keeps serving others, so it scales well unless CPU-heavy code blocks the one thread.

Q2

Explain the phases of the Node.js event loop.

5–8 yrs🔥 Very common
Show answer

Each loop round goes through phases in this order:

  • timers: setTimeout and setInterval callbacks whose time is up,
  • pending callbacks: some system-level callbacks,
  • poll: wait for and run I/O callbacks (network, files),
  • check: setImmediate callbacks,
  • close callbacks: like socket.on("close").

Between every callback, Node.js empties the process.nextTick queue first, then the promise microtask queue.

🗣️ Say it in one line: Timers, pending, poll, check, close; nextTick and promise microtasks run between every callback.

Q3

What is the output of this code?

5–8 yrs🔥 Very common
const fs = require("fs");

fs.readFile(__filename, () => {
  setTimeout(() => console.log("timeout"), 0);
  setImmediate(() => console.log("immediate"));
  process.nextTick(() => console.log("nextTick"));
  Promise.resolve().then(() => console.log("promise"));
  console.log("sync");
});
Show answer

Output: sync, nextTick, promise, immediate, timeout.

  • Synchronous code first.
  • The nextTick queue runs before promise microtasks.
  • We are inside an I/O callback (the poll phase). The next phase is check, so setImmediate runs before the loop comes back round to timers.

Note: in the main module (not inside I/O), the order of setTimeout(0) and setImmediate is not guaranteed. Interviewers like candidates who know that.

🗣️ Say it in one line: Sync, then nextTick, then promises; inside I/O, setImmediate beats setTimeout because check comes right after poll.

Q4

What is the libuv thread pool? What uses it?

5–8 yrs
Show answer

libuv is the C library under Node.js. It has a small thread pool, 4 threads by default (change it with UV_THREADPOOL_SIZE), for work the OS can't do asynchronously:

  • most file system operations,
  • crypto like pbkdf2, scrypt and async randomBytes,
  • zlib compression,
  • dns.lookup.

Network I/O (HTTP, database sockets) does not use the pool; it uses the OS's async mechanisms. If you hash many passwords at once, the 4 threads become the bottleneck.

🗣️ Say it in one line: Four threads by default for fs, crypto, zlib and dns.lookup; network I/O doesn't use it.

Q5

What blocks the event loop, and how do you fix CPU-heavy work?

5–8 yrs🔥 Very common
Show answer

Blocking examples: big for loops, JSON.parse of a 50 MB body, sync functions like fs.readFileSync or bcrypt.hashSync inside a request, a slow regex, generating a PDF or Excel file in the request.

Fixes:

  • use the async versions,
  • move heavy work to a queue (BullMQ) and a separate worker process: the best choice for reports and exports,
  • use worker_threads for CPU work inside the same service,
  • process big data in chunks or streams.

Detect it by watching event loop lag (perf_hooks.monitorEventLoopDelay) or with clinic.js.

🗣️ Say it in one line: CPU work and sync calls block; I move heavy jobs to a BullMQ worker or worker_threads and use streams for big data.

Q6

worker_threads vs cluster vs running more containers?

8–10 yrs
Show answer
  • cluster (or PM2): many Node.js processes sharing one port, one per CPU core. Used on plain VMs.
  • worker_threads: extra threads inside one process for CPU-heavy tasks. They can share memory (SharedArrayBuffer).
  • More containers: in Docker/Kubernetes/ECS, the usual way today is one Node.js process per container and scaling the number of containers behind a load balancer.

So: containers for handling more traffic, worker threads for CPU-heavy tasks inside a request, and cluster only on bare VMs.

🗣️ Say it in one line: Scale traffic with more containers, use worker_threads for CPU work, and use cluster only on plain VMs.

Streams, errors and productionStreams, errors and production

Q7

What are streams and backpressure? When do you use them?

5–8 yrs🔥 Very common
Show answer

A stream processes data piece by piece instead of loading it all into memory. Use streams for big files, CSV/Excel exports, uploads and proxies.

Backpressure: if the writer is slower than the reader (say, a slow client), the reader must pause or memory fills up. stream.pipeline() handles backpressure and errors for you. Don't chain .pipe() without error handling.

💡 Easy example: Filling a bucket from a tap. Streams let you carry water mug by mug, and backpressure is turning the tap down when the mug is full, so water doesn't spill.

const { pipeline } = require("node:stream/promises");
const fs = require("node:fs");
const zlib = require("node:zlib");

async function compress(src) {
  // Works for a 5 GB file using only a few MB of memory.
  await pipeline(fs.createReadStream(src), zlib.createGzip(), fs.createWriteStream(src + ".gz"));
}

🗣️ Say it in one line: Streams process data in chunks; pipeline handles backpressure and errors so memory stays flat.

Q8

How do you handle errors in Node.js? What about unhandled rejections?

3–5 yrs🔥 Very common
Show answer
  • try/catch around await. In NestJS, throw HttpExceptions and let a global exception filter format the response.
  • Don't swallow errors. Log them with context (request id, user id).
  • unhandledRejection / uncaughtException: log them and exit the process, then let Docker/PM2/Kubernetes restart it. After an unknown error, the process may be in a broken state.
  • Since Node.js 15, an unhandled promise rejection crashes the process by default.

🗣️ Say it in one line: try/catch with await, a global exception filter, and on uncaught errors: log, exit and let the orchestrator restart.

Q9

How do you find a memory leak in a Node.js service?

8–10 yrs
Show answer

Signs: memory grows steadily over hours and never comes down, then the container is killed (OOMKilled) and restarts.

Steps: reproduce under load, take heap snapshots a few minutes apart (--inspect + Chrome DevTools, or --heapsnapshot-signal), compare them, and see which objects keep growing.

Common causes: in-memory caches with no size limit or TTL, event listeners added on every request, timers never cleared, closures holding big objects, and storing per-request data in global maps.

🗣️ Say it in one line: Watch memory over time, compare heap snapshots, and look for unbounded caches, listeners and timers.

Q10

What is graceful shutdown and why does it matter in Docker/Kubernetes?

5–8 yrs
Show answer

During a deploy, the orchestrator sends SIGTERM and then, after a grace period (30 seconds by default in Kubernetes), SIGKILL. If you exit immediately, in-flight requests fail and jobs half-finish.

Graceful shutdown: on SIGTERM, stop accepting new requests, let current requests finish, let queue workers complete the current job, close DB and Redis connections, then exit. In NestJS, call app.enableShutdownHooks() and close resources in onModuleDestroy / beforeApplicationShutdown.

🗣️ Say it in one line: On SIGTERM: stop new traffic, finish in-flight work, close connections, then exit; Nest's enableShutdownHooks helps.

Mock task 1: An API that exports 5 lakh rows to Excel times out and makes other APIs slow. Fix it.

Show a sample answer

The export blocks the event loop and holds all rows in memory. Move it to a BullMQ job: the API returns 202 Accepted with a job id. The worker streams rows from the DB (a cursor or batches) into the Excel/CSV writer, uploads the file to S3, and saves the status. The UI polls or gets a notification with a pre-signed download link. Other APIs stay fast because the worker runs in a separate process.

Mock task 2: Write code to read a large file line by line without loading it all.

Show a sample answer

Use readline over a read stream.

const fs = require("node:fs");
const readline = require("node:readline");

async function countErrors(path) {
  const rl = readline.createInterface({ input: fs.createReadStream(path), crlfDelay: Infinity });
  let errors = 0;
  for await (const line of rl) if (line.includes("ERROR")) errors++;
  return errors;
}
