REST basicsREST basics

Q1

What makes an API RESTful? Show good URL design.

3–5 yrs🔥 Very common
Show answer

REST treats everything as a resource with a URL, and uses HTTP methods for actions. It is stateless: every request carries everything needed (like the token), so any server can handle it.

Good design: nouns in URLs, plural, nested only one level, and filters in the query string.

GET    /api/v1/employees?status=active&page=2   # list with filters
GET    /api/v1/employees/42                     # one employee
POST   /api/v1/employees                        # create  -> 201 Created
PATCH  /api/v1/employees/42                     # partial update
DELETE /api/v1/employees/42                     # delete  -> 204 No Content
POST   /api/v1/leaves/7/approve                 # an action that isn't plain CRUD

# Avoid: /getEmployees, /employee/delete?id=42

🗣️ Say it in one line: Resources as plural nouns, HTTP methods as verbs, stateless requests, filters in the query string.

Q2

Which status codes do you use? What is 401 vs 403, and 400 vs 422?

3–5 yrs🔥 Very common
Show answer
  • 200 OK, 201 Created, 204 No Content.
  • 400 Bad Request: the request is broken (bad JSON, wrong type).
  • 401 Unauthorized: not logged in, or the token is missing or expired. "Who are you?"
  • 403 Forbidden: logged in, but not allowed. "I know you, but no."
  • 404 Not Found. 409 Conflict: duplicate email, or a version clash.
  • 422 Unprocessable Entity: the format is fine but a business rule fails (end date before start date). Some teams use 400 for all validation; just be consistent.
  • 429 Too Many Requests. 500 server bug. 502/503/504: upstream problem, unavailable, timeout.

💡 Easy example: Office building: 401 is the guard saying 'show your ID card'. 403 is 'your ID is valid, but you can't enter the server room'.

🗣️ Say it in one line: 401 means not authenticated, 403 means authenticated but not permitted; 409 for conflicts, 429 for rate limits.

Q3

PUT vs PATCH? What does idempotent mean?

3–5 yrs🔥 Very common
Show answer
  • PUT replaces the whole resource with what you send.
  • PATCH changes only the fields you send.

Idempotent means doing it once or ten times gives the same final result. GET, PUT and DELETE are idempotent. POST is not: two POSTs create two orders. PATCH may or may not be ({"count": +1} isn't).

Idempotency matters because networks retry. If a client retries a timed-out request, an idempotent API is safe.

🗣️ Say it in one line: PUT replaces, PATCH updates fields; idempotent means repeating the call doesn't change the result again.

Q4

A user double-clicks 'Pay', or the app retries after a timeout. How do you avoid charging twice?

5–8 yrs🔥 Very common
Show answer

Use an idempotency key:

  • The client generates a unique key (a UUID) per payment attempt and sends it in a header (Idempotency-Key).
  • The server stores the key with the result (a DB table with a unique constraint, or Redis with a TTL).
  • If the same key comes again, return the saved response instead of charging again.
  • If the first request is still processing, return 409 or wait.

Also disable the button on the frontend, but never rely only on that. This is how payment gateways handle it.

💡 Easy example: Like an IRCTC booking reference: refreshing the page shows the same booking instead of booking a second ticket.

🗣️ Say it in one line: The client sends a unique Idempotency-Key; the server stores it with a unique constraint and replays the saved response on repeats.

Pagination, versioning and limitsPagination, versioning and limits

Q5

Offset vs cursor pagination: which and why?

5–8 yrs🔥 Very common
Show answer

Offset (LIMIT 20 OFFSET 100000): simple, and you can jump to page 50. But the database still reads and skips 1 lakh rows, so deep pages get slow. And if rows are inserted meanwhile, users see duplicates or miss rows.

Cursor / keyset (WHERE id < :lastId ORDER BY id DESC LIMIT 20): uses the index to start right after the last row seen, so it is fast at any depth and stable while data changes. You can't jump to a page number.

Use offset for admin tables with page numbers and modest data. Use cursor for feeds, infinite scroll, big tables and exports.

-- offset: slow for deep pages
SELECT * FROM orders ORDER BY id DESC LIMIT 20 OFFSET 100000;

-- keyset/cursor: fast at any depth (needs an index on id)
SELECT * FROM orders WHERE id < 873421 ORDER BY id DESC LIMIT 20;

🗣️ Say it in one line: Offset is simple but slow for deep pages; a cursor uses the index to continue after the last row.

Q6

How do you version an API and make changes without breaking clients?

5–8 yrs
Show answer

Most teams use the URL: /api/v1/... (NestJS supports this with app.enableVersioning()). Headers also work, but they are harder to test.

The real skill is not needing v2 often:

  • adding fields is safe; removing or renaming fields breaks clients,
  • for a rename, add the new field, keep the old one, mark it deprecated, and remove it after clients move,
  • announce deprecation dates and log which clients still use old fields.

🗣️ Say it in one line: URL versioning, additive changes, and deprecate-then-remove for anything breaking.

Q7

How do you implement rate limiting?

5–8 yrs
Show answer

Rate limiting protects the API from abuse and accidents: login brute force, OTP spam, a buggy client looping.

  • In NestJS, @nestjs/throttler gives per-route limits (like 5 OTP requests per minute per phone).
  • With multiple servers, keep the counters in Redis so all instances share them.
  • Common algorithms: fixed window, sliding window, and token bucket (allows short bursts).
  • Return 429 with a Retry-After header. Also limit at the gateway or WAF (Nginx, API Gateway, Cloudflare).

🗣️ Say it in one line: Per-user or per-IP limits with counters in Redis, return 429 with Retry-After, plus gateway limits.

Q8

REST vs GraphQL vs gRPC: when would you use each?

8–10 yrs
Show answer
  • REST: simple, cacheable, works everywhere. The default for public and most internal APIs.
  • GraphQL: the client asks for exactly the fields it needs from one endpoint. Good when many different screens or mobile apps need different shapes. Costs: caching and N+1 problems are harder, and you need query cost limits.
  • gRPC: binary (Protocol Buffers) over HTTP/2, fast and strongly typed. Good for service-to-service calls inside a microservice system; not ideal for browsers directly.

🗣️ Say it in one line: REST by default, GraphQL for many varied clients, gRPC for fast internal service-to-service calls.

Practiceप्रैक्टिस

Design questions like these come up in L2 rounds for 5+ years.

Mock task 1: Design the APIs for a leave-approval workflow (apply, approve, reject, send back, list pending).

Show a sample answer

POST /leaves (apply, 201), GET /leaves?status=pending&approverId=me (paginated), GET /leaves/:id, POST /leaves/:id/approve, POST /leaves/:id/reject (body: remark, required), POST /leaves/:id/send-back. Check the current status in the service (only Pending can be approved), returning 409 if someone else already acted. Record every action in a history/audit table with who, when and the remark. A guard checks the approver role, and the service checks that this approver owns the request.

Mock task 2: A partner calls your webhook, and sometimes calls it twice. What do you do?

Show a sample answer

Make the handler idempotent: store the partner's event id with a unique constraint, and skip duplicates. Return 200 quickly and do the heavy work in a queue. Verify the webhook signature.
