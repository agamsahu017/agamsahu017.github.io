Entities and loadingEntities and loading

Q1

Show an entity with a ManyToOne / OneToMany relation.

3–5 yrs🔥 Very common
Show answer

The ManyToOne side owns the foreign key column. OneToMany is just the reverse view and needs the ManyToOne on the other side.

Name your columns explicitly (@JoinColumn({ name: "department_id" })), so the database schema is readable and matches your migrations.

import { Column, CreateDateColumn, Entity, JoinColumn, ManyToOne, OneToMany, PrimaryGeneratedColumn } from "typeorm";

@Entity("departments")
export class Department {
  @PrimaryGeneratedColumn() id!: number;
  @Column() name!: string;
  @OneToMany(() => Employee, (e) => e.department) employees!: Employee[];
}

@Entity("employees")
export class Employee {
  @PrimaryGeneratedColumn() id!: number;
  @Column() name!: string;
  @Column({ type: "varchar", length: 20, default: "active" }) status!: string;
  @ManyToOne(() => Department, (d) => d.employees, { nullable: false })
  @JoinColumn({ name: "department_id" })
  department!: Department;
  @CreateDateColumn({ name: "created_at" }) createdAt!: Date;
}

🗣️ Say it in one line: ManyToOne owns the foreign key with JoinColumn; OneToMany is the inverse side.

Q2

What is the N+1 query problem? How do you fix it in TypeORM?

3–5 yrs🔥 Very common
Show answer

You load 100 employees with 1 query, then access each employee's department, causing 100 more queries: 101 in total. It is fast with 10 rows in dev and terrible with 10,000 in production.

Fix: load the relation in the same query, with relations in find, or leftJoinAndSelect in QueryBuilder. For GraphQL, use DataLoader to batch the queries. Detect it by turning on query logging in dev and counting queries per request.

// 1 query with a JOIN instead of 101
const employees = await employeeRepo.find({
  where: { status: "active" },
  relations: { department: true },
  take: 50,
});

const rows = await employeeRepo
  .createQueryBuilder("e")
  .leftJoinAndSelect("e.department", "d")
  .where("e.status = :status", { status: "active" })
  .orderBy("e.id", "DESC")
  .take(50)
  .getMany();

🗣️ Say it in one line: One query for the list plus one per row; fix it with relations or leftJoinAndSelect in a single query.

Q3

Eager vs lazy relations: which do you use?

5–8 yrs
Show answer
  • eager: true: the relation loads every time you use find. Convenient, but you load data you don't need, and it can chain into big joins.
  • lazy (a Promise<T> type): loads when you access it, which can quietly create N+1 queries.

A safe default: neither. Load relations explicitly per query with relations or joins, so every query shows exactly what it fetches.

🗣️ Say it in one line: I avoid both and load relations explicitly per query, so the cost is always visible.

Q4

Repository methods vs QueryBuilder vs raw SQL: when to use which?

5–8 yrs
Show answer
  • Repository (find, save, update): simple CRUD and simple filters.
  • QueryBuilder: dynamic filters, joins, aggregates, subqueries and pagination for list screens, still with parameters (safe from SQL injection).
  • Raw SQL (dataSource.query(sql, params)): heavy reports, window functions, CTEs, or database-specific features. Always use parameters ($1), never string concatenation.

Also: save() does a SELECT and then an INSERT or UPDATE. For bulk updates, update() or insert() is much faster.

🗣️ Say it in one line: Repository for CRUD, QueryBuilder for dynamic lists, parameterised raw SQL for heavy reports.

Q5

How do you run a transaction in TypeORM with NestJS?

5–8 yrs🔥 Very common
Show answer

Inject the DataSource and use dataSource.transaction(async (manager) => ...). Every query inside must use that manager (not the injected repositories), or it runs outside the transaction.

For more control (several steps, custom error handling), use a QueryRunner with startTransaction, commitTransaction, rollbackTransaction, and release in finally.

import { Injectable } from "@nestjs/common";
import { DataSource } from "typeorm";
import { Account } from "./account.entity";

@Injectable()
export class TransferService {
  constructor(private readonly dataSource: DataSource) {}

  async transfer(fromId: number, toId: number, amount: number) {
    await this.dataSource.transaction(async (manager) => {
      const from = await manager.findOne(Account, { where: { id: fromId }, lock: { mode: "pessimistic_write" } });
      if (!from || from.balance < amount) throw new Error("Insufficient balance");
      await manager.decrement(Account, { id: fromId }, "balance", amount);
      await manager.increment(Account, { id: toId }, "balance", amount);
    }); // any throw -> automatic rollback
  }
}

🗣️ Say it in one line: dataSource.transaction with the provided manager for every query; QueryRunner when I need manual control.

Q6

Why is synchronize: true dangerous? How do migrations work?

3–5 yrs🔥 Very common
Show answer

synchronize: true changes the database schema to match your entities on every start. If you rename a column, it may drop the old column and its data. Use it only for local experiments, never in staging or production.

Migrations are versioned files with up and down, committed to git, reviewed, and run in the deploy pipeline (typeorm migration:generate / migration:run). Every environment then gets the same changes in the same order.

For zero-downtime changes, use expand and contract: add the new column, deploy code that writes to both, backfill, switch reads, then drop the old column in a later release.

🗣️ Say it in one line: synchronize can drop data; migrations are reviewed, versioned and run in the pipeline, using expand-and-contract for renames.

Q7

How do soft delete and optimistic locking work in TypeORM?

5–8 yrs
Show answer

Soft delete: add @DeleteDateColumn() deletedAt. softDelete(id) sets the timestamp instead of deleting, and normal find calls skip those rows automatically. Use withDeleted: true to include them. Useful for audit and undo. Remember that unique indexes still see the deleted rows.

Optimistic locking: add @VersionColumn() version. TypeORM increases it on every save. To stop "two admins editing the same record" overwriting each other, update with WHERE id = :id AND version = :version (or pass the version and check the affected row count); if nothing was updated, return 409 Conflict.

@Entity("profiles")
export class Profile {
  @PrimaryGeneratedColumn() id!: number;
  @Column() address!: string;
  @VersionColumn() version!: number;
  @DeleteDateColumn({ name: "deleted_at" }) deletedAt?: Date;
}

🗣️ Say it in one line: DeleteDateColumn for soft delete; VersionColumn plus a version check in the update for optimistic locking.

Practiceप्रैक्टिस

Explain these as if they happened in your project.

Mock task 1: An employee list API takes 6 seconds. Logs show 400 queries per request. Fix it.

Show a sample answer

It's N+1: each row loads its department, manager and documents separately. Use one QueryBuilder with leftJoinAndSelect for the needed relations, select only the needed columns, paginate with take/skip (or a cursor), and add indexes on the filter and foreign key columns. Check the query count afterwards (from 400 to 2: the data plus a count).

Mock task 2: A migration must add a NOT NULL column to a 2 crore row table without downtime.

Show a sample answer

Add the column as nullable (fast), deploy code that writes it for new rows, backfill in batches (for example 10,000 rows at a time) to avoid long locks, then add NOT NULL (or a CHECK ... NOT VALID constraint followed by VALIDATE) once all rows are filled.
