Q1

How do you approach any system design question?

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: Ask questions, design the APIs and data, draw the big picture, go deep on the hardest part, then talk about trade-offs.

🖼️ Picture it

Use the same 5 steps every time:

  • Clarify requirements: users, main features, scale (users per day, requests per second), and what matters most (consistency, speed, cost).
  • APIs and data model: the main endpoints and tables.
  • High-level design: clients → load balancer → services → DB, cache, queue, storage.
  • Deep dive into the hardest part: the bottleneck, failures, retries, consistency.
  • Trade-offs and scaling: what breaks at 10x, and what you would add.

Talk while you draw. Interviewers score your thinking, not one "right" diagram.

🗣️ Say it in one line: Clarify, APIs and data, high-level design, deep dive, trade-offs.

Q2

Design a notification service (email, SMS, WhatsApp, in-app).

8–10 yrs🔥 Very common
Show answer

🟢 In simple words: Take the request, put it in the right queue, and let workers send it with retries, backup providers and status tracking.

🖼️ Picture it

  • API: POST /notifications with a template id, user ids, channel and data. Validate it, save it, and enqueue. Return 202.
  • Queues per channel (BullMQ), so a slow SMS provider doesn't delay emails. Priorities: OTPs before marketing messages.
  • Workers: render the template (with the user's language), check user preferences and quiet hours, call the provider with an idempotency key, and save the status.
  • Reliability: retries with backoff, provider failover (a second SMS vendor), a dead letter queue with alerts, and rate limits per provider.
  • Tracking: statuses (queued → sent → delivered → failed) from provider webhooks, plus in-app notifications in a table with a read flag.
  • Scale: more workers per channel, and batch big sends.

💡 Easy example: A college results day: 5 lakh students must get an SMS and an email. OTPs for login must still arrive within seconds during that rush. That's why priorities and separate queues matter.

🗣️ Say it in one line: API → per-channel priority queues → idempotent workers with retries, failover, preferences and delivery tracking.

Q3

Design a report export for 10 lakh rows that users can download.

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: Don't build the file during the request. A background job builds it, stores it in S3, and sends the user a download link.

🖼️ Picture it

  • POST /reports/exports with the filters → create an export record (status queued) → add a BullMQ job → return 202 with the export id.
  • Worker: read from a read replica in batches or with a cursor, stream rows into a CSV/Excel writer, upload to S3 (streamed or multipart), then set the status to ready with the key.
  • Notify the user (in-app or email). Downloads use a short-lived pre-signed URL.
  • Limits: one running export per user, a row cap, a cleanup lifecycle rule (delete after 7 days), and an audit log of who exported what.

🗣️ Say it in one line: Async job, stream from a replica in batches to S3, notify, then a pre-signed download link.

Q4

Monolith vs microservices: what would you choose?

8–10 yrs🔥 Very common
Show answer

🟢 In simple words: Start with one well-organised app. Split it into separate services only when teams or load really need it.

Monolith (or a modular monolith with clean module boundaries, which NestJS modules make easy): one deploy, simple transactions, easy debugging. Best for most teams and products early on.

Microservices: independent deploys and scaling per service, and teams own services. But you pay for network calls, distributed transactions (sagas), tracing, versioning, and much more DevOps.

Choose microservices when team size and independent scaling really need it. A good answer: "We started as a modular monolith and split out the report service, because its heavy load affected the main APIs."

🗣️ Say it in one line: Modular monolith by default; split services when teams or load really need independent deploys and scaling.

Q5

How should services talk to each other? Sync or async?

8–10 yrs
Show answer

🟢 In simple words: Call directly when you need the answer now (with timeouts). Send an event when the other service can do it later.

  • Sync (REST/gRPC): when you need the answer now (check a user's permissions). Add timeouts, retries with backoff, and circuit breakers, or one slow service brings down all the others.
  • Async (queues and events: BullMQ, Kafka, RabbitMQ, SNS/SQS): when the caller doesn't need to wait (send an email when a leave is approved). Services stay loosely coupled and survive each other's downtime.

For data that must stay consistent across services, use the outbox pattern: write the event to an outbox table in the same DB transaction as the change, and a publisher sends it reliably.

🗣️ Say it in one line: Sync with timeouts and circuit breakers when you need an answer now; async events, with an outbox, for everything else.

Q6

What is observability? What do you set up for a production service?

5–8 yrs
Show answer

🟢 In simple words: Observability means you can see inside your running system: logs (what happened), metrics (how much), traces (where time went).

Being able to understand what is happening inside from the outside:

  • Logs: structured JSON with a request/correlation id, user id and no sensitive data.
  • Metrics: request rate, error rate, latency (p95/p99), queue length, DB pool usage, event loop lag. Prometheus/Grafana or CloudWatch.
  • Traces: one request's path across services and DB calls (OpenTelemetry, Jaeger, X-Ray).
  • Alerts on symptoms users feel (error rate, p95 latency, failed jobs), not on every CPU spike.

🗣️ Say it in one line: Structured logs with correlation ids, RED metrics with p95/p99, distributed traces, and alerts on user-facing symptoms.

Q7

Tell me about the biggest production incident you handled.

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: Tell it as: what broke, how you stopped the damage, how you found the cause, and what you changed so it won't repeat.

Structure: detect → contain → communicate → root cause → prevent.

Show that you stopped the bleeding first (rollback, feature flag, scaling up, pausing a queue), kept stakeholders updated, found the real cause with logs, metrics and traces, and added prevention (a test, an alert, a limit). Finish with a blameless post-mortem.

💡 Easy example: "After a release, the approvals API went to 8-second responses. I rolled back in 10 minutes, found an N+1 query in a new relation using query logs, fixed it with a join and an index (8 s → 120 ms), and we added a query-count check to code review."

🗣️ Say it in one line: Contain first, communicate, find the root cause with data, then prevent it and write a blameless post-mortem.

Q8

How do you make sure your team's code is production-ready?

8–10 yrs
Show answer

🟢 In simple words: Clear rules, good reviews, automatic checks and monitoring, and helping juniors.

  • Standards: lint, formatting, PR templates, a definition of done (tests, migrations reviewed, API docs updated).
  • Reviews: focus on correctness, security (authorization checks), performance (queries), and backwards compatibility.
  • Safety nets: CI tests, staging that looks like production, feature flags, monitoring dashboards and alerts.
  • People: pair with juniors on risky changes, share incident learnings, and keep a runbook for common failures.

🗣️ Say it in one line: Clear standards, focused reviews, CI and monitoring safety nets, and coaching juniors.

Q9

Why should we hire you for this backend role?

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: Match your stack, show a result with numbers, and show you take ownership.

Match 3 points to their job description:

  • the stack you've used in production (NestJS, PostgreSQL, Redis/BullMQ, Keycloak, S3, Docker),
  • a result with numbers (cut an API from 8 s to 120 ms; handled 5 lakh notifications a day),
  • ownership (designed a module, handled incidents, mentored juniors).

Finish with what you want to build in their team.

🗣️ Say it in one line: Matching stack, proven results with numbers, and ownership.

Q10

What are your current and expected CTC, and your notice period?

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: Give the true current salary, a researched expected range, and an honest notice period.

  • Current CTC: the exact figure, split into fixed and variable. It will be verified.
  • Expected CTC: a researched range for your role, years and city (AmbitionBox, Glassdoor, LinkedIn, friends in similar roles), with the reason: "I own backend modules end to end, including auth, queues and AWS".
  • Notice period: the official number (60–90 days is common in service companies), whether early release or a buyout is possible, and a realistic joining date.

🗣️ Say it in one line: Exact current CTC, a researched expected range with reasons, and an honest notice period.

Do one of these on paper in 30 minutes, then compare with the sample.

Mock task 1: Design a URL-based document verification system: a QR code on a certificate opens a page that shows whether it is genuine.

Show a sample answer

Store each certificate with a random, unguessable id (not a sequential number) and a hash of its key fields. The QR code holds https://verify.example.in/c/<id>. The public GET endpoint is read-only, cached (CDN plus Redis), rate-limited, and shows minimal data (name, course, date, status: valid or revoked). Revocation updates the DB and clears the cache. Log verifications for audit. It scales easily because it is read-heavy and cacheable.

Mock task 2: 'Explain your current project's architecture' (asked in every round).

Show a sample answer

In 2–3 minutes: the product in one line, the users and scale, a diagram (frontend → API gateway or NestJS services → PostgreSQL, Redis/BullMQ, S3, Keycloak), your modules, one hard problem with numbers, and what you would improve. Be ready to go deep on any box you draw.
