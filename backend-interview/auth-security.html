Q1

Authentication vs authorization?

3–5 yrs🔥 Very common
Show answer
  • Authentication: who are you? Login, verifying a token. Failure → 401.
  • Authorization: what may you do? Roles and permissions. Failure → 403.

In NestJS: an auth guard verifies the token and sets request.user, then a roles or permissions guard checks access.

💡 Easy example: At the airport, showing your ID at the gate is authentication. Your boarding pass allowing you onto only one flight is authorization.

🗣️ Say it in one line: Authentication proves identity (401 if it fails); authorization checks permissions (403 if it fails).

Q2

What is a JWT? How is it verified? Can someone change it?

3–5 yrs🔥 Very common
Show answer

A JWT has three Base64URL parts: header.payload.signature. The payload holds claims: sub (user id), exp (expiry), iss (issuer), aud (audience), and roles.

The payload is only encoded, not encrypted: anyone can read it, so never put secrets in it. But nobody can change it without breaking the signature.

Verification: check the signature (with Keycloak, RS256 using the public key from its JWKS endpoint), then check exp, iss and the audience or client. Never accept alg: none, and fix the allowed algorithm.

🗣️ Say it in one line: Header, payload and signature; readable by anyone but tamper-proof, verified by signature, expiry, issuer and audience.

Q3

Access token vs refresh token? Why keep access tokens short-lived?

3–5 yrs🔥 Very common
Show answer
  • Access token: sent with every API call, short-lived (5–15 minutes). A JWT can't easily be cancelled before it expires, so keeping it short limits the damage if it leaks.
  • Refresh token: long-lived, used only with the auth server to get new access tokens. Store it more safely (an HttpOnly cookie), and rotate it on every use; reuse of an old refresh token signals theft.

Logout or blocking a user: revoke the refresh token or session in Keycloak. Access tokens then die within minutes. For instant blocking, keep a small denylist in Redis.

🗣️ Say it in one line: Short access tokens limit damage; long refresh tokens, stored safely and rotated, get new ones.

Q4

Which OAuth2/OIDC flow for which case?

5–8 yrs🔥 Very common
Show answer
  • Authorization Code + PKCE: users logging in from a browser SPA or mobile app. The standard today.
  • Client Credentials: service-to-service calls with no user (a cron service calling the report service). The service uses its own client id and secret.
  • Refresh Token: getting new access tokens.
  • Avoid the old Implicit and Password grants.

OIDC is a layer on OAuth2 for identity: it adds the ID token and the userinfo endpoint. OAuth2 alone is about access, not "who is this user".

🗣️ Say it in one line: Code + PKCE for users, Client Credentials for services; OIDC adds identity on top of OAuth2.

Q5

What are realms, clients and roles in Keycloak?

5–8 yrs
Show answer
  • Realm: an isolated space with its own users, roles and settings (often one per product or environment).
  • Client: an application that uses Keycloak (the web app is a public client, the backend a confidential client).
  • Realm roles: global roles (admin). Client roles: roles specific to one app.
  • Groups: assign roles to many users at once.

Roles appear in the access token under realm_access.roles and resource_access.<client>.roles.

🗣️ Say it in one line: Realm = isolated tenant, client = an app, roles at realm or client level, which show up as token claims.

Q6

How do you verify Keycloak tokens in NestJS?

5–8 yrs🔥 Very common
Show answer

Use Passport's JWT strategy with jwks-rsa, so Nest fetches (and caches) Keycloak's public keys and verifies the RS256 signature, the issuer and the expiry locally, with no call to Keycloak on every request.

validate() maps the token to your user shape, and a global guard plus a roles or permission guard handles the rest.

import { Injectable } from "@nestjs/common";
import { PassportStrategy } from "@nestjs/passport";
import { passportJwtSecret } from "jwks-rsa";
import { ExtractJwt, Strategy } from "passport-jwt";

const ISSUER = "https://auth.example.com/realms/my-company";

interface KeycloakPayload {
  sub: string;
  preferred_username?: string;
  realm_access?: { roles: string[] };
}

@Injectable()
export class JwtStrategy extends PassportStrategy(Strategy) {
  constructor() {
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
      secretOrKeyProvider: passportJwtSecret({
        jwksUri: `${ISSUER}/protocol/openid-connect/certs`,
        cache: true,
        rateLimit: true,
      }),
      issuer: ISSUER,
      algorithms: ["RS256"],
    });
  }

  validate(payload: KeycloakPayload) {
    return { id: payload.sub, username: payload.preferred_username, roles: payload.realm_access?.roles ?? [] };
  }
}

🗣️ Say it in one line: passport-jwt with jwks-rsa verifies RS256 tokens locally against Keycloak's JWKS, checking issuer and expiry.

Q7

Roles vs permissions: how do you design RBAC on the backend?

8–10 yrs
Show answer

Guards check permissions (leave:approve), and roles are just bundles of permissions kept in config or a table. Adding a role then needs no code change.

Two levels of checks:

  • endpoint level: can this user call approve at all? (a guard)
  • data level: can this user approve this leave? It must be in their department, branch or region. This happens in the service or query (WHERE approver_id = :me). Most real security bugs (IDOR) are missing data-level checks.

Log every sensitive action in an audit log.

🗣️ Say it in one line: Guards check permissions, roles are bundles of permissions, and services enforce data-level ownership.

Q8

How should passwords be stored?

3–5 yrs🔥 Very common
Show answer

Never in plain text, and never with plain fast hashes like MD5 or SHA-256. Use a slow, salted password hash: bcrypt (cost 10–12), argon2id, or scrypt. The salt makes the same password hash differently each time, and slowness makes guessing expensive.

Even better: let an identity server like Keycloak handle passwords, so your application never touches them. Add rate limiting and lockout on login and OTP endpoints.

🗣️ Say it in one line: Slow salted hashes like bcrypt or argon2id, or delegate passwords to Keycloak entirely.

Q9

What are the most common API security risks and how do you prevent them?

5–8 yrs🔥 Very common
Show answer
  • Broken access control / IDOR: GET /orders/123 returns someone else's order. Always check ownership.
  • SQL injection: always use parameters or the ORM; never build SQL by joining strings.
  • Mass assignment: the client sends role: "admin". Use DTOs with whitelist: true.
  • No rate limiting: brute force on login and OTP endpoints.
  • Sensitive data in logs or responses: mask Aadhaar, phone numbers and tokens; never return password hashes.
  • Misconfiguration: open CORS (* with credentials), debug errors in production, public S3 buckets.
  • Vulnerable packages: run npm audit and Dependabot.

Also: HTTPS everywhere, the helmet middleware for security headers, and secrets in a secrets manager.

🗣️ Say it in one line: Ownership checks, parameterised queries, DTO whitelisting, rate limits, masked data and safe config.

Practiceप्रैक्टिस

Security scenarios come up in L2 and client rounds.

Mock task 1: A tester changes /api/applications/1051 to /1052 and sees someone else's data. Fix it.

Show a sample answer

That is an IDOR bug. In the service, load the record with the owner condition (WHERE id = :id AND user_id = :me, or check the branch/region scope for approvers) and return 404 or 403 if it doesn't match. Add this check in a shared helper or policy so every endpoint uses it, add tests for it, and search for other endpoints with the same pattern.

Mock task 2: Our reporting service needs to call the user service. How should it authenticate?

Show a sample answer

Use the Client Credentials flow: the reporting service has its own Keycloak client and secret (stored in a secrets manager), gets a short-lived token, and calls the user service with it. The user service checks that the token's client has the right role. No user passwords or shared static API keys.
