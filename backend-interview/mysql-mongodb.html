Q1

SQL vs NoSQL: how do you choose?

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: SQL databases are neat tables with strict rules, good for money and records. NoSQL is flexible, good for changing shapes or huge scale.

SQL (PostgreSQL, MySQL): tables with a fixed schema, relations and joins, strong ACID transactions. Best when data is related and correctness matters: payments, orders, HR, approvals, government records.

NoSQL is a family:

  • document stores (MongoDB): flexible JSON-like documents,
  • key-value stores (Redis),
  • wide-column stores (Cassandra),
  • graph databases (Neo4j).

It's good for flexible or changing shapes, very high write volume, or data always read as one whole document.

Honest answer: "Start with PostgreSQL unless there's a clear reason not to." It also handles JSON well with JSONB. Many systems use both: Postgres for core data, Redis for cache, and Mongo or Elasticsearch for logs or search.

🗣️ Say it in one line: Relational for connected data needing transactions, NoSQL for flexible shapes or extreme scale; Postgres is my default.

Q2

MySQL vs PostgreSQL: what are the real differences?

5–8 yrs
Show answer

🟢 In simple words: Both are good SQL databases. Postgres has more advanced features; MySQL is simple and very common.

Both are solid, open-source relational databases. Differences that come up in interviews:

  • PostgreSQL: richer features (JSONB with GIN indexes, arrays, CTEs, partial and expression indexes, strong extensions like PostGIS), strict about data types, default isolation Read Committed.
  • MySQL (InnoDB): very common in web apps and hosting, simple to run, great read performance with replicas, default isolation Repeatable Read. Historically it was more relaxed about bad data (it depends on sql_mode).
  • Both support window functions (MySQL 8+), JSON, and replication.

Choose by team skills and features needed, not by hype.

🗣️ Say it in one line: Postgres for richer SQL, JSONB and extensions; MySQL for simple, widely-hosted, read-heavy apps; both are reliable.

Q3

What are read replicas? What is replication lag?

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: A replica is a copy of the database used only for reading. It can be a few seconds behind the main one.

🖼️ Picture it

A read replica is a copy of the primary database that receives changes continuously and serves read-only queries. Use it for reports, dashboards and heavy reads, so the primary stays free for writes.

Replication lag: the replica can be a little behind (milliseconds, sometimes seconds). A user saves a profile, then reads from the replica and sees old data.

Fix: read your own writes from the primary (for example, for a few seconds after a write, or for that user's own record), and send only lag-tolerant queries (reports, analytics) to replicas.

💡 Easy example: The main notice board in the office (primary) and photocopies on each floor (replicas). The photocopies take a few minutes to update. If you just changed a notice, check the main board.

🗣️ Say it in one line: Replicas offload reads, but they lag, so a user's own just-written data is read from the primary.

Q4

MongoDB schema design: when do you embed and when do you reference?

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: Keep things together in one document if they're always read together; store just an id if the thing is shared.

Design for how the data is read:

  • Embed when the child data is owned by the parent, always read together, and limited in size: an order with its line items, a user with addresses.
  • Reference (store ids) when the data is shared, read separately, or grows without limit: a product used by many orders, the comments on a viral post.

Remember the 16 MB document limit, and avoid arrays that grow forever.

// Embed: read the order with its items in one go
db.orders.insertOne({ _id: "ord_1", userId: "u_7", items: [{ sku: "TSHIRT-M", qty: 2, price: 499 }], total: 998 })

// Reference: products are shared and change on their own
db.orders.insertOne({ _id: "ord_2", userId: "u_7", items: [{ productId: "p_55", qty: 1 }] })

🗣️ Say it in one line: Embed what is owned and read together; reference what is shared or grows without limit.

Q5

How do indexes work in MongoDB? What is the ESR rule?

5–8 yrs
Show answer

🟢 In simple words: Mongo indexes work like SQL indexes. Order the fields: exact matches first, then sort, then ranges.

MongoDB also uses B-tree indexes, including compound indexes where the order matters. Check queries with .explain("executionStats") and look for COLLSCAN (a full scan) vs IXSCAN.

The ESR rule for compound index order: Equality fields first, then Sort fields, then Range fields.

// Query: status = "pending" (equality), sort by createdAt, amount > 1000 (range)
db.orders.createIndex({ status: 1, createdAt: -1, amount: 1 })
db.orders.find({ status: "pending", amount: { $gt: 1000 } }).sort({ createdAt: -1 }).explain("executionStats")

🗣️ Say it in one line: Compound indexes in Equality, Sort, Range order, verified with explain().

Q6

What is the aggregation pipeline? Give an example.

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: An aggregation pipeline is an assembly line: filter → group → sort → limit, one step after another.

🖼️ Picture it

A pipeline is a list of stages; each stage transforms the documents and passes them on, like SQL's WHERE, GROUP BY and ORDER BY in steps:

  • $match (filter, put it first so it can use indexes),
  • $group, $sort, $project, $lookup (a join), $unwind (split an array into separate documents).
// Total sales per city for paid orders, highest first
db.orders.aggregate([
  { $match: { status: "paid" } },
  { $group: { _id: "$city", total: { $sum: "$amount" }, orders: { $sum: 1 } } },
  { $sort: { total: -1 } },
  { $limit: 5 },
])

🗣️ Say it in one line: A chain of stages like $match, $group and $sort, with $match first so it uses indexes.

Q7

Does MongoDB support transactions?

5–8 yrs
Show answer

🟢 In simple words: Yes, but they're slower. Good Mongo design keeps changes that belong together inside one document.

Yes. Single-document operations have always been atomic. Multi-document transactions exist since MongoDB 4.0 (replica sets) and 4.2 (sharded clusters), and they need a replica set, even in development.

They are slower than in SQL databases, so good MongoDB design tries to keep data that changes together in one document. If you need transactions everywhere, a relational database may be the better choice.

🗣️ Say it in one line: Yes, multi-document transactions on replica sets, but good Mongo design keeps atomic changes inside one document.

Practiceप्रैक्टिस

Scenario questions: say your choice and one trade-off.

Mock task 1: Store audit logs: 50 lakh rows a day, rarely read, kept for 1 year.

Show a sample answer

An append-only table partitioned by month in PostgreSQL (drop old partitions instead of DELETE), with few indexes. Or a document/log store (MongoDB with a TTL index, or OpenSearch) if search across fields is needed. Write asynchronously through a queue, so audit writes never slow down the main request.

Mock task 2: A dashboard query is slowing down the main database during office hours.

Show a sample answer

Move it to a read replica, or precompute the numbers into a summary table with a cron job or materialised view. Add the right indexes, and cache the result in Redis for a few minutes.
