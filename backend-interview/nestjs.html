Modules and dependency injectionModules and dependency injection

Q1

What is NestJS and why use it over plain Express?

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: NestJS gives Node.js a fixed, tidy structure (modules, controllers, services), so big teams write code the same way.

NestJS is a Node.js framework built on top of Express (or Fastify) that gives a fixed structure: modules, controllers, services, dependency injection, and decorators, in TypeScript.

Plain Express is flexible, but every team invents its own structure, which gets messy in big projects. Nest gives one standard way for validation, auth guards, logging, config, testing, queues and microservices. That is why enterprise and government projects with big teams like it.

🗣️ Say it in one line: Nest adds an opinionated, Angular-like structure with DI and decorators on top of Express, which keeps large codebases consistent.

Q2

What is dependency injection? How does Nest do it?

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: A class just says what it needs in its constructor, and Nest hands it over. The class never builds its own tools.

Dependency injection means a class doesn't create its dependencies; it asks for them in the constructor, and the framework provides them.

In Nest, you mark a class with @Injectable(), register it in a module's providers, and ask for it in a constructor. Nest's IoC container creates one shared instance (a singleton by default) and injects it everywhere.

Benefits: loose coupling, and easy testing, because in tests you inject a fake repository or service.

💡 Easy example: In an office you don't buy your own laptop; IT gives you one when you join. If you need a test laptop, IT gives you that instead. You just say 'I need a laptop'.

@Injectable()
export class LeavesService {
  constructor(
    @InjectRepository(Leave) private readonly leaves: Repository<Leave>,
    private readonly mail: MailService, // Nest creates and injects it
  ) {}
}

🗣️ Say it in one line: Classes declare what they need in the constructor and Nest's container creates and injects singleton instances.

Q3

What are modules? What do imports, providers and exports mean?

3–5 yrs
Show answer

🟢 In simple words: A module is a box for one feature. It shares things through exports, and uses other boxes through imports.

A module groups related code (a feature like Leaves).

  • controllers: handle HTTP routes.
  • providers: services, repositories and helpers that this module creates.
  • exports: the providers that other modules may use.
  • imports: other modules whose exported providers this module needs.

A provider is private to its module unless exported. A common error, "Nest can't resolve dependencies of X", usually means you forgot to export it or to import its module.

@Module({
  imports: [TypeOrmModule.forFeature([Leave]), MailModule],
  controllers: [LeavesController],
  providers: [LeavesService],
  exports: [LeavesService], // other modules can now inject LeavesService
})
export class LeavesModule {}

🗣️ Say it in one line: A module bundles controllers and providers; exports share providers, imports bring in other modules' exports.

Q4

What are provider scopes? How do you fix a circular dependency?

5–8 yrs
Show answer

🟢 In simple words: By default each service is created once and shared. A circular dependency means two services need each other; split out the shared part.

Scopes:

  • DEFAULT (singleton): one instance for the whole app. Fastest. Use it almost always.
  • REQUEST: a new instance per request, for per-request data like a tenant. It also makes everything that depends on it request-scoped, which costs performance.
  • TRANSIENT: a new instance for every consumer.

Circular dependency (A needs B, and B needs A): the best fix is to redesign, by moving the shared logic into a third service or using events. If you must keep it, use forwardRef(() => B) on both sides.

🗣️ Say it in one line: Singleton by default, request scope only when needed; fix cycles by extracting a shared service, forwardRef as a last resort.

Q5

Explain the NestJS request lifecycle.

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: A request passes through checkpoints in a fixed order before and after your code runs.

🖼️ Picture it

In order:

  • Middleware: raw request work (logging, request id, cookies). Doesn't know which handler will run.
  • Guards: can this request continue? (auth, roles). Return true or false.
  • Interceptors (before): wrap the handler (timing, caching).
  • Pipes: validate and transform input (DTO validation, ParseIntPipe).
  • Controller handler → service.
  • Interceptors (after): change the response (wrap it in { data }), log the duration.
  • Exception filters: if anything throws, turn it into a proper HTTP error response.

Global ones run first, then controller-level, then route-level.

💡 Easy example: Entering an office: the gate entry register (middleware), the security guard checking your ID (guard), reception noting your time in and out (interceptor), checking your documents are filled correctly (pipe), the meeting itself (handler), and if anything goes wrong, the escalation desk (filter).

🗣️ Say it in one line: Middleware → guards → interceptors → pipes → handler → interceptors → exception filters.

↪️ Follow-up: Guard vs middleware for auth? Guards know the ExecutionContext (which handler and class, and their metadata), so they can read @Roles(). Middleware can't.

Q6

Write a roles guard with a @Roles() decorator.

5–8 yrs🔥 Very common
Show answer

🟢 In simple words: Put a @Roles() label on a route. The guard reads the label and checks if the user has one of those roles.

Store the required roles as metadata with a custom decorator, read it in a guard with Reflector, and compare it with the user that the auth guard put on the request.

import { CanActivate, ExecutionContext, Injectable, SetMetadata } from "@nestjs/common";
import { Reflector } from "@nestjs/core";

export const ROLES_KEY = "roles";
export const Roles = (...roles: string[]) => SetMetadata(ROLES_KEY, roles);

@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private readonly reflector: Reflector) {}

  canActivate(ctx: ExecutionContext): boolean {
    const required = this.reflector.getAllAndOverride<string[]>(ROLES_KEY, [ctx.getHandler(), ctx.getClass()]);
    if (!required || required.length === 0) return true; // no @Roles(): allow
    const { user } = ctx.switchToHttp().getRequest<{ user?: { roles: string[] } }>();
    return required.some((role) => user?.roles.includes(role) ?? false);
  }
}

// usage: @UseGuards(JwtAuthGuard, RolesGuard) @Roles("hr", "admin") on a controller or route

🗣️ Say it in one line: A SetMetadata decorator stores the roles, and the guard reads them with Reflector and checks request.user.

Q7

How do you validate request bodies? What do whitelist and transform do?

3–5 yrs🔥 Very common
Show answer

🟢 In simple words: Describe the allowed body in a DTO class. ValidationPipe checks it and removes any extra fields.

Create a DTO class with class-validator decorators, and turn on a global ValidationPipe.

  • whitelist: true: removes properties not in the DTO, so a client can't sneak in isAdmin: true.
  • forbidNonWhitelisted: true: rejects the request instead of silently removing extra fields.
  • transform: true: converts the plain body into the DTO class and converts types (like "5" to 5 for query params).
import { IsDateString, IsIn, IsOptional, IsString, MaxLength } from "class-validator";

export class ApplyLeaveDto {
  @IsIn(["casual", "sick", "earned"])
  type!: string;

  @IsDateString()
  from!: string;

  @IsDateString()
  to!: string;

  @IsOptional()
  @IsString()
  @MaxLength(500)
  reason?: string;
}

// main.ts
// app.useGlobalPipes(new ValidationPipe({ whitelist: true, forbidNonWhitelisted: true, transform: true }));

🗣️ Say it in one line: DTOs with class-validator plus a global ValidationPipe using whitelist and transform.

Q8

What are interceptors used for? Write one.

5–8 yrs
Show answer

🟢 In simple words: An interceptor wraps your handler, like a stopwatch around it, to log timing or reshape the reply.

Interceptors run code before and after the handler, using RxJS. Common uses:

  • logging and timing every request,
  • wrapping all responses in one format ({ data, meta }),
  • caching,
  • timeouts,
  • mapping errors.
import { CallHandler, ExecutionContext, Injectable, Logger, NestInterceptor } from "@nestjs/common";
import { Observable, tap } from "rxjs";

@Injectable()
export class TimingInterceptor implements NestInterceptor {
  private readonly logger = new Logger("HTTP");

  intercept(ctx: ExecutionContext, next: CallHandler): Observable<unknown> {
    const req = ctx.switchToHttp().getRequest<{ method: string; url: string }>();
    const start = Date.now();
    return next.handle().pipe(tap(() => this.logger.log(`${req.method} ${req.url} ${Date.now() - start}ms`)));
  }
}

🗣️ Say it in one line: Interceptors wrap the handler for cross-cutting work like timing, response mapping, caching and timeouts.

Q9

How do you return consistent error responses?

5–8 yrs
Show answer

🟢 In simple words: Throw Nest's ready-made errors, and one global filter turns every error into the same neat JSON reply.

Throw Nest's built-in exceptions in services (NotFoundException, ConflictException, ForbiddenException), and add a global exception filter that formats every error the same way and logs unknown ones.

Never leak stack traces or SQL errors to the client. Map a database unique violation (Postgres code 23505) to a 409.

import { ArgumentsHost, Catch, ExceptionFilter, HttpException, HttpStatus, Logger } from "@nestjs/common";
import { Response } from "express";

@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  private readonly logger = new Logger("Errors");

  catch(exception: unknown, host: ArgumentsHost) {
    const res = host.switchToHttp().getResponse<Response>();
    const status = exception instanceof HttpException ? exception.getStatus() : HttpStatus.INTERNAL_SERVER_ERROR;
    if (status >= 500) this.logger.error(exception);
    res.status(status).json({
      statusCode: status,
      message: exception instanceof HttpException ? exception.message : "Something went wrong",
    });
  }
}

🗣️ Say it in one line: Built-in HttpExceptions in services plus one global filter that formats errors and hides internals.

Q10

How do you unit test a NestJS service?

5–8 yrs
Show answer

🟢 In simple words: In tests, give the service fake helpers (a fake repository) and check its logic alone.

Use Test.createTestingModule and give fake providers for dependencies (the repository, the mail service), then test the service's logic in isolation with Jest.

For APIs, write e2e tests with Supertest against the real app and a test database (often Docker). Test the important business rules: "only Pending leaves can be approved" and "HR can't approve their own leave".

const module = await Test.createTestingModule({
  providers: [
    LeavesService,
    { provide: getRepositoryToken(Leave), useValue: { findOneBy: jest.fn(), save: jest.fn() } },
    { provide: MailService, useValue: { send: jest.fn() } },
  ],
}).compile();

const service = module.get(LeavesService);

🗣️ Say it in one line: A testing module with mocked providers for unit tests, plus Supertest e2e tests on the important flows.

Mock task 1: Add a request id to every log line and response.

Show a sample answer

A middleware reads x-request-id or generates a UUID, puts it on the request and the response header, and stores it in AsyncLocalStorage (for example with nestjs-cls). The logger reads it from there, so every log line for that request has the same id, which makes tracing across services easy.

Mock task 2: Make one endpoint public while the JWT guard is global.

Show a sample answer

Create a @Public() decorator with SetMetadata("isPublic", true). In the global auth guard, read it with reflector.getAllAndOverride("isPublic", [handler, class]) and return true early when it is set.
